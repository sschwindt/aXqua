# Post-processing with VisIt (`axqua/postproc/`)

Figures from either solver's results. VisIt ships **its own Python**, so aXqua generates a script and runs `visit -cli -nowin -s` - the same shape as sourcing an `etc/bashrc`. Installed at `/home/IWS/public/visit` (3.5.0, the `linux-x86_64-debian12` prebuilt); config block `postproc:` (`visit` names the **launcher executable**, not a script to source). CLI: `axqua postproc <config> [--list] [--script-only] [--scene ...]`, plus a per-case `postprocessing.py`.

**The seam is `SolverBackend.describe_results(cfg) -> list[Dataset]`** (`BaseBackend` returns `[]`): a backend *describes* what it produced - path, times, fields, patches - and `postproc` draws it. That is what keeps `postproc` from importing a solver, enforced by a test. It is a top-level package, not `core/`, because it renders matplotlib and `test_capabilities` requires a capability listing to import nothing heavy.

v1 scenes: **`free-surface`** (isosurface of `alpha.water=0.5`; under a rigid lid it falls back to the lid patch and **says on the figure that the surface was prescribed**), **`velocity-plan`** (slice at 0.6*h, the depth a FlowTracker measures at), **`profiles`** (bed-to-surface `Lineout` per vertical, exported as curves; **VisIt samples, matplotlib draws** - the measured overlay needs error bars and the comparison must stay reproducible without VisIt). Run `profiles` at the prior centre and at the posterior - those two panels are the calibration result.

**Three things found only by running it**, each pinned by a test: VisIt opens an OpenFOAM case through **`system/controlDict`**, not `case.foam` (unlike ParaView it rejects a zero-byte `.foam` - 0 meshes, 0 variables on VisIt 3.5.0), and its variables are mesh-prefixed (`internalMesh/U`); **the time slider must be set explicitly**, or the figure renders `t=0` (velocity identically zero) behind a `0.000` colour bar while looking well-formed; and the script **must end with `exit(0)`** or `-nowin` hangs forever.


## TELEMAC results for ParaView and VisIt (`selafin_vtk.py`, `axqua export`)

**Neither program reads SERAFIN** (checked: ParaView 6.1.1 has no reader in its plugins, VisIt 3.5.0 has none), so `export_selafin` converts a result into VTK XML with numpy alone - no TELEMAC, no `vtk` package. One result becomes `<name>.pvd` (ParaView), `<name>.visit` (VisIt) and `<name>/<name>_NNNN.vtu`, zlib-compressed appended data in 32 kB blocks with `UInt64` headers. Each `.vtu` carries its time as `TimeValue` (ParaView) **and** `TIME` + `CYCLE` (VisIt): verified with both programs on a 26-step 2D and a 6-step 3D result of the Isar example (time steps, array names, ranges and the last time all agree with the source). `core.selafin.SelafinFile` is the frame-at-a-time reader this needs; `read_slf` loads every frame to return one.

**Coordinates come from `geometry.slf`, never from the result** (`geometry=`; the CLI passes the case's own). TELEMAC writes results in single precision, coordinates included, and at a UTM northing of 5.27e6 a float32 has a spacing of **0.5 m**: every northing in an `r2d.slf` is a multiple of 0.5. TELEMAC computes with the double geometry, so the *fields* are right; the *mesh stored in the result* is not. Measured on the isar-2025 mesh-convergence levels: coarser 4.5 %, baseline **14.4 %**, finest **39 %** of the cells have zero area in the result's own coordinates, and on the baseline 70 % changed their area by more than a quarter (4,188 inverted). ParaView confirms it on the export: 66,418 cells without area and +0.6 % water volume with stored coordinates, none with the geometry's. `model_column.safe_triangulation` already stated this rule for sampling; **what still uses the stored coordinates is everything that reads a result file alone - QGIS/MDAL drawing `r2d.slf` among them** - and the zero-length edges `_geom_stats` filters out are this, not an artifact of merging parallel results as its comment says. The root fix would be `RESULTS FILE FORMAT : 'SERAFIND'` in the steering files; it doubles every result file and changes the hotstart format lines, so it is the user's decision and is **not** made here.

**A 2D result is exported flat (z = 0) on purpose** (`zsource="flat"`). With the nodes at the bed, *Integrate Variables* runs over the sloping bed: on the example +1.4 % area and +1.7 % volume against the model's own. Flat, ParaView returns the plan area and the depth integral to all printed digits, and a *Stream Tracer* stays in the plane the depth-averaged velocity lives in (100 lines, z identically 0). The relief is one *Warp By Scalar* (`BOTTOM`) away; `--z bed|surface` writes it into the files.

**Prisms need two nodes swapped** (`_wedges`): TELEMAC walks both triangles counterclockwise seen from above, a VTK wedge wants the first triangle to face away from the second. Unswapped, every cell has a negative volume, which a picture hides. Checked three ways: ParaView's wedge-volume quality is >= 0 everywhere, ParaView and VisIt both integrate 1584.589 m3, and the depth integral of the same run's 2D companion is 1584.602 m3.

Names stay TELEMAC's (`WATER DEPTH`, with the space): they match QGIS and the TELEMAC manuals, and both programs select them from a list. Components that belong together also become a vector (`vector_groups`: `VELOCITY` from `U`, `V`, `W`; `FRICTION VELOCITY` is not a component of anything).
