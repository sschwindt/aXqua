# The solver-agnostic core: structures, profile and case file

Moved from the root `CLAUDE.md`; loaded when working under `src/axqua/core/`.

## Structures: dams, weirs, walls and buildings (`axqua/core/structures.py`)

**No STL anywhere, and that is not a limitation.** STL is a `snappyHexMesh` requirement: that mesher snaps a background block onto a triangulated surface, so every solid must arrive as triangles. aXqua writes `constant/polyMesh` directly (and `geometry.slf` for TELEMAC), so a structure only has to declare **where its footprint is** and **how high it stands** - both ordinary vector attributes. A structure layer is therefore a plain GeoPackage QGIS authors natively, with no CAD step and no format QGIS cannot round-trip.

**Geometry**: a **polygon** is the footprint directly; a **line** is buffered by its `Width (m)` (flat caps, mitred joins - a lozenge with rounded caps would over-block the channel at each end), which is how one actually draws a wall or a dam crest. **Height**: `Crest (m)` gives a *level* crest (dam, weir, floodwall); `Height (m)` gives a crest that *follows the terrain* (embankment, levee of constant build height). Neither is a sane default for the other, so the field the user fills in is what decides.

**Two modes, and the choice is hydraulic.** `overflow` (dam, weir, embankment, levee, block ramp) **raises the bed to the crest**: the structure is terrain the DEM did not carry, the plan mesh is unchanged, and water passes over it - identical in both solvers. `solid` (wall, floodwall, building, pier) **removes the footprint from the domain** so its sides become no-slip walls from bed to lid; use it for anything never overtopped, since it is both cheaper (no cells inside the obstacle) and more correct (a real vertical face rather than a very steep bed with a sliver of cells on top). The mode comes from the `Type` text by substring - the same convention as `classify_zone` - or from an explicit per-feature `Mode` column. Unrecognized text is `overflow`, deliberately: raising the bed keeps the domain connected and lets water pass, whereas wrongly blanking a footprint would silently wall off part of the reach. Note `block` is **not** a solid keyword - a *block ramp* is overtopped by design while a *concrete block* is not, so the word carries no usable signal.

**Where the two solvers necessarily differ**, and it is reported rather than left implicit: a 2D depth-averaged mesh has no vertical wall to remove, so `solid` structures are burnt into the TELEMAC bed as crest + `structures.solid_freeboard_2d` (default 2 m) - the standard way a floodwall is represented in TELEMAC - while OpenFOAM gets the genuine vertical face. In the OpenFOAM mesher the blanking is applied **after** `binary_fill_holes` in `build_plan_grid`: a building punched out of the domain *is* the interior void that hole-filling exists to close, so blanking first would simply be undone. If blanking disconnects the domain the build **warns** ("a solid structure has cut the domain in two") instead of silently deleting the far side. Verified end to end on isar-2025 with a dam polygon plus a floodwall line: 225 mesh vertices raised to the crest, the wall's columns removed, and `checkMesh` reporting **Mesh OK, 61,002 hexahedra, Number of regions: 1** with the wall's faces folded into the `banks` patch.

Config: `geodata.structures` (the layer) plus a `structures:` block for the attribute names (`type_field`, `mode_field`, `crest_field`, `height_field`, `width_field`, `name_field`, `default_width`, `solid_freeboard_2d`). Applied by `core.structures.apply_to_bed` / `solid_footprint`, called from `mesh.build_mesh` (TELEMAC, via `_burn_structures`) and `openfoam.mesh.build_mesh`. Tests: `tests/test_structures.py`.

## The profile and the case file: the computer and the reach are two files

**A case file (`*.axq-case`, `core/casefile.py`) describes a reach and names nothing that belongs to one computer; the profile (`*.axq-profile`, `core/profile.py`) describes a computer and nothing else.** Before this split, where TELEMAC lives was spread over `solvers.yml` (`core/machine.py`), `profiles.yml` (`jobs/profiles.py`), the plugin's QSettings and, in every one of the nineteen tracked case configs, a `telemac.pysource` naming one of three people's home directories. The profile is the one documented place now; **none of the older mechanisms was removed**, which is the rule that let this land without touching a single existing installation: a computer without a profile behaves exactly as before (pinned by `tests/test_profile.py`).

**Resolution order** (`core/machine.resolve`): environment variable -> case-local `solvers.local.yml` -> **active profile** -> `solvers.yml` -> the case file's own value -> discovery. The active profile is `--profile` -> `$AXQUA_PROFILE` -> `default.axq-profile` beside `solvers.yml` (so `AXQUA_HOME` relocates it, which is how the test suite stays off the developer's real profile; `conftest.py` also clears `AXQUA_PROFILE`). `resolve(use_profile=False)` exists for one caller: `profile.detect()`, which must see the settings a profile is about to replace rather than the profile itself - otherwise a wrong entry could never be re-detected.

**`load_active()` is deliberately not strict.** It runs inside every case load, so a profile with a typing error is reported once and skipped, and the older settings serve the build. The commands that are *about* the profile (`axqua profile show|check`) pass `strict=True`. It caches by path and modification time, because a study loads the case once per mesh.

**Machine settings as data: `core/schema.MACHINE_FIELDS`** (`telemac.pysource|environment|version|solver_python`, `openfoam.bashrc|environment`, `postproc.visit|environment`). `dump_config(portable=True)` leaves them out and is what `axqua migrate --to-case` writes; the **default keeps them**, because the other caller of `config_to_dict` is the job record, and a job has to be reproducible from its own folder including the installation it ran with. `n_processors` stays in the case file as a fallback: the profile's `mpi_processes` wins where set (`jobs.profiles.from_plugin_profile`), a binding without a number has no opinion.

**The job system takes its binding from the active profile** through `jobs.profiles.implicit(cfg, solver)`, which replaced the two `from_config` call sites in `jobs/submit.py`. `--profile` accepts an `.axq-profile` file as well as a name out of `profiles.yml`; a file binds several codes, so `jobcli.run_submit` passes the solver of the job kind. One real bug fell out: `spec.launcher["requested"]` is always at least `"auto"`, which is truthy, so `requested or profile.launcher` never reached a profile's launcher. `"auto"` now means "no opinion". **`implicit` follows the resolution order too**: where the environment variable of a code or a `solvers.local.yml` outranks the profile, the job takes that script, keeps what the profile says about the computer (environment kind, processes, job root, launcher) and drops `config_name` and `overrides`, which belong to the installation of the profile. Until the review of 2026-10-10 a case was loaded with one installation and its job computed with another. A name given to `--profile` is looked up in `profiles.yml` first; only a name ending in `.axq-profile`, or one that is no profile name and is a file, is read as a profile file.

**Checks return findings, they do not raise** (`core/diagnostics.Finding`: severity, dotted code, subject, message, remedy; `anchor` is the label of the code in the docs). `profile.check()` has three tiers - files, factual, functional - and the functional one (`SolverEnvironment.validate`, unchanged) is what tells a working installation from a path that merely exists; it costs ~5 s here and `probe=False` skips it. `axqua profile check` exits 0 whatever it finds: findings are the *result* of the command, and an editor has to be able to show them all and still save. `axqua profile write` (JSON on stdin, what the plugin will call) parses before it writes, so a document that is not a profile cannot replace one that is. **`profile.file_path()` is the one place that says which file a profile name means**: a file that exists is used as it is named, a name without a file gets the suffix. `save` used to append the suffix always, so `profile init office` asked about `office` and wrote over `office.axq-profile`, and a profile kept in a file without the suffix (`AXQUA_PROFILE=~/this-computer.yml`) was read from that file and saved to another one beside it.

**The profile also names the folder each program is installed in** (`installations: {telemac, openfoam, paraview, visit}`; the user's decision of 2026-10-11, "the profile should also store local installation directories"). What aXqua runs is still the environment script of a code and the launcher of a postprocessor; where the profile names the folder only, `AxquaProfile.script()` looks the file up in it (`profile.locate`, by the table `LAYOUT`: `configs/pysource.*.sh` without the template, `shell-rc.sh` before `etc/bashrc`, `bin/paraview`, `bin/visit`, and the same one level below for the folder a wizard was given), so **a profile of four folders is a complete one** (checked on the main workstation against the real installations: `profile check` enters TELEMAC and OpenFOAM from it, and a build, a steady run and a calibration ran with it). An entry under `solvers` / `postprocessors` outranks the folder. Several environment scripts in one folder are a decision aXqua does not take (`locate` answers `None`, the check names them). `installation_of()` goes the other way and is what `detect()` and the installation runner (`bind`) use to enter the folder; a launcher in `/usr/bin` has none ("installed in /usr" says nothing), and a launcher that is a link is followed, the folders above it are not. `machine.resolve` and the job binding (`jobs.profiles.from_plugin_profile`) both go through `script()`. For the plugin: `axqua profile locate <program> <folder>`, and `programs` in the answer of `profile show` (what is run for each program; not part of the file, the editor strips it).

**A profile outlives the version that wrote it** (the user, same day: "when one updates the aXqua plugin in the future, profiles should be retained for local users"). It is kept in the configuration folder of the user, outside of the package and of the plugin (pinned by `test_the_profile_is_kept_outside_of_axqua_and_of_the_plugin`), and the plugin stores nothing but the path of the `axqua` program, in the QGIS settings. Three rules, stated in the docstring of `core/profile.py`: the layout only grows (the text `WRITTEN_BY_0_4_2` in `tests/test_profile.py` is a profile of that version and is never edited); **an entry this version does not know is kept and written back** (`extra`, a warning `axqua.config.unknown_entry` with the nearest known name, where a misspelled key used to make the whole profile unreadable) because the plugin and the library are updated separately and each may meet a file the other wrote; and `save()` never writes over a file it could not read without moving it to `<name>.<date>-<time>.bak` first (`profile.backup`, reported by `profile write` and shown by the editor). The last one closed a real loss: the plugin offers *Create profile...* when the profile cannot be read, and saving the detected one replaced the file. Text where a number belongs (`mpi_processes: many`) was an uncaught `ValueError` in every case load; it is a `ConfigError` now.

**`find_case_file(folder)`** is what the template scripts call instead of naming their case file. One `*.axq-case` is the answer; several raise and name them (a silent pick would run a different model than the user thinks); none falls back to `case-config.yml`. The example cases name their file explicitly, because isar-2025 has five variants. **`cases/munich-vsf/` and `cases/slot-flume/` are NOT converted** - the second workstation runs from them (issue #5); they keep `case-config*.yml` until it confirms.

**What an editor of a case needs is three verbs and one table** (`casecli.py`): `axqua schema` (the field table of `core/schema_meta.py`), `axqua case read|write|new`, and `axqua check` (`core/casecheck.py`). `Config.validate()` is now `for _, step in self.checks(): step()` - the same steps in the same order, as a list of `(what about, step)` - so that the check can run every one of them and report one finding per block instead of only the first failure; steps marked `machine` (`telemac.validate_installation`, the three `environment.validate`) are skipped there, because where TELEMAC is installed is the profile's finding, not the case's. `TelemacEnv.validate` was split into `validate_installation` + `validate_choice` for that reason. The check never raises, whatever the file holds, and `case write` saves first and checks afterwards. Every code either check can emit has an anchor in `docs/troubleshooting/` (`test_every_code_..._is_explained_in_the_documentation`).

## The config schema: round-tripping, classification, and typed errors

**`dump_config(cfg, path)` (`config.py`) is the counterpart of `load_config`**, and exists because anything that *edits* a case - a form in the planned QGIS plugin, a migration, a scripted sweep - has to put the result back. It goes through the dataclass rather than rewriting the YAML text, which **loses comments but cannot produce a config that will not load**; a comment that survives an edit it no longer describes is worse than no comment, and the annotated prose lives in `cases/case-template/case-config.yml`. Paths are written **relative to where the file will live** (`base=`), so `axqua migrate -o elsewhere/case.yml` does not silently break every relative data path, while a path outside the case tree (a solver install) stays absolute. Guarded by a parametrized round-trip test over **all ten** case configs in the repo: `load(dump(cfg))` is field-by-field identical.

**`axqua migrate <config> [-o out | --in-place]`** writes a config back in the current schema - loading already applies every compatibility mapping, so this just makes the file say what aXqua actually read and stops the deprecation warnings. `--in-place` keeps a `.bak`. `--to-case` derives the name of the new file and does not write over a file of that name that exists (it may have been edited since; naming it with `-o` replaces it). For a config that is a case file already the derived name is the file itself, so it is rewritten as `--in-place` does, and neither writes machine settings into a case file.

**`core/schema.py` states which settings are shared intent and which name a solver keyword** - as *data*, because a form-based editor cannot guess. The rule: a fact about the reach or the modeling goal is `SHARED` (geodata, boundaries, friction, ground truth, structures, `mesh.channel_size`, `hydrodynamics.duration`); a knob of one code belongs to that code (`mesh.growth_ratio` is BAMG's, `hydrodynamics.implicitation` is Telemac2d's, `openfoam.max_courant` is interFoam's). Only the genuinely mixed blocks (`mesh`, `hydrodynamics`) are spelled out field by field, and only their SHARED entries - so "is this shared?" has to be answered deliberately. An unknown key classifies as SHARED, which fails safe for a form (showing a setting on the reach page is a smaller mistake than hiding it behind a solver the user has not enabled). Two tests keep the table from drifting away from the dataclasses it describes. **The fields have deliberately NOT been moved.** The plan folded `openfoam.cell_size` into `mesh.channel_size`, but `openfoam.cell_size_factor` now expresses the OpenFOAM lattice *relative to* the 2D channel size - the same shared-intent link, without pretending the two numbers are the same quantity (a per-zone anisotropic target edge length vs a uniform Cartesian spacing). The rest would be pure renaming: no behavior change, every case config touched, the artifact regression baseline invalidated. `LEGACY_KEYS` is the mechanism for doing it later without breaking a config - it maps dotted old key to new, is applied at load, and emits **one aggregated** warning rather than a per-key wall of text. Note `project.results_dir` maps to `calibration_dir`, **not** `model_dir`: the old single "results" folder is where the HydroBayesCal artifacts land.

**`core/errors.py`** gives failures a **stable machine-readable `code`**, an optional `subject` (the config key or layer the failure is about) and an optional `remedy`. Not decoration: a job record has to store a failure that survives serialization, a plugin has to put a message next to the field that caused it, and a batch has to decide what is worth retrying. Deliberately **five categories, one level deep** - `ConfigError` (fix the YAML), `GeodataError` (fix the data), `EnvironmentError` (fix the install), `SolverError` (read the listing), `MeshError` (change resolution) - because mirroring the module layout would produce thirty classes that callers catch by their base anyway. `ErrorRecord.from_exception` turns *any* exception into a JSON-safe record, labeling an unanticipated one `axqua.unexpected` rather than mislabeling it. Additive: existing `ValueError`s keep working.

## Package structure: solver-agnostic core + pluggable backends

aXqua is structured so TELEMAC and OpenFOAM are **two backends behind one case
description**, rather than one tool with a second bolted on.

**Two rules, enforced by tests rather than intent** (`tests/test_capabilities.py`): nothing in `core` imports a solver, and the OpenFOAM backend never reaches into the TELEMAC backend. Both are checked by reading the source, so they hold even for imports that only happen inside a function. OpenFOAM *is* hotstarted from a TELEMAC result, but it reads it through the shared SERAFIN codec in the core - which is exactly why `selafin` sits there.

**Every historic import path still works.** `axqua/mesh.py`, `steering.py`, `pipeline.py` (14 of them) plus `selafin.py` and `openfoam.py` are **shims that alias through `sys.modules`**, not re-export modules: `axqua.mesh is axqua.solvers.telemac.mesh` is literally true. Re-exporting would have silently dropped every private name (tests import `mesh._parse_decimal`) and broken identity checks; aliasing means there is exactly one module object and no second surface to keep in step. Parametrized over all 16 in the tests.

**Both `solvers/*/__init__.py` resolve attributes lazily** (PEP 562), like the top-level package. Not decoration: each backend's `spec.py` is read by `axqua status` to build a capability table, and importing `axqua.solvers.telemac.spec` runs the package `__init__` first - so eager imports there would drag gmsh and numpy into a question that should cost nothing. Measured: `import axqua` 6 ms / 64 modules, a capability listing 30 ms with **zero** heavy modules.

**Capabilities and the `MODEL=` marker files (`axqua/core/capabilities.py`).** Every
case carries one marker per solver at its top level - `MODEL=TELEMAC_ENABLED`,
`MODEL=OPENFOAM_DISABLED` - whose **name** says whether *the case* declares that solver
(`cfg.declared_blocks`, so the filename means the same on any machine) and whose **body**
is a strictly parseable status table: `#` comments, `key = value` header, then fixed-width
rows after `[capabilities]`. Each capability is reported on **three axes**, kept apart
because they have three different fixes: `implemented` (does aXqua support it *for
this solver* - `yes` / `no` = not yet / `n/a` = category error, e.g. OpenFOAM has no
depth-averaged mode while its morphodynamics is merely unbuilt), `configured` (does this
case ask for it, from the config alone), and `built`/`run` (do the artifacts exist - pure
path checks, never a parse, so a status report is fast and cannot fail). Unanswerable
cells render `-`, never a confident `no`. The files are **generated and gitignored**
(`cases/*/MODEL=*`, with `cases/case-template/MODEL=*` committed as the documented
example): they report the *currently available* setup, which is local state like
`axqua-case/`. Refreshed by `pipeline.run`, by `openfoam.build_case` and by
`axqua status <config> [--check-env] [--full]`; `refresh_markers` never raises, since
a succeeded build must not report failure because a status file could not be written.

**The solver registry (`axqua/core/registry.py`).** A backend is described by a
`BackendSpec` - name, title, config key, the capability support matrix, and the
`built`/`run` path predicates - which is **metadata only**, deliberately separate from the
`SolverBackend` implementation that builds and runs. The spec modules
(`axqua/solvers/{telemac,openfoam}/spec.py`) are import-light by contract: they use
the standard library plus attribute access on a `Config`, and nothing else. That is what
lets `axqua status` - and, later, a QGIS plugin running inside the QGIS Python process
- answer "what can this case do?" without importing gmsh, rasterio, pandas or a solver.
Backends are discovered through the `axqua.solvers` entry-point group, with a
hard-coded built-in list as a fallback for source checkouts that predate the group, so
"add your own" and "use ours" are the same mechanism.

**`axqua/__init__.py` resolves attributes lazily (PEP 562).** `import axqua` went
from 505 ms / 652 modules to **21 ms / 64 modules**, and a capability listing imports
**zero** heavy modules - measured, and asserted in `tests/test_capabilities.py` from a
subprocess so the rest of the suite's imports cannot mask a regression. The public API is
unchanged (`from axqua import build_mesh` still works); `__all__` is written out
literally because linters and IDEs read it statically, and a test keeps it in step with
the `_EXPORTS` map.
