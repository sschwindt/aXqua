# TELEMAC meshing and the mesh-convergence study

Moved from the root `CLAUDE.md`; loaded when working under `src/axqua/solvers/telemac/`.

### Meshing (stage 2)

The mesher is **gmsh**, chosen over the SALOME/Q4TS route (which the working Inn model historically used) because gmsh is pip-installable, fully headless/scriptable, and supports the anisotropic meshing needed here - whereas Q4TS runs inside SALOME's GUI/SMESH stack and is heavyweight/version-sensitive to automate. SALOME is installed beside TELEMAC on the main workstation if ever needed.

- **Anisotropic, flow-aligned channel** (the requirement): channel triangles are *elongated along the channel centerline*, floodplain triangles near-equilateral, with a smooth transition. Implemented exactly like gmsh tutorial **t17**: build a coarse background triangulation (a Delaunay grid over the ROI bbox, node-budget-capped ~40k so any domain fits in memory), assign each background node a **3×3 metric tensor** (eigenvalue = 1/h²; anisotropic `1/(channel_size·anisotropy)²` along the local centerline tangent and `1/channel_size²` across, inside `channel` zones; isotropic `1/floodplain_size²` elsewhere), push it as a `TT` list **PostView** + `setAsBackgroundMesh`, then mesh with **`Mesh.Algorithm=7` (BAMG)**, `Mesh.SmoothRatio=growth_ratio`, `Mesh.AnisoMax`. The coarse background also produces the smooth channel→floodplain blend (gmsh interpolates the metric within each background triangle).
- Zone selection is by **substring** of the `Zone Name` attribute (case-insensitive): `*channel*` vs `*floodplain*` in `geodata.mesh_zones`. The centerline (`geodata.channel_centerline`) is sampled and `np.gradient` gives per-vertex tangents (nearest via `cKDTree`).
- BAMG **approximates** the metric: realized cross-channel size and anisotropy come out a bit gentler than the configured targets, and `growth_ratio` (default 1.2) intentionally relaxes them near banks. Knobs: `mesh.channel_size` 0.5, `floodplain_size` 1.5, `growth_ratio` 1.2, `channel_anisotropy` 4.0, `max_aspect_ratio` 4.0. Defaults are **high-res**: the Inn KB15 ROI (~0.32 km², ~130 m-wide channel) yields ~720k elements / ~360k nodes (~90 s, ~0.7 GB; the aspect cap below tightens `AnisoMax` which refines the mesh) - raise the sizes while iterating.
- **Aspect-ratio cap** (`mesh.max_aspect_ratio`, default 4.0 = longest:shortest edge): BAMG overshoots the metric anisotropy in the tail (~1.6x) and leaves a few channel slivers, so `Mesh.AnisoMax` is set to `max_aspect_ratio/1.6` and a post-mesh **edge-flip** pass (`_flip_sharp_edges`) flips the shared (long) edge of over-sharp cell pairs - a topological repair that touches only the offending cells (boundary untouched, IPOBO/winding preserved, no inversions), bringing the realized channel max from ~6.5:1 down to ≤~4:1 while keeping the bulk elongation (channel aspect median ~2.0 vs floodplain ~1.4).
- **The anisotropic mesh is NOT reproducible run to run** - a measured property, not a suspicion. Building the isar-2025 mesh twice from identical inputs **inside one process** gives 230,286 vs 231,223 nodes (458,769 vs 460,654 elements, 1801 vs 1790 boundary nodes; ~0.4% spread, min edge 0.191 vs 0.194 m). The cause is the retry below: **BAMG fails intermittently on the first attempt** with the same inputs, and the retry ladder then meshes with a coarser background metric grid, giving a different but equally valid mesh. gmsh is already single-threaded (`General.NumThreads` = 1), so this is not thread scheduling. Consequences worth knowing: `geometry.slf` / `boundaries.cli` / `initial-conditions.slf` **cannot be byte-compared** between runs (regression-test them on mesh *statistics* within ~1% instead); a **resumed mesh-convergence study may compare levels built at different retry rungs**, so a level re-run is not guaranteed to reproduce its own earlier mesh; and a published result should quote the `geometry.slf` actually used rather than assume it can be regenerated bit-for-bit. The OpenFOAM mesh has no such problem - it is aXqua's own structured lattice and *is* bit-reproducible.
- **BAMG failure retry** (`build_mesh`, `_BAMG_RETRY_LADDER`): at fine, high-contrast anisotropic metrics (e.g. a small `refinement` zone next to a coarser floodplain, hit as the mesh-convergence study refines) BAMG's Delaunay insertion can abort with `Fatal error in the meshgenerator 1001 / BAMG failed`. Empirically a **coarser** background metric grid rescues it (larger background triangles smooth the interpolated size gradient BAMG must honor; a *denser* grid makes it worse), as does a looser `Mesh.AnisoMax`. `build_mesh` therefore retries `gmsh.model.mesh.generate(2)` on a BAMG failure with a ladder of `(background node budget, AnisoMax relaxation)` each gentler than the last (`(40000,1.0) -> (20000,1.0) -> (10000,1.5) -> (6000,2.5)`) before re-raising; the normal path meshes on the first (default) attempt with no retry. Isotropic meshing has a single attempt.
- The **isotropic fallback** (no mesh_zones/centerline) is the original distance-field path (`default_size`/`breakline_size`/`region_sizes`); the integration test exercises it.
- **Quality assessment** (`mesh_quality.py`, vectorized, scales to the ~525k-element mesh): logs per-region (channel vs floodplain, via a centroid-in-`_channel_union` mask) internal angles, aspect ratio, skewness; the **shortest edge** (flagged as CRITICAL for the CFL-limited adaptive time step); and the fraction of adjacent-cell area jumps over `mesh.max_area_jump` (20%). The channel is `relaxed=True` so its *intended* anisotropy (aspect ≫ 1) is reported but never warned on - shape warnings (angle < `min_angle_deg`/> `max_angle_deg`, high aspect) apply to the floodplain only. Fatal defects (zero-area, inverted/mixed-orientation, duplicate nodes, non-manifold edges) **raise**; orphan nodes, extra boundary loops (hanging gaps) and IPOBO mismatch (wrong boundary tags) warn. Thresholds are `mesh.min_angle_deg`/`max_angle_deg`/`max_area_jump`.
- Meshing (mesh-zones) and friction (roughness-zones) are **separate concerns**: `geodata.mesh_zones` only sizes the mesh. Friction zonation comes from `geodata.roughness_zones` (an integer `Zone ID` per polygon): `mesh.interpolate_roughness(cfg, mesh)` tags every node/element with the `Zone ID` it falls in (nearest polygon otherwise), writes it as the per-node `FRIC_ID` (overriding the MATID-derived ids), and stores the `roughness_table` value for that id as the `BOTTOM FRICTION` variable. `mesh.run` (hence `pipeline.run`) calls it whenever `roughness_zones` + `roughness_table` are set, so the built `geometry.slf` carries the zone `FRIC_ID` + `BOTTOM FRICTION`, and `steering.write_friction_tbl` derives the matching `.tbl` rows (`<Zone ID> NIKU <ks> NULL`, law `friction.roughness_law`, default 5) from the same table. HydroBayesCal perturbs each `ks` via `zone1`/`zone2`.

The mesh-convergence study (`axqua/convergence.py`, step 2; `cases/example-Inn/mesh_convergence_study.py`, which creates and works in its own `axqua-case/mesh-convergence/` folder) runs the same steady sim on a **four-mesh r=1.3 ladder** (`ratio_levels`: one coarser x1.3, the configured baseline, two finer /1.3 and /1.3² - Celik et al. 2008 recommend a grid refinement factor **r >= 1.3**; closer-spaced grids like the old ±20% `percent_levels`, kept only for backward compat, drown the grid-to-grid differences in solver noise and degenerate the GCI denominator r^p−1) at constant discharge with TELEMAC's variable time step (per-mesh CFL dt), samples water depth + scalar velocity at the ground-truth probe points (`default_probes`) (**no point within `boundary_clearance` of the inflow/outflow lines** since 2026-11-04, the user's rule "never evaluate the model close to its boundaries": 4 (`BOUNDARY_ADAPTATION_LENGTHS`) flow adaptation lengths h/(2 c_f) (Struiksma 1985) of the case depth (`steering.flow_scale`) and channel ks, KB15 4 x 47 = 189 m, capped at a quarter of the centerline; measurement points closer to a liquid line are dropped, fewer than three left -> centerline. Measured on the six KB15 k-epsilon meshes at points every 10 m: the mesh-to-mesh velocity difference was 0.75 m/s 15 m below the inflow and the time swing 0.2 m/s, both down to the interior level (<0.02 m/s) within 150-200 m, nothing comparable at the outflow. With the old points (from half a step = 21 m) one point below the inflow made 93 % of the first velocity change (11 %) and the four-mesh study read not converged; with the clearance it reads converged at 5 % (velocity 4.8/2.2/3.0 %, depth 2.9/2.2/2.0 %), the bar edge making most of the rest), and judges convergence on the **GCI of the finest grid triplet** (observed p clamped to `THEORETICAL_ORDER` 2 for the GCI; an **asymptotic-range check** `GCI(med)/(r^p·GCI(fine)) ∈ 0.8..1.25` decides whether the GCI is trustworthy, else the finest successive relative change is the fallback - `ConvergenceReport.verdict_basis`) vs a tolerance (default **5%**, `DEFAULT_TOLERANCE`; Celik: 5-10% is engineering accuracy). Each level is built with **`mesh.size_scale`** (= level channel size / config `channel_size`), a global multiplier applied to *every* target edge length **including the per-zone `Max Edge Length (m)` gpkg values** - scaling only `channel_size`/`floodplain_size` does nothing when the gpkg carries that field (the bug that invalidated the first ering study: five "levels", one mesh). The study is **resumable** (each level folder gets a `level.json`; on re-run a prompt offers reusing completed levels, QoI re-extracted from their `r2d.slf`; size-mismatched levels re-run) and **extensible**: when not converged it offers up to `MAX_EXTRA_LEVELS` further /1.3 refinements one at a time, each prompt showing a **runtime estimate** (log-log fit of measured runtimes, theoretical t~dx⁻³ fallback) and the **mesh-validity check** of the candidate size; non-interactive sessions auto-resume and auto-stop (no hang). A refinement that **fails to mesh/run** (e.g. BAMG gives up even after its retries, or the solver diverges) is caught as the practical refinement limit: the extension stops and the report is written from the levels already completed, instead of crashing the study. **Auto-refinement mode** (`run_mesh_convergence(auto_extend=True)`, exposed by the per-case `mesh_convergence_study.py` as `python .../mesh_convergence_study.py mode='auto-refinement'`) auto-approves the resume prompt and every extension (no prompts, interactive or batch) so the study marches finer one grid at a time until it converges, exhausts `AUTO_MAX_EXTRA_LEVELS` (default 8, vs. the interactive `MAX_EXTRA_LEVELS` 3), or a level fails. Every level's report row carries the `axqua/mesh_validity.py` checks: shear velocity from the fully-rough log law, wall **y+** (O(10⁴) in rivers, always passes - reported as standard), roughness Reynolds **ks+** (>=70 fully rough for the Nikuradse law), **dx vs ks** (dx < channel ks = roughness double-counting risk; fires first under refinement), and **turbulence-model consistency** (`steering.turbulence_pick_for_dx` vs the pinned baseline model). The study fixes **one flow depth for all meshes** (`_with_turbulence_depth`: the case's steady result, else normal flow on the case mesh, set as `turbulence_length_scale` on a copy, since a level folder has no result of its own), pins the model chosen on the **case's own mesh**, judges each level by the **filter width measured on its `geometry.slf`** (`steering.geometry_filter_width`, the nominal cell size understates it about 1.5x on the anisotropic mesh), and a resume **re-runs a level whose `steady2d.cas` ran another TURBULENCE MODEL** (`_level_turbulence`). **The 2D levels are averaged over the second half of their run too** (`TIME_WINDOW` 0.5, `extract_mean_at_points`, `LevelResult.fluctuation`/`n_frames`, `ConvergenceReport.unsteady_quantities`; since 2026-11-03): with k-epsilon the KB15 flow oscillates at the inflow (point 1 on the baseline mesh 0.97-1.36 m/s, period ~1,100 s; fluctuation at the points 3.2 % baseline, 1.1 % finest), which Spalart-Allmaras had damped; a reused level is averaged the same way (a result of another code, `result_name`, is still read at its last frame). Every per-level build is **pre-wetted** (`INITIAL_DEPTH`, default 0.5 m -> `initialization.prewet_depth`): the channel mesh-zone nodes are hotstarted with that water depth so the solver need not advance the wetting front from a dry bed (see "Pre-wetting" below). `ConvergenceReport.to_xlsx()` writes a **styled .xlsx** (openpyxl) to `mesh-convergence/` (incl. the validity rows) and `recommendation()` picks the **coarsest grid-independent cell size** (convergence vs. compute-time tradeoff, with the runtime speed-up vs. the finest; under a GCI verdict with no rel-change-adequate level it recommends the medium grid of the converged triplet). The TELEMAC run is injectable (`simulate=`) so the report maths/xlsx are unit-tested without the solver (`tests/test_convergence.py`, `tests/test_mesh_validity.py`). Results SELAFINs are read with the minimal `selafin.read_slf` (the writer's counterpart; single/double precision, multi-frame, returns the last frame). **A level is read on its own `geometry.slf`** (`mesh_coordinates`, `extract_at_points(..., geometry=)`, `_geom_stats(..., geometry)`; since 2026-11-02): the float32 coordinates of `r2d.slf` resolve 0.5 m at a UTM northing, which on the Inn KB15 ladder floored the reported shortest edge of both fine meshes at 0.50 m (really 0.77 and 0.58 m) and moved the mean depth at the points by up to 1.6 %, a fifth of the change between two meshes; the field is interpolated in the mesh's own triangles (`_interp_on_mesh`), not in a Delaunay of the nodes. Without a matching geometry the old path is kept. `write_study_report` also draws `<stem>.png` (`plot_report`: value at each point per mesh, mean against cell size, change per refinement against the tolerance) and the workbook has a sheet *values at the points*; both serve the 2D, vertical and OpenFOAM studies. **What the Inn KB15 ladder showed (2026-11-02, sandbox case, size_scale 3, 30 September verticals)**: steady to <0.25 % over the last 2000 s on every mesh, wetted area falling 159,276 -> 156,636 m2, and a change of 7-12 % per refinement in depth and velocity that does not shrink: mean depth and velocity zig-zag, the observed order is not computable, the verdict falls back to the relative change. That is the expected result on a natural reach, not a defect. **The vertical study averages each layer count over the second half of its run** (`vertical_convergence.FRAMES` 20 result frames per run via `build_3d_cas(graphic_frames=)`, `WINDOW` 0.5, `convergence.extract_mean_at_points` -> `TimeAverage`; since 2026-11-03) and reports the fluctuation in time per level (`||std_t|| / ||mean||`, the norm of the relative change) plus a note when the finest change is not larger than it (`VerticalConvergenceReport.unsteady_quantities`). Reason, from the Inn KB15 trial (3/5/7 levels, k-epsilon, 13.9 h on 16 cores): verticals 12 to 30 around the bar moved by 1 to 5 cm and 0.1 to 0.3 m/s between outputs 1,000 s apart, as much as between layer counts; with snapshots the verdict read depth 6.8/5.4 %, velocity 40/25 %, averaged over the last three frames depth 3.9/2.8 %, velocity 38.8/14.6 % (fluctuation 26/12/6 %). The same trial: the 3D model is 14 cm shallower at the verticals than the 2D one with the same per-node ks (TELEMAC-3D reads `BOTTOM FRICTION` from the geometry; its bed shear is a log law at the first plane, `tfond.f`, so it depends on the lowest layer's thickness), and dz at 7 levels (0.151 m) equals the channel ks.

**Measurement points near a liquid boundary and the 3D mesh (the user's orders of 2026-11-04).** (1) A measurement point less than `bayescal.MIN_BOUNDARY_NODES` (15) mesh nodes from an inflow or outflow node (shortest path over mesh edges from the liquid nodes of `boundaries.cli`, `boundary.liquid_boundary_hops`, nearest node of the point) is dropped by `bayescal.away_from_liquid_boundaries` from the calibration CSV (`build_velocity_csv`, which the validation uses too, and `compile_flow_csvs`) and from the mesh study's measurement probes (fewer than three left -> centerline). The warning goes to the logger `axqua.near_boundary` with the user's remedy text `NEAR_BOUNDARY_REMEDY` ("Increase ROI beyond the concerned liquid boundary."); `jobs.executor._surfaced` copies that logger's warnings into the result manifest's `summary.warnings`, which the plugin shows on *Load results* (`jobs_widget._results_found`, also for a job without layers). An unbuilt case keeps every point. Isar example: the 33 November calibration verticals all stay, 29 of 83 September validation verticals (outflow) go. (2) `mesh.size_scale_3d` gives the TELEMAC-3D runs their own horizontal mesh: `threed.three_d_case(cfg)` returns a copy with that size scale, `model_dir` = `axqua-case/simulation-3d/` and its own `calibration_dir`; `prepare_three_d_mesh` builds it with `pipeline.run` (rebuilt when the case's geometry is newer or the scale changed, stamp `mesh-3d.json`) and writes the case's `r2d.slf` interpolated onto it as that folder's `r2d.slf` (`interpolate_result`: linear in the 2D triangles on the double-precision geometry, its own BOTTOM, FREE SURFACE = bottom + depth, single precision like TELEMAC). The backend's 3D build, 3D runs, unsteady 3D and vertical study all go through it; the vertical study's report stays in the case's `postprocessing/vertical-convergence`. KB15 at 2.308: 76,694 nodes, built in 12 s, smoke run fine (same 0.21 s step as the baseline, set by dz).
