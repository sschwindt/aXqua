# The OpenFOAM free-surface extension

**Optional OpenFOAM free-surface extension (`openfoam_preprocessing.py` / `openfoam_run.py`, `axqua/openfoam/`).** A **3D two-phase (VOF) `interFoam` case** built from the same config, the same geodata and the same converged `r2d.slf` as the TELEMAC case, into `<sim_dir>/openfoam/`. Entirely **additive**: a config with no `openfoam:` block gets the default `OpenFoam` dataclass and nothing in the TELEMAC path consults it. It exists because `simpleFoam` cannot represent a water surface with a gradient (so the air-water interface must be modeled) while the air phase itself is of no interest and is what usually wrecks these runs.

**The TELEMAC pre-run seeds it, automatically (`axqua/prerun.py`).** OpenFOAM is the expensive model in the chain and TELEMAC is cheap, so the surface is *approximately known* before `interFoam` starts. `prerun.ensure_seed(cfg)` returns the result to seed from, in order of preference: the case's own converged `r2d.slf` (`reuse`, the default - hours of fine-grid compute beat anything generated here); else a **dedicated coarse pre-run**, a deepcopy of the case at `pre_run.size_scale` x the cell size, pre-wetted and marched at `pre_run.courant` 0.6, built and run by `pipeline.run(dry_run=True)` into `<model_dir>/pre-run/` with its other products sent to a discarded scratch dir - the same shape as `convergence._level_simulator`, because that pattern is already proven; else nothing, when `pre_run.enabled` is false (`--no-pre-run`, or `PRE_RUN = False` in the case script), and the case builds cold under a flat lid. Measured on isar-2025: a x4 pre-run **builds and runs in 54 s** and yields a 3D mesh within 3% of the one the full production `r2d.slf` seeds (14,192 vs 14,632 cells, 81.9% vs 79.3% water at t=0). It **lives at the top level, not in the OpenFOAM backend**, because `tests/test_capabilities.py::test_openfoam_does_not_import_the_telemac_backend` reads the backend's source and fails on any reference to `axqua.solvers.telemac` - orchestration driving both belongs above both, next to `workflow.py`. A failed pre-run **warns and returns a cold seed** rather than losing the build; an unconverged one warns (`require: warn`) or raises (`error`), judged by reading the pre-run's own `.sortie` through `sortie.read_sortie` + `flux_convergence.relative_imbalance` against `hydrodynamics.flux_tolerance`. `pre_run.dimension: 3d` follows it with the hydrostatic `telemac3d` case and seeds a **vertical velocity profile** - but **only when the mesh can carry one, and it often cannot**. Verified end to end against the real solver, which changed four things. (a) The extension applies to a **reused** 2D result too; hanging it off the coarse-pre-run branch alone made `dimension: 3d` silently do nothing on every case that already had an `r2d.slf`, i.e. the normal case under `reuse: true`. (b) It runs in the folder **holding the seed** (`FILE FOR 2D CONTINUATION` names the result, so a pre-run subfolder is not the main model dir). (c) A **level gate** (`MIN_USEFUL_LEVELS` 3) refuses before launching the solver: TELEMAC-3D has only sigma planes and `infer_vertical_layers` refuses cells more than 4x taller than wide, so a **shallow reach meshed fine in plan has no room for an interior level** - isar-2025 is 0.26 m deep with 0.62 m cells and gets exactly **2 planes on the production mesh**, one layer, a depth-averaged answer at 3D cost. The gate returns in seconds with that reason instead of burning the run. (d) The seed run is made **robust rather than faithful** (`_make_3d_robust`): it cold-starts from `INITIAL CONDITIONS : 'CONSTANT DEPTH'` instead of the 2D continuation, because the continuation lifts a surface carrying many dry/near-dry columns onto the sigma mesh and TELEMAC-3D then diverges **on the very first solve** (`GRACJG ... RELATIVE PRECISION NaN` immediately after `DEPTH IS READ IN THE BINARY FILE`) - measured on the coarse pre-run mesh *and* on the fine production mesh with a converged 2D result and no user-fortran, so it is neither the coarsening nor the seed quality; and it **replaces a Spalart-Allmaras pick with k-epsilon**, since S-A maps to 3D model 5 which diverges in the velocity-diffusion solve on a wetting/drying bed unless a source-term patch is linked (NaN on two meshes with S-A, zero NaN with k-epsilon). Both are the right trade for a *seed*, which needs a plausible profile rather than agreement with the 2D surface - and the cold start is the same choice the vertical-convergence study already makes. A produced result is additionally checked **finite** before adoption (`_is_finite`): a diverged run can march to the end and write a file of NaN, and seeding `U` from that gives an OpenFOAM run that dies with no visible cause. **The NPLAN trap, found only by reading a real result:** TELEMAC-3D writes the plane count in **`IPARAM(7)`** (index 6) and leaves the dims record's fourth slot at **1** - so `read_slf` reading `dims[3]`, the intuitive place, reported every real 3D result as 2D (verified on `inn-kb08/r3dsteady_Q46.slf`: `iparam[6] = 5`, `dims[3] = 1`, NPOIN 1,103,870 = 5 x 220,774). The synthetic test fixture had set *both* fields, which hid it; it now writes the file the way TELEMAC does. Verified end to end on that result: 5 planes, `has_profile` true, and a genuine boundary layer at the deepest node (u 0.039 m/s at the bed to 0.124 m/s at the surface), which `initial_velocity` turns into a seed spanning 0.074-0.390 m/s where a 2D seed gives a uniform 0.251 m/s. **Verified end to end on 12 cores** (isar-2025, `pre_run.n_levels: 6` pinned past the gate deliberately, since the reach itself only supports 2): aXqua built the 3D case, launched `telemac3d`, the result passed the finite check and was adopted with its profile - and the OpenFOAM case built from it seeds `U` with a **mean 0.415 m/s bed-to-surface spread per column, against exactly 0.000 from the 2D seed**, which is the entire point of the mode. The mechanics: `core/selafin.read_slf` now returns `nplan` and, for a 3D file, cuts `x`/`y` back to the `npoin2` plan nodes and reshapes every variable to `(nplan, npoin2)` (a 2D file is untouched); `State2D._from_3d` keeps `u3d`/`v3d`/`z3d`, derives the depth-averaged `u`/`v` by **trapezoidal integration over the actual level elevations** (not the mean over levels - sigma layers are equal only where the depth is, so the plain mean over-weights the thin near-bed layers where the velocity is smallest, a one-sided error), and `sample_profile(xy, z)` interpolates linearly in z, **holding** the end levels rather than extrapolating a jet above the surface. `fields.initial_velocity` uses it when present.

**The seed is an approximation, and the build says where it might be wrong.** Under `openfoam.headroom_mode: auto` (default) the `freeboard` and `wet_margin` are **sized from the seed's own flow** instead of being constants: `State2D.headroom` = velocity head `p95(V)^2/2g` (what the water could convert at a stagnation point or the outside of a bend) + 0.25 x depth (for what a depth-averaged model cannot see at all - secondary currents, local deformation, standing waves), and `lateral_margin` = that rise / `bank_slope` (0.1), with the configured values as **floors, never caps** - so no existing case ever gets *less* room than it had. On isar (p95 0.90 m/s, 0.22 m deep) that derives 0.10 m and both stay at their 0.5 m / 5 m floors; a 3 m/s reach 1 m deep would get 0.71 m. Then, after the run, `report.surface_freedom` answers whether it mattered: two `surfaceFieldValue` monitors (`lidContact`, `wallContact`, `areaIntegrate` of `alpha.water` on the top and `banks` patches, read back by the same `read_monitors` machinery as the discharge) say whether the water ever reached the lid or the lateral wall - i.e. whether the answer was set by a **meshing decision** rather than by the hydraulics, which nothing else in the output reveals: the run converges, the discharge balances, the picture looks like a river. Judged as a **fraction of the patch's own area** (from the `# Area :` header), because a bare area means nothing across reach sizes and because the domain has to end somewhere - at the inflow and outflow the channel necessarily runs into that edge, so `WALL_CONTACT_TOLERANCE` is 2% and the lid's is 0.1%. Verified on a deliberately 8x-coarse isar run: lid 0.001% (dismissed as noise), wall 5.6% (flagged - at dx 2.4 m a 5 m margin is two cells). Under `mode: rigid-lid` it reports "prescribed by the 2D seed, not solved" instead, since there the surface never had freedom to lose.

**Meshing - extrude, don't snap (`openfoam/polymesh.py` + `openfoam/mesh.py`).** aXqua writes `constant/polyMesh` itself (as `selafin.py` writes SERAFIN), because a river bed is a **single-valued height field** z_b(x,y) and can therefore be *followed* rather than snapped to. snappyHexMesh's castellate-and-snap buys nothing on such a surface and costs the sliver/negative-volume repairs that make it painful. The mesh is a **structured (i,j,k) lattice warped onto the bed**: in plan a uniform Cartesian grid of spacing `cell_size`, optionally **rotated onto the reach's principal axis** (`align_to_flow`, PCA of `geodata.channel_centerline`; isar +32.9 deg), with columns outside the footprint absent, hole-filled and reduced to the largest 4-connected block; in the vertical `n_layers` sigma layers per column. Result: **all-hexahedral, conformal by construction** (levels are computed at the *plan vertices*, so neighboring columns of different height share their corner points exactly - no merging, no hanging nodes) and **bed-fitted** (the bottom face of the lowest cell *is* the DEM, not a staircase). `polymesh.assemble` enforces the format contract - internal faces first in **upper-triangular** order, `owner < neighbor`, every face oriented owner→neighbor using the known cell centers - and `polymesh.validate` additionally checks **cell closure** (face area vectors summing to zero) before anything is written. Files are ASCII (written once, read once); the run's own output is `writeFormat binary`. Verified: `checkMesh` reports **Mesh OK, 1,579,074 hexahedra, one region, upper triangular ordering OK** on the isar case at 0.5 m / 14 layers.

**The lid is the fix for the air phase.** The lid is clamped `freeboard` (0.5 m) above the **2D free surface** instead of being a flat plane over the terrain, so most air cells simply never exist (isar: only 9.7% of cells start as water, and a flat lid would be far worse), the `atmosphere` patch stays close to the interface where `inletOutlet`/`totalPressure` behave, and the surface still has room to move. It is gray-**dilated** (`lid_dilation`, default **2** - 1 left a single 70.16 deg severely non-orthogonal face where the lid dipped over a shallow cell) then smoothed (`lid_smoothing`), so it is never *below* the surface it came from and has no dents that pinch the air into slivers. `domain: wetted` further trims the plan footprint to the 2D wetted extent buffered by `wet_margin` (isar: 28,198 m2 of the 66,000 m2 ROI).

**The other two air levers** are in `openfoam/dicts.py`: **`MULESCorr yes`** (semi-implicit MULES) removes the alpha equation's own Courant limit, so `maxCo`/`maxAlphaCo` run at ~0.9 instead of the tutorials' 0.2; and **`system/fvOptions`** carries a **`limitVelocity`** constraint at `air_velocity_cap` (default 5x the reach's p95 water speed, isar 4.5 m/s). Water never reaches the cap; a runaway air jet does, and that is what collapses the time step. Also `momentumPredictor no` (buoyancy dominates) and `nNonOrthogonalCorrectors 2` (a bed-following mesh *is* non-orthogonal where the bed is steep).

**Cutting the air phase out entirely: `openfoam.mode: rigid-lid`.** The levers above *tame* the air; this removes it. The lid is placed **on** the 2D free surface as a `slip` wall, so the domain is water only and `alpha` is identically 1 - `interFoam` degenerates to a single-phase run while `p_rgh` and gravity stay intact (which is what keeps it a river rather than a duct). Consequences, all measured on isar-2025: no interface, so **no spin-up stage** (`stages()` returns one) and no interface Courant limit (`maxAlphaCo` 10, and the run reports `Interface Courant max: 0`); **`MULESCorr no`**, because an implicit correction to a field that is uniformly 1 is pure overhead - it cost **four fifths of the run time** (60 s of river in 88 s with it, 21 s without, same dt, same alpha to 8 significant figures); and the ~90% of cells that were air are simply absent. `openfoam.cell_size_factor` coarsens relative to the 2D channel size (one number, so a test run cannot drift away from the mesh being tested). Together, for 300 s of river on one core: `vof` at 0.5 m is 1,579,074 cells at dt 3.1e-3 s (~97,600 steps); `rigid-lid` at factor 5 is **14,632 cells at dt 3.7e-1 s - 832 steps, 91 s wall-clock** (factor 3: 36,164 cells, 60 s of river in 96 s). **What it gives up is the free surface**: it cannot move, so the mode cannot show a hydraulic jump, a standing wave or superelevation in a bend - it is the way to a trustworthy `vof` run, not a substitute. Two knobs are rigid-lid-only. `min_water_depth` (0.20 m) drops shallower columns, and **cannot be raised freely** - at 0.25 m the trim ate isar's inlet patches, whose inflow sections are themselves shallower than that. The layer count is then **fitted to it** (`build_mesh`): under a rigid lid `n_layers` spans the water alone (0.2-1.0 m), not water plus freeboard (0.7-1.8 m), so the count carried over from a two-phase case gives cells 3-4x thinner - past the bed roughness they are meaningless, and thin enough that the bed's variation within one plan cell folds them, which `checkMesh` rejects as incorrectly-oriented face pyramids. 14 layers over 0.20 m is reduced to 4 and the build says so. `auto_bed_layer` defaults **off** here for the same reason (48 bad face pyramids and 83.6 deg non-orthogonality with it on, 0 and 74.7 deg with it off). The cost estimate has its own rigid-lid model: carrying the two-phase one across (thinnest layer at the full water speed) predicted 0.019 s against a measured 0.369 s, because only the *vertical* component crosses a thin layer - so `estimate_time_step` sums `u/dx` and `u.S/dz` with `S` the mesh's own median bed slope (`case.terrain_slope`, isar ~8%), which lands within 25%.

**Two-stage run.** `system/stage1-spinup/` and `system/stage2-run/`; `dicts.activate` copies one into `system/`. The first moments after a hotstart are the least like the converged flow - the 2D state is depth-averaged, so at t=0 there is no vertical structure at all - so **stage 1** runs briefly (`spinup_time`) at `spinup_courant` 0.3 with **half** the interface compression (`cAlpha 0.5` in `fvSolution`, against 1 in stage 2; ESI keeps the coefficient there and the scheme is plain `Gauss vanLeer` with a separate `div(phirb,alpha)`, where Foundation folded it into an `interfaceCompression` scheme) and upwinded momentum; **stage 2** restarts (`startFrom latestTime`) at `max_courant` 0.9 with full compression and `limitedLinearV 1`. `fvSchemes` also needs `wallDist { method meshWave; }` for kOmegaSST.

**Boundary conditions (OF9-verified against that install's source + the `waterChannel`/`weirOverflow` tutorials).** Inlet/outlet patches come from the **same `boundaries.liquid_boundaries` layer that drives the `.cli`** (`boundary.liquid_line_details`), one patch per line, so 2D and 3D take flow in and out at identical places and each line's `Target flow` gives its own Q (isar: `inlet-1` 1.6, `inlet-2` 0.8 m3/s). Inlet: `flowRateInletVelocity` with the **mass flow** of the water and the density field, + `variableHeightFlowRate` alpha - the inlet **stage is an outcome, not an input** (prescribing Q *and* a depth over-determines it). It was `variableHeightFlowRateInletVelocity` until 2026-10-13, which lets in `Q <alpha^2>/<alpha>` of water (see the section on the Isar below). Outlet: the case's own `outflow_condition` becomes `prghPressure` with a hydrostatic `p` profile below the target level, **continued above it as air at rest**, plus an `inletOutlet` alpha profile 1 below / 0 above - the direct analogue of TELEMAC's `PRESCRIBED ELEVATIONS` (isar: 815.347 m from the section rating at Q=2.4); `free` still selects the weirOverflow-style outfall. A two-phase case also gets `constant/hRef` at the lowest outlet stage. Above that stage plus `openfoam.outlet_air_margin` (0.25 m) the outlet faces are walls, joined to `banks` (lww-133, `557d898`: open over its whole height, the outlet of munich-vsf let an air loop of 7 to 10 m3/s through the domain and reversed after about 40 s). The mesher takes the stage from `outlet_stage`, then from the level the build resolved from `outflow_condition` (`build_mesh(tailwater=)`; under `stage_discharge` there is no `prescribed_elevation`, so without it the Isar outlet was not walled at all), then from `prescribed_elevation`; its check for an outlet squeezed into a slot compares the open height with the height of the outlet's cells, not with the plan spacing (on the 2 m Isar lattice that warned for every build). On the Isar the wall changes nothing that is read off a result (2026-10-15, `<scratchpad>/hyd/dbg/seal-test.sh`: the 2 m model restarted from the view from above of its own 3002 s result and run 600 s, once with 52 of the 72 outlet faces walled and once open, `<scratchpad>/hyd/sealcmp.py`): levels at both inflows the same to the millimeter and at the outflow 2 mm higher, depth -0.03 cm and velocity +0.0006 m/s on average (rms 0.25 cm and 0.018 m/s, against 0.17 cm and 0.018 m/s between 500 s and 600 s of the walled run). The inlets let in air at the speed of the water over the whole height of the patch (13 m3/s at 2 m, 7.1 m3/s at 1 m; `<scratchpad>/hyd/patchflux.py`); open, the outlet let out 13.6 m3/s of air, walled 3.9, and the rest left through the top (net 9.1 instead of -0.6 of about 1,270 m3/s that leave and enter there), which carried 0.0011 instead of 0.0007 m3/s of water out over the last 100 s, 0.05 against 0.03 % of the discharge. Bed/banks: `noSlip` + **`nutkRoughWallFunction` with per-face `Ks`** from the same `geodata.roughness_zones` that drives `FRIC_ID`/`.tbl`.

**Initial fields (`openfoam/fields.py`, `openfoam/hotstart.py`).** `alpha.water` is the **submerged fraction of each cell** below the 2D free surface (a one-cell-sharp interface, far better than `setFields` boxes), **in the columns that are wet in the 2D result and nowhere else**; `U` is the 2D depth-averaged velocity in water, scaled by alpha, zero in air, deliberately **uniform over the depth** (the vertical structure is what the 3D run is *for*); `p_rgh` uniform 0; k/omega uniform from the reach's own depth and velocity. `State2D` samples the 2D result **nearest-node on a KD-tree, not P1 on the element table**: a SELAFIN merged from a parallel run is not a clean triangulation (isar: 4,393 coincident nodes and 66,759 zero-area triangles of 460,314, which makes matplotlib's `TrapezoidMapTriFinder` reject the mesh outright), and nearest-node costs nothing in accuracy because the 2D mesh is *finer* than the 3D lattice it seeds - `resolution_check` warns if that ever reverses.

**The honest limitation (`openfoam/quality.py`).** `nutkRoughWallFunction` needs the first cell **center** above the roughness crests (`y1 > ks`, i.e. a bed layer ~`2 ks`), so `auto_bed_layer` pins the bed layer to **2x the wetted-median ks** (isar 0.10 m; the *wetted* median, because the dry floodplain's vegetation ks 0.5 m has no bearing on a wall function under water). Even so, on isar **41% of wetted bed faces** still have `y1 < ks` - the reach's roughness (ks 0.085-0.5 m) is a large fraction of its depth (median 0.22 m). OpenFOAM does **not** fail there: it clamps y+ to `e/E` and carries on, so the run completes and the near-bed velocity is simply not physical. Refining towards the bed makes it worse, not better. The report states the share per build; read such a result as bulk flow, not as a resolved bed boundary layer. `quality.py` also reproduces `checkMesh`'s **own** definitions exactly - `face_geometry` (triangle-fan centroids: a terrain-following quad is non-planar, so its center is not the corner average), `cell_geometry` (pyramid decomposition), skewness normalized by the **face half-width** floored at `0.2|d|` (not by `|d|`, which understates it ~7x), aspect ratio as `max(component ratio, hydraulic ratio)` (the component form dominates on flat cells: 16.7 where the hydraulic form alone reads 3.1), and the mean non-orthogonality as `acos(mean(cos))`. Verified against `checkMesh` on the isar mesh to 3 significant figures (60.11 deg / 7.84 deg, skew 4.025, aspect 16.66, identical volumes). `MeshReport.usable` (structurally sound: no zero/negative volumes) is deliberately **weaker than `.ok`** (passes every checkMesh check): a mesh cut from a real DEM routinely carries a few marginal faces at survey steps and seams - isar has exactly one skew face in 4.9 million, which no lid smoothing moves because it comes from the bathymetry - and refusing to run on that would be refusing to model the terrain. `runtime.check_mesh` blocks only on its `_FATAL_CHECKS`.

**Running and reporting.** `OpenFoamRuntime` extends the new shared `env.ShellRuntime` (extracted from `TelemacRuntime`, behavior unchanged) and sources `openfoam.bashrc` per command: `checkMesh`, `decomposePar` (**scotch**, since the wetted corridor is sinuous and a geometric split would hand some ranks empty space), `mpirun -np N interFoam -parallel`, `reconstructPar`. Output is **streamed** with an `OpenFoamProgress` bar sharing the new `progress.ProgressBar` with the TELEMAC renderer; it shows **`Co` and `dt`**, which are the diagnostic - a healthy run holds `dt` near the Courant target, a misbehaving air phase shows `dt` falling by orders of magnitude while the clock barely advances. `openfoam/report.py` reads the `surfaceFieldValue` monitors written into `controlDict` (`sum(phi)` **weighted by `alpha.water`**, so it is the water discharge, not water+air) into `discharge-convergence.csv`/`.png` and judges the relative inlet/outlet imbalance against the **same `hydrodynamics.flux_tolerance`** the 2D run is judged by, so 2D and 3D are held to one standard. CLI: `axqua openfoam <config> [--check] [--cell-size <m>] [--layers <n>]` (`--check` reports the cell count without building). Tests: `tests/test_openfoam.py` (no OpenFOAM, no solver).

## A whole river reach in two phases: what the Isar example found (2026-10-13/14)

The user's order of 2026-10-13: "only run a hydrodynamic simulation of the isar case for now [...] the challenge of doing an openfoam simulation of that river stretch remains challenging enough if it is hydrodynamic only". The working case is `cases/isar-openfoam/` (not tracked, excluded locally in `.git/info/exclude`): case files that read the inputs of `cases/example-isar/` and their own job root in `_run/`. The first run of the example at 1 m cells (393,246 cells, 14 layers, 16 cores) needed 1.45 s per time step of 0.0013 s, 16 hours for 120 s of river. Four defects were behind it, none particular to this reach (commits `cf10190`, `4c25def`, `22c3981`).

**How the limiting cells were found, worth repeating before anyone changes numerics.** Write one step in ASCII, compute the Courant number of every cell from the face fluxes (`0.5 sum|phi| / V dt`), and list the largest with their phase, layer, 2D depth of the column and distance to each patch. The step is set by the worst 0.01 % of the cells. Three properties of the air (damping with `velocityDampingConstraint`, air ten times heavier, air a thousand times more viscous) changed nothing, because the cause was a boundary condition.

1. **The air on the outflow was not at rest** (`fields.outlet_pressure`, `reference_level`). `totalPressure 0` on the open top is `p_rgh = 0`, air at rest at any elevation, because the solver carries `p_rgh = p + rho g (z - hRef)`. The outflow prescribed `p = 0` above the stage, which leaves `rho_air g (z - hRef)`: 8 kPa at 816 m a.s.l. with `hRef` 0. All 84 cells with the largest Courant numbers were within 3 m of the outflow. Now air at rest above the stage, the water hanging on it, and `constant/hRef` at the lowest stage (removed again by a rigid-lid or leg C build in the same folder). Step 0.0013 s to 0.008 s. On munich-vsf the same term is 7 to 25 Pa, probably the "air loop" of 2026-10-04 (issue #4); not run there.
2. **The seed put water on dry ground** (`fields.initial_alpha`). The free surface of a dry 2D node is its own bed, the column bed is the terrain model: 583 m3 of water, a sixth of the reach, on 55 % of the dry columns. A column whose 2D depth is not above `wet_depth` starts dry. Fastest water after 1 s: 3.9 to 1.5 m/s.
3. **The inlets delivered 90 and 93 %.** `variableHeightFlowRateInletVelocity` lets in `Q <alpha^2>/<alpha>` of water. `flowRateInletVelocity` with `massFlowRate` and `rho rho` (one velocity, mass over the mass on the patch) delivers 99.5 to 99.8 %; the rest is the air's share of the mass on the patch. Level still floating (`variableHeightFlowRate` alpha).
4. **The first stage handed nothing to the second.** The solver saves at whole write intervals counted from the start of its run and not at its end; spin-up 2 s with results every 50 s ended without a result and stage 2 restarted from 0. `dicts.stage_write_interval` makes the end of each stage a write time (the production stage counts from `spinup_time`).

**What limits the step after that: air drafts at steep banks.** Air falls at 1.5 to 2 m/s through the dry columns beside the waterline and runs along the ground, through layers of 3 to 5 cm. The cause is the cells of a column next to a steep bank: they lean, and several of them hold a little water. The discrete hydrostatic balance of a VOF field on leaning sigma cells has such a state: for one 1.8 m cut bank of the example it gives a water fraction of 0.22 in each low cell of the bank column, 0.25 was observed. That mixture is heavier than air, slides, and drags the air. Not removed. `openfoam.max_flow_courant: 3` lets those cells cross more than one cell per step while the surface keeps `max_courant` 0.9: step 0.026 to 0.049 s, surface Courant number then 0.91, water cells at most 0.13. `pressure_correctors: 2`, `non_orthogonal_correctors: 1` gave the same volume, depths, velocities and discharges to three digits after 40 s on the 2 m lattice at 0.6 of the cost.

**Measured and not adopted (2 m lattice, 40 s):** Courant 2 at the surface and 6 for the flow (0.7 of the steps, lid leak up to 0.012 m3/s); `wet_margin` 2 m (a third fewer cells, ten times more wall contact, 1.2 % of the wall); `freeboard` 0.3 m with 6 layers (lid leak 15 times larger, 0.5 % of the discharge); `interIsoFoam` (no larger step, 1.5 times the cost per step; on the 2 m lattice its step was a third to a quarter of that of MULES, and its surface no sharper than with `interface_compression` 2: at 20 s 46 against 40 % of the water in full cells, 0.12 m thick in both); explicit MULES with three sub-cycles (`MULESCorr no`, `nAlphaSubCycles 3`: the surface exactly as smeared as with semi-implicit MULES); `layer_expansion` 3 (21 % of the water in full cells against 19 %); layers that follow the surface of the seed (4 or 5 of 8 layers from the bed to the 2D surface, the others growing towards the lid; built on 2026-10-14 and removed again: 26 and 29 % in full cells, but 1.96 and 7.2 m3/s of water left through the top, 0.8 and 3 times the discharge, carried by air that left the top at 2.1 m/s).

**What a result is worth: the surface is smeared over the depth of the water.** Measured as the share of the water volume in full cells (alpha above 0.99) and as the height between the levels where alpha falls below 0.95 and below 0.05 (`<scratchpad>/hyd/sharp.py`). At 1 m and 14 layers: 84 % in full cells in the seed, 54 % at 2 s, 43 % at 52 s, 36 to 37 % from 500 s to 1500 s, the surface over 4 cells and 0.23 m (p90 0.44 m) in columns of median depth 0.26 m. ## Fine sediment over a bed that stays in place (`sediment.py`)

**What it is, and why the bed is fixed.** `Capability.MORPHODYNAMICS` of this backend is not a moving bed. It is Olsen's `sediDriftFoam2` (simpleFoam plus the concentration of one grain size, from the stack the OpenFOAM installation builds) run with `initialIterations` beyond the end of the run, so that neither the bed nor the water surface is ever moved. The user's direction of 2026-10-12, when asked which reach to develop it on: "it should be the isar case and there the fine sediment concentration in the riverbed because there was no elevation change for sure (any elevation change is a DGPS artifact -- only fine sediment fraction change is real)". The solver's own moving mesh is unusable on a natural reach anyway, for three rules in `sediDriftFoam2.C`: a bed point is lowered until the water is ten bottom cells deep (`minDepthMultiplier`), the points of a vertical are spread evenly after every bed change, and `bedCenter.x() < 0.5` and the last meter before the largest x are treated as the ends of a flume. The case is the block `fine_sediment` (top level, classified SHARED like `gain_lose`: a fact about the reach that one backend computes today), built into `<sim_dir>/openfoam-sediment/` by the job kinds `openfoam-sediment-build` and `openfoam-sediment`.

**The mesh is the rigid-lid mesh, and the solver's requirements are checked on it, because the solver checks none.** `sediment_config` forces `mode: rigid-lid` on a copy of the case whatever its free-surface case uses. `check_columns` re-implements what the solver assumes: patches `bedWall` / `freeSurface` with face k of both in one column, points rising along each vertical, and the neighbor search by vertex numbers (east: my vertices 3,2 are its 0,1; north: my 1,2 are its 0,3), which has to find every pair of bed faces that share an edge. The mesher's vertex order passes as it is (640 of 640 pairs on the first mesh tested); which way "east" points is of no consequence.

**The finding that cost the first run: the height of the first cell center above the bed face, in the solver's definition `mesh.C().z() - patch.Cf().z()`, can be zero or negative.** It enters `log(30 h / ks)`, so the run ends with a floating point exception inside libm with no message (found by compiling a copy of the solver with checks in the scratch folder; the installed stack was not touched). Two separate causes. (1) *Layers of varying thickness on a sloping bed*: with evenly spread sigma layers the bed cell is a wedge whose center lies towards its thick end, which is the low end. 54 of 2721 bed faces of the Isar example. The cure is a bottom layer of **one thickness everywhere** (`pin_bottom_layer`, through the mesher's own `sigma_levels(bed_layer=)`; it changes levels and nothing else). (2) *A steep, twisted bed face*: the cell is the bed face moved up, so its center lies over the middle of the face in plan, while the center of the face (area-weighted triangle fan) lies towards its steep part. This gives `h = layer/2 + offset` with an **offset of the face that does not depend on the layer** (verified to 3e-10; between -0.026 and +0.018 m on the Isar example at 1.5 m cells). So where the case leaves `bottom_layer` open, the build makes it as thick as the worst face needs to clear the logarithm by the factor e (`required_bottom_layer`; 0.062 instead of 0.050 m there), capped at half the shallowest column, and a named thickness that fails is refused with the one that would do. aXqua's `quality.face_geometry` / `cell_geometry` reproduce the solver's number to six digits (-0.073897 against -0.073896803), which is what makes the check exact rather than approximate. **The anisotropic TELEMAC mesh is not reproducible, so neither is this lattice**: the first chain of jobs on a fresh build of the same example had one face of 2720 below the bed where the mesh of the day before had none.

**One roughness for the bed.** The free-surface case gives each bed face the `Ks` of its roughness zone. Here that keeps the residuals of p, Uz and k at 5e-3 from the fiftieth iteration on (the zones of the Isar reach 0.5 m, ten times the bottom layer); with one value, the same as in the shear stress on the grains, the run converges below 1e-5 in about 400 iterations. A `limitVelocity` constraint has the same effect on the residual of U (a few cells are clipped at every iteration) and is not written: a steady run has no time step to protect.

**`steadyState` for the concentration.** Olsen's example marches the concentration with `Euler` and `deltaT 0.02`, which a moving bed needs; a front would take 50,000 iterations through a 480 m reach. With `ddtSchemes default steadyState` the equation is solved as it stands at every iteration (it is not relaxed: the solver calls `solve` on it directly). `deltaT 1`, so time is the iteration count and the progress of a job counts iterations.

**How the solver books settling and pick-up, which the budget has to follow.** The fall velocity field `Umod` has no flux through the bed face (fixed value zero), so the settling flux that arrives in the bed cell has nowhere to go, and the `bounded` convection scheme turns exactly that divergence into a sink: settling = fall velocity x concentration of the bed cell x **plan area** of the column. `bounded` is therefore part of the model, not a matter of taste (and the implicit term the solver adds in the surface cells cancels the same correction there). Pick-up is the volume source `S_explicit = w / (2 h) x c_a` in the bed cell, so the mass that really enters is `S_explicit x V`, which is `w c_a` per plan area only where `2 h` is the cell height. `evaluate` uses the source as the solver adds it, and the budget (in = out + settling - pick-up) closes to 0.01 to 0.35 % on the example. `S_explicit` is not written by the solver, so `bed_exchange` recomputes it from the written velocity (log law, the fitted Shields curve, Dey's factor, van Rijn's T and reference concentration with the limit 0.1); compared with a copy of the solver that writes the field: median difference 3e-6 for both formulas. `sedimentFormula` other than 0 and 1 leaves the pick-up at zero in the source, which is what `pick_up: off` writes (2).

**`pick_up: suspended | bedload` mean a bed that consists of the fine sediment.** On the Isar example with 0.2 mm sand the flow then picks up 8 t/s against 0.05 kg/s that enter. For fines over a gravel bed the choice is `off` (the bed as a sink), and the supply-limited case is not modeled: with the unmodified solver it would take two runs and a superposition (the concentration equation is linear for a given flow). Not built; asked the user.

**What a result is worth on the Isar.** The lid test of the mesher refuses the example at every cell size tried (the surface of the 2D result steps 120 to 182 % of the local depth within two cells, 99th percentile, from 0.36 to 1.53 m cells), so the fine sediment case needs `openfoam.allow_stepped_lid: true` there, and the result carries the verdict with the fastest cell (5.5 m/s where 95 % of the 2D result stay below 0.8). With `min_water_depth` 0.2 m against a median depth of 0.23 m, about half of the wetted area is not in the model at all. Numbers of 2026-10-13 on that example (10,880 cells, 4 layers, inflow 20 mg/l, pick-up off): 30 um silt converges in 446 iterations and 20 s, 87 % of what enters settles in the reach; 60 um, 100 %; 0.2 mm sand settles within the first meters. Those are properties of the model, not results about the river: the concentration is made up.

**Jobs.** The two kinds are the `build` and `run` verbs of the backend with `Capability.MORPHODYNAMICS`. Both, and `openfoam-build`, wait in the queue of the case (`jobs.workspace.QUEUED_WITH_THE_CASE`), because the builds read the 2D result; `openfoam-run` stays out as before. After a run the evaluation is not guarded like a report: it is the result, and a job without it fails. Tests: `tests/test_sediment.py` (no OpenFOAM; meshes built with the mesher's own `extrude`, a result of three hand-written field files, a stub in place of the runtime).


## The outlet with a stage-discharge relation, and the mesh study (2026-10-17)

**`openfoam.outflow_boundary: rating-curve`** (default `level`) puts BAW's `waterLevel_alpha_prgh` (Thorenz 2024, `HydBCsForOF`, library `dicts.BAW_LIBRARY`, which the OpenFOAM installation of aXqua builds into the stack's user lib dir) on `alpha.water` and `p_rgh` of every outlet patch, `mode ratingCurveTable` with `data table ((Q h) ...)`; U stays `pressureInletOutletVelocity`, k/omega `inletOutlet`. The table is `case.rating_table`: `boundaries.stage_discharge` when it has >= 2 discharges, else derived over `RATING_SHARES` (0.1-3 x Q) by `boundaries.rating_method` and written as `rating-curve-openfoam.csv` in the case (BAW does not extrapolate). The run starts, and the mesher walls the outlet, at the curve's level at the case Q. `control_dict` adds `libs (...)` whenever `dicts.uses_rating_outlet(cfg)`, so `activate()` regenerating the controlDict keeps it. Refused with `mode: rigid-lid` and with `outlet_stage`. Several outlet patches each use their own Q with the same table (noted in the build). Verified 2026-10-17 on a scratch copy of the Isar example (2.7 m lattice, 79,282 cells, the stack at `~/.local/openfoam-sediment-v2406`): interFoam loaded the BC, ran spin-up and production for 1 s, outlet 1.41 m3/s against 1.59 in (still filling). The installer's `sediDriftFoam2Rating` (Olsen with a moving surface) is installed and deliberately not set up: the fine sediment case keeps bed and surface fixed.

**Mesh convergence of the OpenFOAM model** is `solvers/openfoam/convergence.py` (job kind `openfoam-mesh-convergence`): the plan spacing on the r=1.3 ladder around `plan_spacing(cfg)`, layers unchanged, every level built (`openfoam_dir` per level below `<postprocessing>/openfoam-mesh-convergence/`) from the same seed the executor prepares (`_pre_step`), run, and compared through `planview.write` (`depth-averaged.slf`) with `axqua.convergence.run_mesh_convergence(result_name=..., check_validity=False)` - the TELEMAC closure checks of `mesh_validity` do not apply. **Run for real on 2026-10-17** on a scratch copy of the Isar example (`end_time` 1 s, 4 MPI ranks, 7 probes from the ground truth): levels 3.51 / 2.70 / 2.08 / 1.60 m plus one automatic extension at 1.23 m (46,886 to 262,318 cells, 60 to 427 s each), the next extension at 0.95 m refused by `checkMesh` (one incorrectly oriented face pyramid) and handled as the practical refinement limit; verdict not converged on the relative change, as expected after 1 s of a filling reach - a test of the chain, not a result. That run found the decomposition bug: `backend.run(n_processors=4)` on a case built for 1 decomposed into one domain and mpirun refused ("Number of processor directories = 1 is not equal to the number of ranks = 4"); The decomposition for the ranks of a run lives in `OpenFoamRuntime`, decided per stage from one read of the case (`runtime.Layout`: number of domains, also from the `processors<N>` folder of a collated decomposition; the latest time in the processor folders and at the top level; whether the active controlDict continues from `latestTime`). **`decomposePar` carries over exactly one top-level time, the one the active controlDict starts from** (measured with v2406 on 2026-10-18), so whether a split loses anything depends on the stage: `run_stage` activates the stage first, then `_prepare` makes the case ready for it. A stage that starts afresh moves what earlier runs left into `previous-run/` (`layout.set_aside_runs`: the time folders after 0, the processor folders and `layout.RUN_PRODUCTS`, i.e. `postProcessing` whose monitors `report.read_monitors` would otherwise join to the new run's, `VTK`, `depth-averaged.slf` and the report files; a later time is where the next stage would continue from, also an old reconstructed result at the top level) and, on several ranks, splits the case anew from the start time. Moved, not deleted (review of 2026-10-18): the processor folders of a run that was not reconstructed may hold the only copy of hours of computing, and the new run has produced nothing yet; only the run before is kept, the next one replaces the folder, and `calibration._clean_template` deletes it. A stage that continues runs on results that only the processor folders hold, refuses (`SolverError`) where those were split for other ranks or the stage runs on one processor, and splits again from the latest time where the top level holds it (after `reconstructPar`). `build_case` sets them aside as well, before it writes the new case (review of 2026-10-18: set aside afterwards, a build that failed while writing left the old times and processor folders beside the new mesh; a second attempt finds nothing to move and keeps `previous-run/`), because the results of an earlier build cannot be continued on a new mesh, its processor folders hold the old mesh itself, on which a parallel stage would go on, and its depth-averaged result would be listed as one of the new case. Every question of which folders are times, which are processor folders and how the case lies on disk is answered by `solvers/openfoam/layout.py` (standard library only; `runtime` re-exports `Layout` and `processor_count`; planview, sediment, spec and the backend use `time_folders`). `describe_results` describes a result that only the processor folders hold as `Dataset.decomposed`, with the times of the first domain, and `postproc.visit._open` then sets VisIt's OpenFOAM option `Case Type` to 0 (Decomposed): VisIt 3.5.0 opens a case reconstructed by default and showed t = 0 alone for such a case, measured 2026-10-18. Nothing splits before the stages any more (the backend, the calibration pre-spin and the tracked `openfoam_run.py` scripts leave it to `run_stage`, so a run decomposes once); the public `decompose` stays for munich-vsf's script (not edited; it decomposes without its ranks and is split again by the first stage) and never splits over results only the processor folders hold (it returns None), which is what keeps that script's stage-by-stage resume (spin-up without reconstructing, production stage in a second call) working: checked with v2406 on the scratch Isar copy, the production stage continued from the spin-up at 0.1 s. All of this happens without touching the case's own file: `dicts.decomposition_for` returns None where `system/decomposeParDict` names that count (it is used as it is, with a method that may be the user's) and otherwise writes aXqua's scotch file `system/decomposeParDict-<n>`, which `decomposePar` and the parallel solver both get with `-decomposeParDict` (a parallel interFoam reads the dictionary too and refuses one that names more domains than it has ranks). Checked with OpenFOAM v2406 on a scratch copy of the Isar example (case file for 1 domain, run on 3 ranks through the backend and through the flow of the scripts, both stages, reconstructed, case file unchanged); `calibration._clean_template` strips the `decomposeParDict-<n>` files. The size scale of a level is `dx / plan_spacing(cfg)`, recomputed after the study for levels taken over from `level.json`, and written back into that file.
