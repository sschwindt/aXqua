# Installing the simulation programs

Moved from the root `CLAUDE.md`; loaded when working under `src/axqua/install/`.

## Installing the simulation programs (`axqua/install/`, `axqua install`)

**aXqua carries no installer. It runs the user's published scripts** (`Ecohydraulics/numerical-software-installers`, `recipes.REPOSITORY`) **at a pinned commit** (`recipes.PINNED`, the version a release was tested with; `--ref main` or `$AXQUA_INSTALLERS=<local clone>` override it). The clone on this machine is `/srv/private/numerical-software-installers`; it is the user's repository and is read and run, never edited. When the scripts change, re-run the real installations below and move `PINNED`.

**Except the OpenFOAM installer, which aXqua ships** (`src/axqua/install/vendor/OpenFOAM-installer/`, `recipes.BUNDLED`, package data `install/vendor/**/*`), on the user's order of 2026-10-15 after two users reported the installation stopping at Olsen's sources with HTTP 502 (`www.pvv.ntnu.no/~nilsol`, his only publication place, unversioned; down on Windows/WSL and Ubuntu alike, still 502 that day). The copy is commit `12fcb7e` plus what `VENDORED.md` lists: Olsen's 20 source files in `olsen-sources/` (byte-identical to the SHA-256 pins of `olsen_sources.json`, copied after the check, the download only a fallback whose failure is an `InstallError` instead of a traceback), the Python-3.12-only f-string split, `/usr/local/bin` last in `clean_environment`, and a test of the installer that broke on Python 3.12. **Licenses:** the installer is MIT (into BSD-3 aXqua: fine with its notice); Olsen's sources and `cpp/olsenRatingCurve.H` are GPL-3.0-or-later, shipped as an aggregate (GPL-3 section 5): aXqua neither imports nor links them, it runs the compiled solvers as separate programs, so the GPL does not reach aXqua (contrast pythomac, whose GPL Python would have been imported). Both are stated in `NOTICE` and `olsen-sources/README.md`. The `openfoam` and `postprocessors` targets use the copy unless `--installers`, `$AXQUA_INSTALLERS` or `--ref` names other scripts (`_other_installers`); TELEMAC still comes from the pinned repository. `tests/test_install.py` runs the copy's own unittest suite (92 tests, 0.5 s) and compiles it with any Python 3.10/3.11 found. Verified with a real `axqua install start openfoam --reuse-openfoam` on the main workstation while the site answered 502: all three solvers and the BAW library built, smoke test passed, 4 min. The same changes are **not** in the user's installer repository (the auto-mode classifier refused edits there; the user had also said to wait with commits there), so a Windows user running its `install.ps1` directly still meets the 502 until the user applies them; the patch is the diff of the copy against `12fcb7e`. An installation folder an older installer started is refused by the installer's identity hash, so a failed installation is repeated in a new folder. **Since 2026-10-17 the plan says so before anything runs** (`axqua.install.installer_changed`, computed with the installer's own `identity` through `recipes.IDENTITY_DRIVER`), and `--reinstall replace` (the wizard's *Remove the existing installation and install it again in its folder*) removes exactly what `recipes._removal` names (a folder carrying the installer's marker; for TELEMAC only `telemac-mascaret`; for VisIt the `apps/visit*` folders) before installing anew; `continue` is the installers' own resume. Change 6 of `VENDORED.md`: a smoke run that passed is not repeated and one that failed is kept as `runs/baw-smoke.failed-<n>` (the user's Linux Mint 22.3 laptop stopped at "Smoke-run directory already exists"). Every change to the vendored installer changes its identity, so existing OpenFOAM folders need `replace` or a new folder after an update.

Three targets: `telemac` (`debian12/telemac_debian12_installer.sh` or `ubuntu24-mint22/telemac_ubuntu24_installer.sh`; there is none for Ubuntu 22.04), `openfoam` (`OpenFOAM-installer/install.py`: OpenCFD v2406 or `--reuse-openfoam`, Olsen's sediDriftFoam / sediDriftFoam2 / sediDriftFoam2Rating, BAW's rating boundary, distro ParaView, pinned VisIt 3.5.0) and `postprocessors` (ParaView + VisIt for a TELEMAC-only computer). The last has no script: `recipes.VISIT_DRIVER` is ten lines run with `python -I -c` that import the installer's own `install_visit`, so the pinned URL and checksums stay in one place. `-I` matters: the installer's modules must not see anything of aXqua on their import path.

**What aXqua adds is what a click needs.** (1) *No password.* Both scripts call `sudo apt-get`, which needs a terminal. aXqua reads the package list **out of the script** (`_script_packages` parses the `apt_install_deps_*` shell functions, `_python_list` the `BUILD_PACKAGES`/`GUI_PACKAGES` literals - nothing is duplicated, so nothing drifts), asks `dpkg-query` and then `apt-get --simulate` (no privileges; it resolves names that another package provides and names the sources do not offer), and hands over the one command. The scripts then always run in their no-sudo mode (`--skip-apt`; never `--install-system-packages`). `install_packages` can run that command through `pkexec`, so the desktop's dialog takes the password; **this path is unit-tested with the command only and was never run against a real polkit**. (2) *A plan before anything runs* (`recipes.plan` -> steps as argv, outputs, findings; never raises for a finding; an error finding empties the steps). (3) *A detached runner* (`runner.py`: a folder under `data_dir()/installs/<time>-<target>/` with `plan.json`, `status.json`, `install.log` (each step between `=== n/N: <name> (started <time>) ===` and `--- n/N: <name>: done|exit code N|cancelled|not started after <s> s ---`, `runner.FOOTER`; `_last_words` skips both, and only the exact footer, since build output may start with `--- `); `start` spawns `python -m axqua install run <folder>` in a new session; `read` reconciles a vanished process to `failed`, so nothing stays "running" after a reboot). Each step runs in a **session of its own**, so `cancel` reaches the whole build tree and nothing else, detached or in a terminal. (4) *Verification and the profile*: the TELEMAC script exits 0 even when its own build check failed (it only warns), so the runner checks `expects` globs (`builds/*/bin/telemac2d`) itself, then `bind` writes the outputs into the active profile (creating it with `profiles.detect()` like *Create profile* does; a profile that cannot be read is left alone and reported) and probes the environment once. A plan names the outputs that are additions to its target (`Plan.optional_outputs`: ParaView and VisIt for OpenFOAM, ParaView alone for the postprocessors, where VisIt is what is installed); a missing addition is a warning, so a VisIt that did not arrive does not cost the OpenFOAM build of hours before it. `bind` reads, changes and writes the profile under the job lock on a file beside it (`runner._writing_profile`), because two installations may end in the same moment and each adds an entry of its own. It also enters the folder of what was installed (`installations`, told from the file by `profile.installation_of`).

**For me only, or for all users** (`Options.scope`: `user` | `system`; CLI `--for-all-users`; the first setting of each plugin wizard, which moves the default folder along until the user types one; the user's order of 2026-10-15). `user` is the old behavior: a folder in the home folder, no administrator at all (missing system packages aside). `system` defaults to `/opt/telemac`, `/opt/openfoam-sediment-v2406`, `/opt/axqua-postprocessors` and adds two `Step(admin=True)` around the unchanged build, because the installers refuse to run as root: before, `install -d -m 0755 -o <user> -g <group>` creates the folder for the user (or, for a folder carrying `SYSTEM_MARKER` from an earlier system install, `chown -R <user>` takes it back); after, `chown -R root:root`, `chmod -R u+rwX,go+rX,go-w` and the marker. `runner.elevated` runs them through `sudo` when the run has a terminal on both ends (`--foreground`; the step then stays in the session and inherits stdin so sudo can ask) and through `pkexec` on a desktop; neither gives the `needs_admin` error before anything is built. Folders like `/opt` itself, `/usr` or the home folder are refused (`folder_for_all_users`), a foreign unwritable one too. The OpenFOAM installer had to accept an existing **empty** prefix for this (`claim_prefix`, change 5 of `VENDORED.md`). Other users find the result by discovery (`machine.DISCOVERY` gained `/opt/telemac*/telemac-mascaret/...`, `/opt/openfoam-sediment*/shell-rc.sh` before `/opt/openfoam*/etc/bashrc`, `/opt/*/apps/visit*/bin/visit`), not by a profile. **Never run with a real password:** the admin steps were tested with a stand-in for the elevation tool only (no sudo password on the main workstation), like the pkexec path of the packages.

**VisIt is a choice, and the recommended one** (`Options.visit`, on by default; `--no-visit`; the user, 2026-10-11: "users should have the choice to not install Visit but we want to recommend the visit installation"). The installer has one switch for both programs (`--skip-visualization`), so without VisIt aXqua passes that switch and enters the ParaView of the operating system itself; of the GUI packages only `paraview` is then asked for. For the `postprocessors` target, leaving VisIt out leaves nothing to download: **a plan without a step can be ready** (`Plan.ready` is "steps or outputs, and no error"), its installation consists of entering ParaView in the profile, and without the package it is the error `axqua.install.packages_required`. A plan that leaves VisIt out says once why aXqua recommends it (`recipes.VISIT_RECOMMENDED`: its predefined 3D figures are rendered with VisIt).

**Of TELEMAC's example cases, only what a run reads is downloaded by default** (`Options.telemac_examples`: `inputs` | `all` | `none`). **This was built on a misreading and the user never asked for it**: their "it should download the example cases, only what is absolutely necessary" of 2026-10-10 meant the example cases of aXqua (Isar, Inn), not TELEMAC's. It stays because the alternatives are worse (the installer's own behavior is the full download of an hour, and without the input files TELEMAC's examples do not run), and it is one setting if the user wants another default. The binary files of the examples and the manuals are 1,496 files / 1.65 GB in Git LFS, and the checkout fetches them one at a time: 63 of the 67 minutes of the full installation on the main workstation (the commit message of `8f34806` says "68 of the 67", which is a slip). So the installer script always runs with `GIT_LFS_SKIP_SMUDGE=1` unless `all` is asked for, and `install/telemac_examples.py` then fetches a list. **Which files are needed is read from TELEMAC, not guessed from names**: every file keyword in `sources/*/*.dico` has a `SUBMIT` entry whose fifth field is `LIT` (read) or `ECR` (written); `needed_inputs` collects what the 830 steering files name under a read keyword and keeps the LFS pointers among them - geometry, previous-computation and data files, not the `f2d_*`/`*_ref*` reference results (two thirds of the files) and not what a run writes. Measured on v9.1.1: 363 files, 460 MB, 7.3 min through `git lfs pull --include` in lists of 60 (the whole installation 10.9 min; TELEMAC's `gouttedo` example then runs, its reference result still a pointer). The step is `optional` in the plan: TELEMAC is built by then and its server answers `429` after many requests, so a failure is a warning (`axqua.install.step_incomplete`) and `axqua install telemac-examples <folder>` repeats what is missing (the action carries TELEMAC in its name because "the example cases" otherwise means the examples of aXqua). It is one of aXqua's own steps and runs as `python -m axqua install telemac-examples`, not through the installer scripts.

**The steps run in a cleaned environment** (`recipes.clean_environment`, the installer's own whitelist plus the proxy variables): aXqua usually runs inside conda, whose `cmake`, compilers and MPI would otherwise come first on `PATH` and get mixed into the build.

**The OpenFOAM binding is the stack's own `shell-rc.sh`**, not `etc/bashrc`: it sources v2406 and adds `WM_PROJECT_USER_DIR`, where the sediment solvers and the BAW library live. Verified with `SolverEnvironment.validate` on this machine.

**Found by doing it.** `sediment_installer/installer.py` of the pinned commit has an f-string with nested double quotes (line 350) that only parses from Python 3.12 on, so `python3 install.py` is a `SyntaxError` on stock Debian 12 (3.11) and Ubuntu 22.04 (3.10) - the installer's own targets. `installer_python` therefore *tries* the interpreters (aXqua's first) and reports `axqua.install.python_too_old` when none can compile the files; it needs no change when the installer is fixed. With `--reuse-openfoam`, the 56-package list is what compiling OpenFOAM takes, not what building the solvers takes: this machine lacks `gawk` and `libmpc-dev` and the stack builds without them, so in that case the finding says so (`Plan.package_note`).

Tests (`tests/test_install.py`) install nothing: a fixture lays out a folder like the repository whose scripts create the promised files. Real runs on the main workstation, into scratch folders with `AXQUA_DATA_DIR`/`AXQUA_HOME` redirected so the user's profile was not touched, are recorded in the commit message.

## What an installation can do for aXqua (`core/installation.py`, `axqua profile inspect|use`)

**The user's order of 2026-10-30**: a valid installation that lacks a part must be told apart from an invalid one. `installation.inspect(solver, script)` enters the script once (`SolverEnvironment.validate`) and looks, with the PATH and variables the script set, for each part aXqua uses: required (TELEMAC-2D: `telemac2d.py` + the build's `bin/telemac2d`/`lib/libtelemac2d.*` under `BUILD_DIR` of v9, else `$HOMETEL/builds/$USETELCFG`; OpenFOAM: `interFoam`, `checkMesh`, `decomposePar`, `reconstructPar`) and optional (TELEMAC-3D, GAIA `lib/libgaia.*`, partel + MPI launcher, the Fortran compiler of `build_commands.json` / `cmd_obj`; OpenFOAM v2406, `sediDriftFoam2`, the BAW library in `FOAM_USER_LIBBIN`). A missing required part is `axqua.environment.solver_incomplete` (invalid), a missing optional one `axqua.environment.module_missing` (valid, names the module that will not work). `profile._probe` delegates to it, so *Check* of the profile says the same. `core` must not import a backend, so the names `BAW_LIBRARY`, `FINE_SEDIMENT_SOLVER` and `OPENFOAM_RELEASE` live in `core/installation.py` and the backends import them (`dicts`, `sediment`, `profile` re-exports). `profile use` enters through `install.runner.bind`, the same function an installation ends with. **Which settings a new script keeps** is `profile.rebound(profile, solver, script)`: only the same script (`same_script`, compared as full paths, the old one named or located in the installation folder) keeps `config_name`, `overrides` and `shell` (`INSTALLATION_FIELDS`); another `pysource.<configuration>.sh` of the same folder sets another configuration and drops them. `jobs.profiles.implicit` applies the same rule. Measured on the main workstation: the TELEMAC v9.1.1 build complete; the login-shell OpenFOAM-9 valid without v2406, sediDriftFoam2 and the BAW library; `~/.local/openfoam-sediment-v2406/shell-rc.sh` complete. The fake TELEMAC of the tests is now a build tree of empty files (`tests/fakes/telemac/builds/fake`).

## Windows: aXqua in Windows, TELEMAC and OpenFOAM inside WSL (`install/wslproxy.py`, the user's decision of 2026-11-06)

**One aXqua, in Windows; the simulation programs inside a WSL 2 distribution.** The earlier docs asked for a second aXqua inside the distribution, whose installer wrote a profile nobody read (a student's report on a German Windows computer). Now `axqua install plan|packages|overview|telemac-examples` on Windows run **the installer code of this aXqua inside the distribution**: `wsl.exe -d <distro> --exec env AXQUA_DATA_DIR=<the Windows data folder as /mnt/c/...> ... python3 -c LAUNCH install ...`, where `LAUNCH` loads the `axqua` package of the Windows folder and calls `installcli.run_install` directly, **not** `axqua.__main__`, whose `cli.py` imports the pipeline and numpy, which a fresh distribution's python3 lacks (the wheel job of the 1.3.2 release found it; the conda job's python3 has numpy, so the stand-in `wsl.exe` of the tests now runs `python3 -S`). That works because `axqua.install` imports the standard library only (`test_the_installer_code_needs_nothing_but_the_standard_library` keeps it so; checked with Python 3.11). **`--exec`, never `--`**: after `--`, wsl.exe hands the command line to the default shell, which expands `$(...)` and re-splits the quoting. Path options are translated to Linux (`installcli._linux_paths`); OpenFOAM is planned with `--no-visualization` and the `postprocessors` target is refused (ParaView and VisIt are Windows programs there); without a usable distribution the plan has the one finding `axqua.install.windows_needs_wsl` whose remedy is for the administrator (`recipes.WINDOWS_REMEDY`). `start` plans in WSL with `--no-bind` (`options.bind` stays False in plan.json, `bind_windows` carries the intent) and `runner.start_in_wsl` keeps the installation folder on the Windows side, records the detached `wsl.exe` that keeps the runner and the WSL machine alive in `keeper.json` (a file of its own: the runner inside rewrites status.json from memory), and `runner.read` enters a finished installation once in the Windows profile as `\\wsl.localhost\<distro>\...` paths, which `profile.rebound` turns into `environment: wsl` + `distro`. `cancel` writes the request and only ever signals Linux process ids inside the distribution. **Inside WSL, administrator steps and Run fixes run as the root of the distribution** (`recipes.elevation() == "wsl"`, `wsl_root`: `wsl.exe -d $WSL_DISTRO_NAME -u root`), which needs no password and no Windows administrator; `clean_environment` keeps `WSL_INTEROP`/`WSL_DISTRO_NAME` for that and sets `LC_ALL=C.UTF-8`, because apt's answers are parsed in English. **Nothing of this ran on a real Windows with WSL**: tests use a stand-in `wsl.exe` that runs the command locally (`tests/test_install_wsl.py`), so the Linux half really runs.

## Windows: TELEMAC built in Windows itself (`install/windows_telemac.py`, `--native`, the user's decision of 2026-11-10)

**Without WSL, or when the wizard's *Build TELEMAC* says *In Windows itself*, TELEMAC is compiled as a Windows program in the user folder**, no administrator, one processor core (no MPI) by default; the opt-in parallel build is described at the end of this section. It is the route a Windows test computer without administrator rights proved by hand on 2026-11-09 (TELEMAC v9.1.1, conda-forge gfortran/gcc 15.2 + CMake + `mingw32-make`, MinGW Makefiles, `builds\win64-seq`, the Isar steady run in 58 min through the job list); re-test 4 (2026-11-10) ran the wizard's installation there: 16 min, closing QGIS mid-compile, cancel without survivors, and the Isar run on the result. It is not an installer script inside aXqua: `recipes._plan_telemac_windows` writes a conda step (`conda create --override-channels -c conda-forge --prefix <folder>\telemac-build WINDOWS_PACKAGES`, the conda of the installation aXqua runs from, `recipes.conda_base`, else `axqua.install.conda_missing`) and four steps `python -m axqua.install.windows_telemac source|configure|build|script` (standard library only), which download TELEMAC from its own GitLab at install time (`windows_telemac.REPOSITORY`, `TAG`, `GIT_LFS_SKIP_SMUDGE=1`, `core.longpaths`), run CMake and Make with the environment's folders first on `PATH` and its `etc\conda\activate.d\*.bat` hooks called first, always through `cmd` so a bare program name is found on the environment's `PATH` and not the runner's (`windows_telemac._run`; **not** conda's `activate.bat`, which asks PowerShell for a temporary name and printed "'powershell' is not recognized" on the test computer; `--conda-base` is still accepted and ignored), build `homere_telemac2d build_commands` (`--modules 2d`, default) or everything plus `build_commands` (`all`), and write `telemac-mascaret\configs\pysource.win.bat` with `%USERPROFILE%`-relative paths (a batch file is read in the console code page). Outputs `solvers.telemac.setup_script`, expects `builds\win64-seq\bin\telemac2d.exe`; `--reinstall replace` removes `telemac-mascaret` with `windows_telemac remove` (Git's read-only objects), the compiler environment stays and is reused. `axqua install plan|packages|start telemac` on Windows take this route with `--native` or when no WSL 2 distribution is usable (`installcli._native_windows`), the overview gives `native_folder` (`recipes.windows_folder()`, `~\opt\telemac`); OpenFOAM still needs WSL (`windows_needs_wsl`). **The runner runs on Windows for this**: detached with `CREATE_NEW_PROCESS_GROUP | CREATE_NO_WINDOW`, breaking away from QGIS's job object where allowed; each step in a process group of its own with a hidden console; a step is ended with `taskkill /T /F` (`_kill_group`), and `cancel` on Windows never signals the runner (that would be `TerminateProcess` and leave the build running) but writes `cancel.request` and waits; `clean_environment` on Windows keeps the Windows variables and only `system32;Windows;Wbem` on `PATH`. The wizard (`install_wizard`) shows *Build TELEMAC* (`route`) and *Modules* only for TELEMAC on a Windows host, hides *Install for*, the example cases and SALOME for the build in Windows, and sends `--native` / `--modules all` (`runner_client.install_flags`). Re-test 5 (2026-11-10, aXqua 1.3.3 from PyPI) passed every step: wizard build 868 s with zero `powershell` lines, step times in the log, Isar started and cancelled from QGIS without survivors, CLI install cancelled during Configure without survivors; its documentation findings (the 58-min run was a hand-prepared build after a failed clone, the source step's number varies, `profile check` lists findings while `profile show` names the script) are in `docs/installation/simulation-software.rst`.

**The parallel build (`--mpi`, wizard route `windows-mpi`, opt-in since 2026-11-11, the user's decision)** follows what the Windows test computer did by hand on 2026-11-11 (results in `~/axqua-diagnostics/telemac-windows-native-mpi-results/` on the main workstation): MS-MPI 10.1.3 runtime + SDK from TELEMAC's WinTel repository at a fixed commit (`windows_telemac.MSMPI_URL`, eight files pinned by SHA-256 in `MSMPI_FILES`, into `<folder>\msmpi`), an import library `lib\libmsmpi.a` from `msmpi.def.x86_64` with the environment's `dlltool`, `mpi.mod` from `mpi.f90` with `MPI_FORTRAN_FLAGS` (GNU Fortran refuses MS-MPI's BOZ constants otherwise), and a two-process `MPI_Allreduce` probe before anything long runs (step `msmpi`); METIS 5.1.0.3 (scivision's CMake tarball, SHA-256 pinned) compiled static into `<folder>\metis\build` (step `metis`); CMake with `-DUSE_MPI=ON` and the explicit FindMPI variables of `_mpi_options` (without `MPI_Fortran_LIB_NAMES` and `MPI_mpifptr_INCLUDE_DIR` the test's configure failed twice), build folder `builds\win64-mpi`, `configure` refuses a `systel.cfg` without `mpi_cmdexec`; `--modules 2d` adds `homere_partel homere_gretel`; the script is `configs\pysource.win-mpi.bat` with `MPIRUN=mpiexec`, `MSMPI_DISABLE_ND=1` and MS-MPI's `bin` on `PATH`. Nothing is registered in Windows: `mpiexec` starts `smpd` itself. Downloaded at install time, never shipped (aXqua stays small). `--reinstall replace` leaves `msmpi` and `metis` like the compiler environment: verified files are reused. `--mpi` on Linux/WSL is `axqua.install.mpi_native_only`; on Windows it implies `--native`. The test found 4-rank Gouttedo 2D/3D equal to 1 rank and to TELEMAC's references, Rouse 3D+GAIA 1 vs 2 ranks equal, `axqua submit --np 4` on Isar COMPLETED, `profile inspect` saw parallel support. Re-test 6 (2026-11-11, `~/axqua-diagnostics/telemac-windows-retest6-results/`) passed the wizard's own MPI build (2D+GAIA 16.5 min: compilers 261 s, compile 549 s; all modules 987 s, telemac3d.exe built), no firewall dialog, Isar from QGIS on 4 ranks COMPLETED in 23 min (58 min on 1 core), merged r2d.slf, worker listings removed. Its cancel from QGIS left no process but took 11-12 s from the click: `axqua cancel` imported the pipeline (NumPy, pandas) before writing the request, and `ShellRuntime.run` asked `should_stop` only after an output line while TELEMAC printed in bursts; both fixed, plus job.json recording the case's count instead of the job's `ncsize`. Not yet tested: a 3D simulation through aXqua on Windows.
