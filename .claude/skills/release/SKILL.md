## The program on PyPI (`pip install axqua`, since 1.0.1)

**The user asked on 2026-10-19 whether the program could go to PyPI; the answer was measured, not assumed.** The wheel is pure Python (about 1 MB). Installed with pip alone into a plain venv, with no conda, every dependency comes from PyPI wheels (rasterio and pyogrio each bring their own name-mangled GDAL and coexist), the whole `tests/` suite passes on Python 3.10 and 3.12, and the example downloads from GitHub raw at the tag and builds in about a minute. So the conda stack of `environment.yml` and of the `test` job is a choice, not a requirement; the `wheel` job of `tests.yml` keeps it that way by testing the built wheel pip-only on 3.10 and 3.13 from a folder whose `import axqua` must resolve to site-packages. Tests that read the checkout find it from their own file (`Path(__file__).parents[1]`), never from `axqua.__file__`, or they break (or, for `git grep`, pass vacuously) against an installed wheel.

**What the wheel carries is checked, because PyPI never takes a version twice** (a deletion does not free the number; a release can only be yanked): `scripts/check_wheel.py` requires the package to hold exactly the tracked files of `src/axqua` minus `CLAUDE.md` (so bytecode a run of the vendored installer's tests leaves in a working tree, or a file missing from the package data, fails), and the `License-Expression` and `license-files` of `pyproject.toml` in the metadata. The expression is `BSD-3-Clause AND MIT AND GPL-3.0-or-later` because the wheel carries the vendored OpenFOAM installer (MIT) and Olsen's sources (GPL, an aggregate per `NOTICE`); PEP 639 needs setuptools >= 77. What the wheel does not carry: `cases/case-template/`, `scripts/` and the docs sources; the docs link them on GitHub (`docs/installation/qgis-plugin.rst#install-from-source`). The examples and Help already handle a wheel install (`examples.sources`, `docscli.checkout`). gmsh's Linux wheel links X11/OpenGL libraries even for headless meshing (`libGLU.so.1` first); the installation page lists the `apt` packages.

**Release**: since 1.2.0 (the user's order of 2026-11-01, "I pushed but the new release is still missing") a new version on `main` is released without a tag pushed by hand: `.github/workflows/auto-release.yml` runs when `tests` has passed for a push to `main`, and if `v<version>` of `pyproject.toml` does not exist, checks the four version places and the changelog head of `metadata.txt`, pushes the tag on the tested commit and starts `release` with `gh workflow run plugin-release.yml --ref v<version>` (a tag pushed with the workflow's GITHUB_TOKEN starts no workflow, a dispatch does). So a release is: bump the version in the four places, add the changelog entry, push. Since 1.1.1 (the user's order of 2026-10-27, "automate the pypi axqua package releases via gh") a pushed tag `v<version>` publishes the program: the job `pypi` of `.github/workflows/plugin-release.yml` (workflow `release`) builds, runs `twine check` and `scripts/check_wheel.py`, and uploads with trusted publishing (environment `pypi`, deployment restricted to tags `v*`, no token stored) while the repository variable `PYPI_UPLOAD` is `true` (set with `gh variable set`); it skips a version already on PyPI and attaches the wheel and sdist to the GitHub release. The publisher registration on pypi.org (owner sschwindt, repository aXqua, workflow `plugin-release.yml`, environment `pypi`) is the user's, done in the browser; without it the job fails with `invalid-publisher` and is re-run with `gh run rerun <id> --failed` once it exists. *Run workflow* with target `testpypi` rehearses on TestPyPI regardless of the variable. Before that, 1.0.1 and 1.0.2 were uploaded by hand with `twine` (commands in `docs/code/plugin.rst`, still the fallback); 1.1.0 was tagged but never reached PyPI. The version is in `pyproject.toml`, `_FALLBACK_VERSION`, `qgis_plugin/axqua/metadata.txt` and `docs/conf.py`; the first two and the plugin are pinned together by tests, and the job checks the tag against `pyproject.toml`.
