## The five pipeline stages

`axqua cases/example-Inn/case-config.yml` runs a 5-stage pipeline (`src/axqua/pipeline.py`):

1. `dem.py` - reproject + clip the initial (and optional target) DEM to the ROI boundary. When `dem_of_difference.enabled` (or `morphodynamics.enabled`), also computes the **DEM-of-Difference** (`dem.dem_of_difference`, `dem_target - dem_initial` on the ROI-clipped initial grid) thresholded by a **minimum level of detection** (`dem.resolve_lod`): an explicit `dem_of_difference.min_lod`, else the propagated survey uncertainty `t·√(uncertainty_initial² + uncertainty_target²)` (`dem.propagated_lod`, `t` from `confidence_level`); sub-LoD cells are masked to nodata (`mask_below_lod`) or zeroed, and the net/erosion/deposition volumes are logged. A precomputed `geodata.dem_of_difference` short-circuits the computation.
2. `mesh.py` + `selafin.py` - gmsh triangular mesh; DEM interpolated onto nodes; geometry written as SELAFIN with a `FRIC_ID` per-node variable (so no separate ZONES FILE is needed). The geometry is written in **double precision** (SERAFIND); single precision collapses sub-metre cells on UTM coordinates (see `selafin.py` design point). `build_mesh` prunes gmsh's geometry/1D-only nodes to triangle-referenced nodes (no orphans/duplicates), enforces consistent CCW winding, then runs `mesh_quality.assess_quality` (logged via `log_report`, stored on `Mesh.quality`). The mesh boundary is walked to build IPOBO, which **must** stay consistent with the `.cli` row order. **Two meshing strategies** (auto-selected): *anisotropic* (when `geodata.mesh_zones` + `geodata.channel_centerline` are set) types each mesh-zone polygon `channel`/`floodplain`/`refinement` (by `Zone Name` substring) and sizes it by its own `Max Edge Length (m)` field - channel cells elongated along the centerline, floodplain/refinement near-equilateral - via a metric-tensor background view + gmsh **BAMG** (`Mesh.Algorithm=7`); *isotropic fallback* uses `default_size`/`breakline_size`/`region_sizes` distance fields. See "Meshing" below.
3. `boundary.py` - classify contour nodes against the liquid-boundary lines and write the `.cli`. The lines come from `boundaries.liquid_boundaries` (a line layer whose `Type (inflow/outflow)` field - note the Inn file's typo `Type (inflow/outlfow)`, still detected - tags each line `inflow`/`outflow`; several of each allowed) and must coincide with the mesh-zone outer bounds. Codes: solid wall `2 2 2` (every non-liquid outer node), inflow `4 5 5` (prescribed Q, depth free - `LIHBOR` must be 4 not 5, else the inflow depth is forced to the inflow's PRESCRIBED ELEVATIONS slot of 0 and TELEMAC's DEBIMP aborts on a dry inflow), outflow `5 4 4` prescribed-elevation (the default `boundaries.outflow_condition: elevation`, a fixed WSE from `boundaries.prescribed_elevation`; or `stage_discharge` for a WSE from the rating curve at the simulated Q) or `4 4 4` free/Neumann (`outflow_condition: free`, needs no WSE). Matching tolerance is tied to the local edge length (anisotropic: ~2×`floodplain_size`). If total inflow- vs outflow-node counts differ by >10%, a stability-risk warning is logged.
4. `steering.py` - friction `.tbl` (one row per friction zone: `<id> <LAW> <coef> NULL`, ends with `END`; comments only on `*` lines - rows come from `friction.zones`/MATID or, failing that, the roughness table as `<Zone ID> NIKU <ks> NULL`) and the Telemac2d `.cas`; GAIA `.cas` when enabled. The **default solver is the classic finite-element kernel** (`hydrodynamics.finite_volumes: false`); set it true for the HLLC finite-volume kernel (robust on transcritical wetting/drying but constant-viscosity only). The **turbulence model is auto-selected** (`hydrodynamics.turbulence_model: auto`) by `steering.select_turbulence_model(cfg, mesh)` (user's order 2026-11-03): a depth-averaged model never resolves eddies smaller than the depth, so it compares the **Smagorinski filter width** of the channel cells (`steering.filter_width`, sqrt(2A) as in TELEMAC's `smagor.f`; about 1.5x the nominal channel size of the anisotropic mesh) with the **flow depth** of `steering.flow_scale` (explicit `turbulence_length_scale` > median wetted depth of the case's steady `r2d.slf` > normal flow at the case discharge through the centerline cross-sections, `_normal_flow_sections`, shared with the pre-wet > `prewet_depth` > 1 m with a warning; normal flow ignores backwater, KB15: 0.57 m against 0.89 m): **k-epsilon (3)** where the filter width exceeds `les_depth_ratio` (1) depths (TELEMAC's 2D k-epsilon has the Rastogi-Rodi bed production, `kepsil.f`, and a viscosity independent of the mesh), **Smagorinski LES (4)** where it does not, with the bed turbulence `les_bed_coefficient` (kappa/6) x u* x h added by a generated `user_fortran/smagor.f`. **k-epsilon needed two fixes to run at all on the wetting/drying KB15 mesh**: GMRES for the k-epsilon system (`keps_solver` 7; TELEMAC's default conjugate gradient failed ~3x per step, some NaN, because the system is not symmetric) and a generated `user_fortran/corvis.f` that resets k, epsilon and the viscosity on nodes shallower than `keps_shallow_depth` (0.02 m): TELEMAC computes C_mu k^2/eps at dry nodes too and never caps k, and on the coarse KB15 mesh k reached 147 at a dry node after 12 s (viscosity 57,000 m2/s) and the run stopped after 26 s with `LIMIT VALUES TRESPASSED`. The same routine bounds the turbulent length scale C_mu^0.75 k^1.5/eps by `keps_length_limit` (1) depths through epsilon: the run starts with k = 0 and eps at its 1e-8 floor, and on the KB15 mesh finer by 1.3 k grew 0.18 -> 482 m2/s2 in a second at a wet node near the outflow (viscosity 1e5 m2/s, stopped after 10 s); steady bulk length ~3 cm in 0.9 m, so inactive there. With GMRES + reset + limiter the six-mesh KB15 study (edge 1.95 to 0.525 m, 8000 s each) ran with zero k-epsilon solver failures; averaged over the second half, the velocity changed 11.3/4.2/7.7/7.2/2.7 % and the depth stayed near 1 %, and the last change (2.7 %) lay below the runs' own fluctuation in time (3.7 %), almost all of it at the point below the inflow. Those were points from 21 m below the inflow; at the points that keep 189 m from the liquid boundaries (since 2026-11-04, `convergence.boundary_clearance`) the velocity changed 4.8/2.2/3.0/2.0/1.2 % and the depth 2.9/2.2/2.0/0.8/1.0 %, so four meshes are within 5 %. Both routines come from `solvers/telemac/turbulence_fortran.py` (`write_routines(cfg, model)`, called by `write_cas`, which emits `FORTRAN FILE`; routines of another model are removed again, a user's own file of the same name is never touched, and they are never linked into TELEMAC-3D: `three_d_routines`). **Spalart-Allmaras (6) is never auto-selected**: TELEMAC-2D's (`spalart_allmaras.F`) has no bed production and takes its length scale from the distance to the banks (`WDIST`), so an explicit choice is honored with a warning unless the reach is at most `SA_MAX_WIDTH_DEPTH` (10) depths wide (a flume). Until 2026-11-03 the rule was an 80 %-TKE 3D-LES criterion on L = 1 m or the pre-wet depth, which put KB15 and the Isar example on Spalart-Allmaras. LES output adds the eddy viscosity `D` to the printouts; the smoke run on KB15 (baseline mesh, 300 s) gave a median 0.0062 m2/s with the bed term against 0.0021 without. The **initial run is always steady** (`steady2d.cas`). The FE numerics are written **compute-stable by default** to keep the wetting/drying steady march from exploding: `time_step` is only a conservative CFL **start** step (0.25 s) while `desired_courant` (0.30) drives the adaptive marching step, `IMPLICITATION FOR DEPTH/VELOCITY` 0.80 (config `implicitation`), `FREE SURFACE GRADIENT COMPATIBILITY` 0.9, `DISCRETIZATIONS IN SPACE : 11;11` (linear FE, required by the distributive advection scheme 14), `NUMBER OF SUB-ITERATIONS FOR NON-LINEARITIES`/`MAXIMUM NUMBER OF ITERATIONS FOR ADVECTION SCHEMES`, `H CLIPPING : NO`, and a raised k-epsilon solve budget (`MAXIMUM NUMBER OF ITERATIONS FOR K AND EPSILON`, config `max_keps_iterations`). The graphic printout is `'U,V,S,B,H,M,Q,F'` plus `K,E` (TKE + dissipation) **for the k-epsilon model (3)**. **Time bound:** with the default `variable_timestep` the run is capped by `DURATION` (the explicit `hydrodynamics.duration` in seconds, else the `n_time_steps × time_step` fallback - so a small CFL start step no longer shrinks the simulated time), **not** `NUMBER OF TIME STEPS` - the latter does **not** terminate a variable-dt run (the CFL-driven dt is unknown a priori), so it would otherwise be unbounded. Convergence is judged by the **boundary-flux balance** (`initial_run.py` → `axqua.flux_convergence`), not by the solver. **The steady-state auto-stop is OFF by default** (`hydrodynamics.stop_if_steady: false`) and is hard-suppressed whenever `variable_timestep` is on: TELEMAC's `steady.f` stops when the change between **two consecutive time steps** falls below `STOP CRITERIA`, but that is an **absolute per-step** change (order **H ; (U,V) ; tracers** in `steady.f`; the dico's English help listing (U,V) first is wrong), and with the tiny CFL dt it false-fires during a slow transient (e.g. a low-Q reach still filling from a dry start) **long before the fluxes balance** - the run halts far from steady state (the symptom: it stops with inflow ≠ outflow). It is emitted only for a steady **fixed-step** run (`variable_timestep: false`, where a per-step change is meaningful), never for the unsteady run, and **TELEMAC-3D has no equivalent keyword**. When `boundaries.inflow` carries a *varying* hydrograph, `pipeline.run` additionally writes `unsteady2d.cas` (DURATION from the series) plus a TELEMAC liquid-boundaries file (`inflow-hydrograph.liq`, `Q(t)` per inflow / `SL(t)` per prescribed-elevation outflow via `steering.write_liquid_boundaries`). The steady inflow Q comes from `boundaries.prescribed_flowrate` (the optional `boundaries.inflow` series, read by `hydraulics.py`, is only for a varying hydrograph / unsteady case). The outflow water-surface elevation is needed for the prescribed-elevation conditions: the default `boundaries.outflow_condition: elevation` uses `boundaries.prescribed_elevation`, while `stage_discharge` interpolates `boundaries.stage_discharge` (a Q-h CSV; one pair suffices for steady) at the simulated Q; `free` prescribes nothing. When no measured rating curve exists, `axqua.rating.generate_stage_discharge` (CLI: `axqua rating`) synthesizes one from a Manning `n`/Strickler `Kst` and a trapezoidal channel geometry by inverting Manning's normal-flow equation; `rating.synthesize_outflow_rating(cfg, Q)` derives the geometry from the case data (width = outflow liquid-boundary line length, bed = DEM thalweg along it, slope = reach slope from the DEM along the centerline, roughness = `friction.boundary_*`) and `cases/example-Inn/preprocessing.py` (and the convergence-study script) call it to auto-generate `boundaries.stage_discharge` when missing. The lateral-boundary friction keywords (`LAW OF FRICTION ON LATERAL BOUNDARIES` / `ROUGHNESS COEFFICIENT OF BOUNDARIES`) come from `friction.boundary_law` / `boundary_coefficient` (Inn: Strickler 38).
5. `ground_truth.py` + `calibration.py` - compile the configured `ground_truth.sources` into the **tidy multi-tab table** (`ground_truth.compile_ground_truth`, written to `preprocessing_dir/ground-truth.xlsx` unless `ground_truth.measurements` overrides), then turn it into `measurements-calibration.csv` and the HydroBayesCal `config_Telemac.py` (both in `calibration_dir` = `calibration-validation/`).

`pipeline.run()` returns an `Artifacts` dataclass listing every produced path; `cli.py` logs these. The public API is `__all__` in `axqua/__init__.py` (resolved lazily; see Package structure). `mesh.build_mesh(cfg)` (no DEM) yields a bare mesh; `interpolate_elevations(mesh, dem, decimals=4)` fills the bottom from a raster (rounded); `write_mesh(mesh, path)` writes a geometry SELAFIN. These low-level helpers let you build a mesh programmatically; the worked example's `preprocessing.py` instead drives the full `pipeline.run` build (writing `geometry.slf` etc. into `simulation/`; see the workflow below).

## Meshing and build design points

Key design points:
- The build runs in its **own** `axqua-env` conda env (gmsh/geopandas/rasterio); it does not import TELEMAC's Python. `env.py` *sources* `telemac.pysource` (the `pysource.*.sh`) in a subshell for any solver/SELAFIN call. The config's `telemac.pysource` must point at the real script (e.g. `/home/modelling/telemac-v911/telemac-mascaret/configs/pysource.debian12.sh`).
- Friction zonation has two routes: (a) the **roughness-zones** route - `geodata.roughness_zones` (`Zone ID`) + `geodata.roughness_table` (id→ks) drive the per-node `FRIC_ID` and `BOTTOM FRICTION` via `interpolate_roughness` (preferred for the Inn case; see the Meshing section); (b) the older **MATID** scheme (1 riverbed_fine … 5 floodplain; see table below) carried by `geodata.region_points` + `geodata.region_table` and/or `friction.zones` in the config → friction `.tbl` rows and `zone<MATID>` calibration parameters. Either way HydroBayesCal perturbs the coefficient column of the `.tbl`. `steering.write_friction_tbl` builds the `.tbl` in priority order: explicit `friction.zones` (MATID) > the roughness table (one `<Zone ID> NIKU <ks> NULL` row each) > a single default zone - so the `.tbl` rows always match the geometry's per-node `FRIC_ID`.
- `src/axqua/selafin.py` is a self-contained big-endian SELAFIN writer (plus a `read_slf` reader for results); its output is validated against TELEMAC's own `data_manip.formats.selafin.Selafin` reader in the tests.
- **Logging** (`src/axqua/logsetup.py`): each script/phase writes a compound, timestamped `axqua.log` into its **own output folder** (`setup_logging(path)` routes the `axqua` logger and captured Python warnings to it; file at DEBUG, console at the chosen level, append mode). the build (`pipeline.run`, called by `preprocessing.py`; and `initial_run.py`'s test run) -> `model_dir` (`simulation/`), the mesh-convergence study -> `mesh-convergence/` (scoped via the `logging_to(path)` context manager so it doesn't capture the per-level builds elsewhere). `log_step(name)` logs `START`/`DONE … in N.NNs` (or `FAILED … after N.NNs`) - wrapped around every pipeline stage and the heavy mesh/convergence sub-steps for per-step timing. `pipeline.run(..., log_to_file=False)` skips its own logfile (the convergence study's per-level builds use this so they log only to `mesh-convergence/axqua.log`). Tests reset handlers via an autouse fixture (`tests/conftest.py`).
- **Initial condition - DRY START (default) vs pre-wetting**: the initial run is a **dry start** by default. A *fully* dry bed (`ZERO DEPTH`) can't be used because TELEMAC's `DEBIMP` aborts at a prescribed-Q inflow when the inflow cross-section is dry (it scales the velocity profile by Q/Q1 with Q1 ∝ ∫H along the inflow; H=0 ⇒ Q1=0 ⇒ abort, even with the correct `4 5 5` code - see the inflow-cli memory). So `steering.write_dry_start_conditions` seeds a thin water **plug only on the nodes within `initialization.dry_start_extent` of the inflow line(s)** (default ~5 cells) to `dry_start_depth` (default 0.5 m, kept ≥ normal depth so the inflow stays subcritical) and leaves the rest of the domain **dry**; the `.cas` continues from this SELAFIN (`PREVIOUS COMPUTATION FILE` + `INITIAL TIME SET TO ZERO : YES`) and the flow wets the reach from the inflow. The inflow geometry comes from `boundary._load_liquid_lines`; with no inflow line it falls back to the analytical dry `INITIAL CONDITIONS`. **Pre-wetting** (`initialization.prewet_depth`, m) is the *alternative*: when set, stage 4 instead hotstarts the **`*channel*` mesh-zone** (`write_initial_conditions` + `mesh.channel_node_mask`) so the wetting front need not advance from the inflow - a large time saving, used by the **mesh-convergence study** (`INITIAL_DEPTH`, default 0.5 m) but **not** the initial run (which the user wanted dry). **How the seeded surface is built** is `initialization.prewet_mode`: the default **`normal-depth`** (`_normal_depth_prewet_depth`) cuts a real perpendicular cross-section every `prewet_bin_spacing` (20 m) along the centerline, samples it at 0.5 m, clips it to the channel zones, and seeds the **stage that conveys the case discharge** through it via `rating.stage_for_discharge` (the Keulegan conveyance inversion factored out of `section_rating`, so the seed and the outflow rating share one implementation), with the local bed slope from the gradient of the transect thalwegs rather than one reach slope. The seeded surface is `thalweg + prewet_fill x (normal stage - thalweg)`; **`prewet_fill` is 0.70, below 1 on purpose** - under-seeding is recoverable (the flow refills a pool in seconds), over-seeding is not, because a 2D model has neither infiltration nor evaporation and water perched above the converged surface becomes permanent stagnant film. `prewet_mode: constant` is the older `_longitudinal_prewet_depth` (a low bed percentile per bin + `prewet_depth`), also the automatic fallback without a centerline or a discharge; on the braided isar-2025 reach it seeded a median **0.28 m above** the converged surface and left 4694 m2 (35% of the wetted area) as film that had stopped draining. `prewet_min_depth` (0.05 m) additionally leaves a node dry rather than laying down a feathered margin (a seed film is exactly what stalls), and `drainable_prewet` still runs on top. **After every filter the inflow plug is re-imposed** (`_inflow_plug_mask`, same `dry_start_extent`/`dry_start_depth` as the dry start): none of the filters has any reason to keep the inflow cross-section wet, and the normal-depth seed is shallowest exactly at the upstream end, so without the guard `DEBIMP` aborts the run at t=0 on a dry inflow - which is precisely what the old over-seeding had been hiding. Sizes are validated in `tests/test_prewet.py`; the calibration is recorded in `cases/isar-2025/test-approaches.md` (R2). `pipeline.run` records whichever file in `Artifacts.initial_conditions`. A side effect of the dry start: while the domain is mostly dry the **k-epsilon / Spalart-Allmaras turbulence linear solve** is ill-conditioned, so TELEMAC's needlessly tight default accuracy (`ACCURACY OF K`/`EPSILON`/`SPALART-ALLMARAS` = 1e-9) is unreachable within its 50-iteration cap - the transient `GRACJG: EXCEEDING MAXIMUM ITERATIONS 50` warning, which is **benign** (it reaches ~1e-6, the run stays mass-conservative and self-heals once the reach wets). `steering` therefore writes `hydrodynamics.turbulence_solver_accuracy` (default **1e-6**, plenty for turbulence) for the k-epsilon (3) / Spalart-Allmaras (6) models, which converges the turbulence solve in fewer iterations.
- Calibration CSV schema (read by HydroBayesCal): `id, x, y, z, <QTY>_DATA, <QTY>_ERROR`, where `<QTY>` is a SELAFIN name (e.g. `WATER DEPTH`, `SCALAR VELOCITY`).

v1 covers the **2D hydraulic** path end to end; the **DEM-of-Difference** (with a level of detection) is implemented in pre-processing (`dem_of_difference` config block, `dem.dem_of_difference` / `dem.resolve_lod`), and **GAIA morphodynamics** is wired for simulation - `steering.write_gaia_cas` writes a damocles-valid GAIA steering file (transport modes + bed-process capacities: morphological factor, slope effect, secondary currents, active-layer stratigraphy, prescribed solid discharges) coupled to the steady, `unsteady2d.cas` and `unsteady3d.cas` runs (`morphodynamics` config block). What **remains an extension point** is the *calibration* side: turning the DoD into per-point topographic-change calibration targets and folding the GSD `sediment_classes` into GAIA from the ground-truth template.

## The per-case workflow

`cases/example-Inn/` holds the worked example for the Inn case, run against its `case-config.yml` as flat scripts (`mamba run -n axqua-env python cases/example-Inn/<script>.py`). The **workflow is three ordered steps**: (1) `preprocessing.py` builds the complete TELEMAC case into `axqua-case/simulation/` (via `pipeline.run`, at the steady discharge from **this case's** `case-config.yml` `boundaries.prescribed_flowrate` - the shared `axqua.prepare_steady_inputs` helper reads the inflow Q and outflow-stage prescription from the config rather than a value hard-coded in the script, synthesizing a constant inflow series + outflow rating only if missing) - the final mesh `geometry.slf`, `boundaries.cli`, `friction.tbl`, `steady2d.cas`, plus the HBC artifacts in `calibration-validation/`; (1b) `initial_run.py` test-runs *exactly that* `steady2d.cas` once (`axqua.run_solver_streaming` → `TelemacRuntime.run_solver` with `-s --nozip`, no rebuild) to confirm it does not crash - the solver's listing is **streamed live** to the terminal (via `TelemacRuntime.run`'s `on_line` callback, so the run isn't silent) with a **progress bar** of simulated time vs `DURATION` (`axqua.progress.SolverProgress`; the CFL-adaptive dt makes the *number* of steps unknown a priori, so progress is measured against the simulated-time cap `expected_duration(cfg)` = `hydrodynamics.duration` else `n_time_steps × time_step`, with the live iteration count shown). A module-level **`NCSIZE`** at the top of `initial_run.py` overrides `telemac.n_processors` for this one test run (leave it `None` to use the configured core count). The run then gets a **boundary-flux convergence analysis** (`axqua.flux_convergence`) that reads the `.sortie` (needs `PRINTING CUMULATED FLOWRATES : YES`, already emitted) and writes four files into `simulation/` - `extracted-fluxes.csv` + `flux-convergence.png` (per-boundary fluxes) and `convergence-rate.csv` + `convergence-rate.png` (the relative imbalance `|Q_in|-|Q_out|`/`|Q_in|` and its convergence rate). The listing is parsed by **`axqua.sortie`** (`read_sortie` / `latest_sortie`): each `BALANCE OF WATER VOLUME` block is read as a unit and its time taken from the `RELATIVE ERROR IN VOLUME AT T =` line *inside* it, so times, volumes and fluxes cannot drift out of alignment and no sample is fabricated. This replaced a dependency on the external **pythomac** package, which cannot be vendored (it is GPL-3 and its parser derives from TELEMAC's GPL-3 `postel`, while aXqua is BSD-3) and whose package boundary forced several adapters: the printout spacing had to be back-calculated (a CFL-adaptive run has no fixed `period*time_step`), `convergence-rate.csv` had to be written separately (only the `.png` was produced), and the rate plot had to be swapped out whenever the rate was undefined. Now `flux_convergence` owns the maths (`relative_imbalance`, `convergence_rate`, `convergence_index`) and both plots; the converged time and iteration count are read straight off the listing rather than estimated, and the convergence figure always shows the relative imbalance (with the tolerance marked) plus the rate where it is defined - during the filling phase the rate is undefined everywhere, which is exactly when one needs to see the imbalance. **Tolerance grades** (`hydrodynamics.flux_tolerance`, default **1e-3**): the imbalance is *relative*, so the discharge/depth/velocity read off a steady run inherit it directly - 0.1% is far inside field-measurement uncertainty and inside the 5% the mesh-convergence study accepts, so 1e-3 is the right grade for a hydraulic result. The stricter **1e-4** (`HOTSTART_TOLERANCE`) is for a **hotstart seed**, where the residual transient is inherited by every perturbed calibration run rather than averaged out; 1e-6 is a rarely-worth-it validation grade. The *absolute* steady criterion is derived as `flux_tolerance x prescribed_flowrate` (so the hotstart gate means the same on a 2 m3/s side channel as on a 200 m3/s river) rather than a fixed 1e-3 m3/s. The analysis also **deletes the per-processor `*_p0000N.sortie` copies** of a parallel run (only the merged main listing matters) and detects the **absolute steady window**: when `||Q_in|-|Q_out||` stays below 1e-3 m³/s over 10 consecutive listing printouts (`flux_convergence.find_steady_window`; on a noisy steady state, whose instantaneous imbalance oscillates above that floor, the 10-printout *mean* is the fallback, flagged as such), a **`hotstart2d.cas`** is generated next to the steady case via `steering.write_hotstart_cas` - it continues from `r2d.slf` (`PREVIOUS COMPUTATION FILE`, clock reset), renames the results to `r2d-hotstart.slf` (no self-clobber), caps `DURATION` at that steady time, and keeps the constant Q/H prescriptions unchanged. A balanced flux budget says nothing about **where** the water is, so `initial_run.py` additionally writes `wetting-report.csv` and `outlet-profile.csv` via **`axqua.wetting`**: `wetting_report` splits the wetted area into *active* flow (H > 0.05 m, |U| > 0.15 m/s, in the largest connected body), *stagnant film* (wet but under 0.05 m/s) and *isolated puddles*, attributes each to the pre-wet seed when the initial-conditions SELAFIN is passed, and samples earlier frames to say whether the film is still draining or has **plateaued** - the failure mode a longer run cannot fix, since a 2D model has neither infiltration nor evaporation (isar-2025: 4694 m2 of film, 75% seeded, shrinking 1.8% over 3100 s). `outlet_profile` bands the actively flowing nodes by distance from the outflow line, reports the discharge-weighted free surface / depth / Froude per band, and compares the near-boundary surface slope with the reach's own to return `backwater` (the prescribed stage is holding the level up over ground that should be dry) / `drawdown` / `neutral`. The report's wetted threshold is `hydrodynamics.wet_depth` (0.01 m) - a **reporting** convention, since on a bed with ks 0.05-0.5 m water 5 mm deep stands *inside* the grain roughness rather than flowing over it (on isar-2025 that band was 13% of the wetted area but 0.16% of the volume); use the same filter in ParaView so the picture and the report agree. Water an external source holds in place is passed in via `supported=` and reported as its own category, excluded from *film* and *isolated puddles* - otherwise a legitimately wet water-table pool reads as a defect. This ends preprocessing; (2) `mesh_convergence_study.py` runs the grid-independence study; (3) `run_Bayes_cal.py` calibrates the built case with HydroBayesCal. An **optional 3D extension** runs after step 1b (and after step 2 fixes the horizontal mesh): `add3d.py` writes the three 3D steering files (hydrostatic flux-convergence check, non-hydrostatic steady, unsteady), then `vertical_convergence_3d.py` runs the vertical-layer (`dz`) grid-independence study - both are documented in the `hbc-calibration` skill. Step 3 compiles the FlowTracker velocity ground truth into the calibration-points CSV (the velocity at **0.6 h above the riverbed**, the user's rule of 2026-11-11, read off a log profile fitted to each vertical's readings by the default profile rule `log-profile` in `ground_truth.py`; MeasD counts from the surface, as the KB15 data confirm; compared to TELEMAC `SCALAR VELOCITY` = sqrt(U²+V²) built from the **horizontal** components only), ensures the `.cas` outputs `SCALAR VELOCITY` (graphic-printout `M`), emits `config_Telemac.py`, and stages and launches HydroBayesCal's `bal_telemac.py`. **HydroBayesCal is a pip dependency** (`pip install 'axqua[calibration]'`, requiring `>=1.12.2`, the floor whose history is in the comment above the extra in `pyproject.toml`; 1.12.1 starts the Sobol design at the first point of the sequence, 1.12.2 lets `gp_library: skl` run with TELEMAC. pip checks the floor only when it installs, so `hbc.require_hbc` also refuses an installed version below `hbc.HBC_MINIMUM`, and `tests/test_hbc_version.py` keeps the two equal): the driver is copied out of the installed package by `hydroBayesCal.copy_driver` and run in aXqua's own environment, so there is no checkout directory to point at and no second conda env to name. It is an *optional extra* because its surrogate stack (bayesvalidrox, gpytorch, scikit-learn) is irrelevant to building or running a TELEMAC case, so `bayescal.require_hbc` imports it lazily and explains the install if missing. The driver is still a subprocess - it is a script with an `argparse` main() that must run with TELEMAC sourced, and sourcing mutates the environment - but under `sys.executable`. Pass `checkout=` to develop against an unreleased driver; `--prepare-only` writes the CSV+config without launching - everything into `calibration-validation/`. HydroBayesCal reads the CSV's first four columns by position (id, x, y, z) and `<QTY>_DATA`/`<QTY>_ERROR` by name; `_ERROR` is a site-specific error in physical units added in quadrature to its built-in 10% measurement + 10% surrogate error.

## Build prerequisites

A build needs a **ROI boundary polygon** (`geodata.boundary`, a closed polygon/polyline in EPSG:25832; the Inn example uses `cases/example-Inn/user-sources/geodata/roi-kb15.gpkg`) and `boundaries.liquid_boundaries` (both set in the Inn config). The steady **inflow Q comes from this case's `boundaries.prescribed_flowrate`** (m³/s) - the shared `axqua.prepare_steady_inputs` helper (used by `preprocessing.py` and the mesh-convergence script) reads it from the config rather than a value hard-coded in any script, so each case uses its own discharge. A constant-Q `boundaries.inflow` series is then **auto-synthesised** at that discharge when missing (`boundaries.inflow` itself is optional - only a *varying* series triggers the unsteady case), and the outflow rating `boundaries.stage_discharge` is synthesized from a normal-flow curve when the `stage_discharge` outflow condition is active and none is given (the default `outflow_condition: elevation` needs no rating, just `boundaries.prescribed_elevation`), so the only machine-specific thing to set for a build is `telemac.pysource`.

## Material / region classification (MATID scheme)

Region/zone polygons assign a max triangle area (mesh density) and a `MATID` (material zone) used later for roughness and sediment classes in GAIA. Base resolution is ~0.2 m.

| MATID | name           | max area (m²) | type        | meaning                              |
|-------|----------------|---------------|-------------|--------------------------------------|
| 1     | riverbed_fine  | 1.0           | riverbed    | fine bed (sand, silt)                |
| 2     | riverbed_coarse| 4.0           | riverbed    | coarse bed (gravel, cobbles)         |
| 3     | block_ramp     | 0.5           | block_ramp  | block ramp / high-roughness structure|
| 4     | gravel_bank    | 2.0           | gravel_bank | gravel bank / transition zone        |
| 5     | floodplain     | 25.0          | floodplain  | floodplain, vegetated overbank       |

## Boundary-condition gauge data (Bavarian LfU)

The upstream (discharge) and downstream (water level) boundaries are driven by gauge exports from the Bavarian LfU (gkd.bayern.de) - discharge [m³/s] at Kraiburg (Q ≈ 47 m³/s for the Nov-2020 reference period), stage [cm] at Wasserburg (upstream) and Mühldorf (downstream). When such CSVs are supplied via `boundaries.inflow` / `boundaries.stage_discharge`, mind the **German LfU CSV format**:
- UTF-8 **BOM** on the first line.
- **Semicolon** delimiter, **comma** decimal separator (e.g. `43,3`).
- 9 metadata lines (Quelle, station name/no., Gewässer, gauge coordinates as `Ostwert`/`Nordwert`, `Pegelnullpunktshöhe`), a blank line, then a header row (`Datum;"...[unit]";Prüfstatus`), then `"YYYY-MM-DD HH:MM";value;Geprueft` rows.
- Times are MEZ (CET). Stage is in **cm**; convert to m and add the gauge zero-point height for absolute water-surface elevation.

Read with `pandas`: `pd.read_csv(path, sep=';', decimal=',', skiprows=10, encoding='utf-8-sig')`.
