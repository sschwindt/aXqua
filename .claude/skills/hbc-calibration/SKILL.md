### HydroBayesCal calibration (step 3) - `axqua/bayescal.py` + `axqua/campaigns.py`

Step 3 is **thin scripts over the package**: `run_Bayes_cal.py` (single discharge) and `run_Bayes_cal_multiflow.py` (multi discharge) each just declare the case-specific choices and call `axqua.run_single_flow_calibration` / `axqua.run_multiflow_calibration`. Both scripts live in `cases/case-template/` and every case folder. All logic - CSV compilation, `.cas` derivation, HBC config emission, driver staging, launching, the smoke test, resume - lives in `axqua/bayescal.py`; the multi-campaign FlowTracker-to-CSV compilers in `axqua/campaigns.py` (`adapter` = summary workbook + DGPS layer joined by ID; `transect` = taped cross-section + point gpkg keyed by vertical number; `inline` = inline-coordinate verticals; each keeps the 0.6-depth vertical and floors the propagated velocity error). Tests: `tests/test_campaigns.py`.

- **Single-flow** (`run_single_flow_calibration`): compiles `ground_truth.sources` into the velocity CSV, ensures the `.cas` prints `SCALAR VELOCITY` (`M`), emits `config_Telemac.py` via `calibration.emit_hbc_config`, stages `bal_telemac.py` and launches. `--prepare-only` stops before launch.
- **Multi-flow** (`run_multiflow_calibration`, `launch_mode` = `prepare`|`smoke`|`run`|`resume`): calibrates **one shared roughness against several steady discharges jointly**. The case script lists `axqua.FlowSpec(name, discharge, kind, values, positions, duration, vel_err_floor)`. Each flow gets its own steering file derived from the built base `steady2d.cas` (only Q, the outflow stage from the synthetic rating at that Q, `DURATION`, and the results name change) and its own calibration CSV; they are joined into one 57-point (e.g.) observation/output space by the **additive hydrobayescal extension** `hydroBayesCal.telemac.multiflow_telemac.MultiflowTelemacModel` + `bal_telemac_multiflow.py` (wraps one stock single-flow `TelemacModel` per flow; single-flow users untouched). `--smoke` runs an isolated 3-level tiny-run plumbing test (checks per-run JSON accumulation, that rows differ with ks, and the combined shape) in ~15 min before committing solver hours; `--resume` reuses each flow's completed initial design from `flow-<name>/.../restart_data/initial-model-outputs.json` (only_bal_mode) and skips straight to surrogate + BAL.

**Lessons baked in (all fixed / guarded):**
- **`prior_samples` is a memory trap.** gpytorch predicts the surrogate at every prior sample by building a `prior_samples x prior_samples` dense covariance **per calibration location**; 25000 OOM-kills a 16 GB box. `calibration.prior_samples` (config, default **5000**) is emitted into both single- and multi-flow configs; a low-dimensional roughness posterior needs only a few thousand. Raise only with RAM.
- **HydroBayesCal fixes (in the checkout, backward compatible for existing users):** (a) `control_telemac.rewrite_steering_file` matched only `KEYWORD = value`; aXqua `.cas` files use `KEYWORD : value`, so per-run RESULTS-FILE renames silently no-op'd - now matches `=` or `:`. (b) `function_pool.update_json_file` used `key in output_data` with **int** calibration-point IDs against JSON's **str** keys, so every run overwrote instead of appending (only run 1's outputs survived, rest read as zeros) - now `str()`-normalises keys. (c) `bal_functions.select_indexes` called `np.in1d`, **removed in NumPy 2** - now `np.isin`.
- **The staged driver extracts the `last` (converged) SELAFIN frame, not the `mean_last` window** (which would average a dry-start transient into the calibration values).
- **Data comparability governs which flows are calibratable - and verify the discharge label itself.** Compare per-campaign mean U, depth, and spatial span: a few-point survey confined to slow, shallow near-bank margins samples partially-wet cells the 2D depth-averaged model represents poorly, not the modelled channel (the Inn KB15 March-2026 campaign - 5 margin verticals, ~0.58 m / 0.02-0.52 m/s - was first excluded under a **mislabelled Q=168** that made the model look ~5x too fast; at the true **45.8 m3/s** the magnitudes match to order, but the margin points still carry the DEM too-shallow/too-fast bias and add no discharge diversity, so it stays excluded from velocity calibration). Use WATER DEPTH / flood-extent for high flow instead - **wadeable FlowTracker velocity surveys are safety-capped at low flow (~46-48 m3/s)** (river entry at high discharge endangers the operators), so velocity calibration cannot gain discharge diversity. Down-weight a single-cross-section campaign by raising its `vel_err_floor` (KB15 Nov-2025: 0.05 m/s) so its many low-variance points do not dominate the joint likelihood. `MultiflowTelemacModel` also fails fast on all-zero or all-identical initial-design rows per flow.

**Optional 3D extension (`add3d.py`, `axqua/threed.py`).** The 3D path sits **strictly after the 2D path** and depends on it twice over: a 3D run is only built (1) once the 2D run has produced its **hotstart** result (`initial_run.py` → `r2d.slf`; the 3D case is seeded from it and would otherwise start from a dry bed), and (2) once the **2D mesh-convergence study** has settled the **horizontal** resolution - the 3D case reuses that same horizontal mesh, so building 3D before step 2 means resolving the vertical on an unvalidated horizontal grid. After `initial_run.py` has produced `r2d.slf`, `add3d.py` writes **exactly three** steering files for `telemac3d.py` next to the 2D case (no rebuild) via `threed.build_3d_cases` (which reads `r2d.slf` **once** and shares the inferred levels/turbulence/dt across all three; the per-case script is a thin wrapper printing `workflow.format_3d_cases`): (a) **`hotstart3d_hydrostatic.cas`** - `NON-HYDROSTATIC VERSION : NO` (no PPE keywords), constant in-file Q/H, `HYDROSTATIC_N_STEPS` (30k) fixed steps with `LISTING PRINTOUT PERIOD : 100` so the sortie carries enough `FLUX BOUNDARY` printouts to check when the boundary fluxes converge in a steady telemac3d run; results go to `r3d-hydrostatic.slf`/`r3d-2d-hydrostatic.slf`; (b) **`hotstart3d_hydrodyn.cas`** - the non-hydrostatic steady run with the same in-file prescribed Q (in) and H (out); (c) **`unsteady3d.cas`** - non-hydrostatic, hydrograph-driven via `unsteady.build_unsteady_3d_case(out_name=...)`: Q(t) inflow + outflow SL(t) from the **same** `inflow-hydrograph.liq` as `unsteady2d.cas` (skipped with a notice unless `boundaries.inflow` is a varying series). `--run [hydrostatic|hydrodyn|unsteady]` launches one of them streaming (default: hydrostatic). All three (and every `build_3d_cas` product) emit `PRINTING CUMULATED FLOWRATES : YES` - a valid TELEMAC-3D keyword - so `axqua.sortie` can read the fluxes. Every case is **hotstarted from the 2D run**. The default hotstart is the **TELEMAC v9+ true 2D→3D continuation** (`FILE FOR 2D CONTINUATION` + `FILE FOR 2D CONTINUATION FORMAT : 'SERAFIN'` + `INITIAL TIME SET TO ZERO`), which lifts the 3D free surface + horizontal velocities from the final 2D state (in v9 this keyword alone triggers the continuation - the old `2D CONTINUATION` flag is gone). Because a thin/supercritical 2D inflow can make `telemac3d` abort with `DEBIMP_3D: PROBLEM ON BOUNDARY` on the prescribed-Q inflow, a cold-start `INITIAL CONDITIONS : 'CONSTANT DEPTH'` seed (median wetted 2D depth, which over-wets the inflow) is emitted **commented-out as a fallback** - and is the `build_3d_cas(hotstart="constant_depth")` mode the vertical convergence study uses so every per-layer run reaches steady state. `INITIAL GUESS FOR DEPTH : 1` and a `MINIMAL VALUE FOR DEPTH` floor (guards the sigma transform against dry columns) back both modes. TELEMAC-3D has **no Delft3D-style constant-dz z-layers**, only **sigma planes** (`NUMBER OF HORIZONTAL LEVELS` + `MESH TRANSFORMATION : 1`), so `infer_vertical_layers` sizes the level count from the 2D depth/cell size to target `dz ~ dx/2` while keeping `dz >= dx/4` (the "max 4× finer" rule). The turbulence model reuses the 2D `select_turbulence_model` quality check, mapped onto the 3D numbering (k-epsilon 3, Smagorinski 4, **Spalart-Allmaras 5** - 3D numbers S-A 5, not the 2D 6) with the vertical model paired per TELEMAC's rules (S-A must be 5 in both directions; k-epsilon→3; Smagorinski→vertical mixing length 2). TELEMAC-3D cannot run finite volumes (always FE), has no zonal `FRICTION DATA FILE` (a single representative `LAW OF BOTTOM FRICTION` + `FRICTION COEFFICIENT FOR THE BOTTOM` is written - **not** spatially equivalent to the 2D zonal friction), and has **no `DESIRED COURANT NUMBER`** keyword - so the fixed `TIME STEP` is sized for a target Courant of 0.6 from the 2D velocity and the cell sizes (the 2D steady run's `desired_courant` default is the safer 0.30, since its dry start is less stable than this hotstarted 3D run; raise either toward ~0.9 to march to steady state in fewer steps). It also has **no steady-state auto-stop** (the 2D `STOP IF A STEADY STATE IS REACHED` keyword does not exist in TELEMAC-3D), so the 3D run always marches the full `NUMBER OF TIME STEPS`. For wetting/drying robustness the 3D numerics use **MURD PSI advection with the locally-implicit option** for velocity *and* k-epsilon (`SCHEME FOR ADVECTION ... : 5` + `SCHEME OPTION ... : 4` - robust on tidal flats without the sub-iteration blow-up the default MURD option hits), **mass-lumping** on depth+velocity with `TREATMENT OF NEGATIVE DEPTHS : 2`, segment-wise `MATRIX STORAGE : 3`, and `ACCURACY FOR PPE : 1.E-4` (the v8.1+ default; tighter just wastes iterations on spin-up). The boundary conditions reuse the 2D `PRESCRIBED FLOWRATES`/`ELEVATIONS`/`VELOCITY PROFILES` plus a logarithmic `VELOCITY VERTICAL PROFILES`. `add3d.py --run` launches `telemac3d.py` via `run_solver_streaming(..., solver="telemac3d", duration=dt*n_steps)` (live listing + progress bar; 3D has no DURATION keyword, so the bar spans the fixed step count).

**3D vertical-layer convergence (`vertical_convergence_3d.py`, `axqua/vertical_convergence.py`).** Choosing the number of vertical layers is a **separate discretization decision that the 2D mesh-convergence study never addresses** (step 2 only varies the horizontal cell size), so the vertical resolution `dz` needs **its own grid-independence study** - run after `add3d.py`. It is the 3D analogue of the 2D study: where the 2D study varies the horizontal cell size, this varies the **number of sigma layers** (`NUMBER OF HORIZONTAL LEVELS`) on the *same* (already 2D-converged) horizontal mesh. `run_vertical_convergence` runs the hotstarted 3D case once per layer count (a ladder around the inferred baseline, or explicit `counts=`), each in its own `postprocessing/vertical-convergence/L<n>/` folder with the geometry/`.cli` symlinked in (no mesh rebuild) and `build_3d_cas(..., n_levels=<n>)` forcing the level count (the time step adapts to the resulting `dz`), samples depth-averaged water depth + scalar velocity at the probe points from the run's `2D RESULT FILE`, and reports the relative change / observed order / GCI keyed on the layer thickness `dz` (reusing `convergence`'s report maths; the report `recommendation()` picks the **fewest grid-independent layers**). The TELEMAC run is injectable (`simulate=`) for unit tests. The whole vertical study was verified end-to-end against the real `telemac3d` solver on `ering-revised`.

**Gain-lose reaches (`gain_lose` config block, `axqua/gainlose.py` + `watertable.py` + `fortran.py`).** A reach that loses flow into a porous body (a gravel bar, an alluvial patch) and regains it downstream. A 2D depth-averaged model has no subsurface, so the underflow is represented as an internal **withdrawal** where water infiltrates plus an **injection** where it resurfaces, generated into a `USER_RAIN` routine (`FORTRAN FILE` + `RAIN OR EVAPORATION : YES` + rate 0; TELEMAC compiles it per run). The routine is **depth-limited** - the withdrawal tapers to zero as a cell approaches `min_depth` and is additionally capped at half the water available above that floor per step, so a sink can *never* dry a cell (TELEMAC's own source terms have no such guard, which is what collapsed the CFL-adaptive time step in the isar-2025 T2/T3 rungs) - and **mass-exact**: whatever is withdrawn is reinjected in the same step, so no net sink appears in the boundary budget (a permanent sink S would make the steady budget read `|Q_in| - |Q_out| = S` and put a floor under the relative flux imbalance, so no `hotstart2d.cas` would ever be written). **Two independent choices:**
- **Where** (`faces`): **`water-table` (default)** derives both faces from the body's phreatic surface and needs *nothing drawn* - a node **loses** where it is wet and its free surface stands above the table, and **gains** where the table stands above the bed, evaluated inside the zone polygon buffered by `zone_buffer` (default one channel cell, so the losing face can reach the wetted channel beside a bar). The classification happens **at run time**, so the faces move with the stage rather than being frozen at build time. This is the default because it is genuinely fuzzy where percolation begins and ends. `faces: lines` instead pins the exchange to the `int-*` lines of `boundaries.liquid_boundaries`, each buffered to a strip - for a surveyed seepage face, or to reproduce a calibrated exchange (isar-2025 uses it).
- **How big** (`conductivity` or `discharge`): `conductivity` (kf) drives it by default via Green-Ampt's saturated limit `f = kf (h + Lz + hf) / Lz` at the local head, so the exchange **responds to water level** and kf is the calibration parameter; `discharge` overrides it with a measured total normalised over the losing face. Both work with either `faces` setting. **kf is exposed to HydroBayesCal as `f.HMP_KF`** (`targets.PARAMETER_CATALOG` → "POROUS ZONE kf (gain-lose)"): it is emitted as a run-time *assignment* rather than a `PARAMETER` declaration precisely so HBC's `f.` mechanism - which rewrites the line whose text left of `=`/`:` matches - can find it, and `calibration.emit_hbc_config` passes `fortran_file: user_rain.f`. Riverbed kf spans orders of magnitude (clean gravel 1e-2..1e-1, moderately colmated 1e-4..1e-3, silted 1e-7..1e-5), so calibrate rather than assume - values from Calver (2001), *Riverbed Permeabilities: Information from Pooled Data*, Ground Water 39(4):546-553, doi:10.1111/j.1745-6584.2001.tb02343.x.

**The water table** (`water_table: phreatic`, `axqua/watertable.py`) is the surface joining the two channel levels the body exchanges with - that *is* the water table of the through-flow, and its gradient is what drives the exchange. It is fitted as a **plane** (five numbers, so the Fortran needs no per-node array) from the `int-*` lines (`faces: lines`) or, with `faces: water-table`, from the **channel water surface at each end of the zone's centerline extent** - which is what makes drawn lines optional. `water_table_levels` pins them explicitly. Besides locating the faces it does two things: the **pre-wet seeds any ground below it**, so closed depressions *on* the bar start full (they can never fill otherwise - no surface flow reaches a hollow sitting above the channel, and `drainable_prewet` deliberately refuses to seed behind a rim), and the **patch drain** (`patch_drain`) tapers to zero *at the table* instead of at `min_depth`, so it clears standing water off the bar top but cannot empty a pool that cuts below the saturated zone. `water_table_depth` is the single place the clip-to-the-zone rule lives - extended across a reach the plane would stand above every bed lower than the bar (22 598 m² of it on isar-2025). `gainlose.derive_faces` / `estimate_exchange` report the faces and the discharge they imply **at build time**, before any solver run. On isar-2025 the polygon-derived route gives a 5.30 ‰ table and 391 m² losing / 208 m² gaining → 0.213 m³/s at kf=3e-4, against the 0.065 m³/s the drawn lines prescribe - i.e. in polygon mode kf must be calibrated, which is exactly why it is exposed. The block was called `percolation:` while the feature lived in the isar-2025 case; that spelling still loads (mapped `mode`→`enabled`, `losing_region`→`faces`) with a deprecation warning, and `cfg.percolation` remains an alias for `cfg.gain_lose`.

**Optional unsteady extension (`unsteady_run.py`, `axqua/unsteady.py`).** Turns the converged steady case into a **hydrograph-driven quasi-steady** run (a flood wave discretised as a sequence of steady discharges), **hotstarted from the steady result** `r2d.slf` (`PREVIOUS COMPUTATION FILE`, clock reset to zero) - so it runs strictly after step 1b. The flood wave `Q(t)` comes from **this case's** `boundaries.inflow` **time series** (a genuinely varying series; a constant Q is the steady case). Unlike the manual tutorial, aXqua **does not re-define the boundaries**: the generated `boundaries.cli` is reused unchanged (inflow `4 5 5`, outflow `5 4 4`), the inflow discharge is driven by the `LIQUID BOUNDARIES FILE` (Q(t) per inflow; SL(t) per prescribed-elevation outflow at the rating stage, else the fixed `prescribed_elevation`) and the downstream level by its prescribed elevation - **no** `5 5 5`→`4 5 5` find-replace, no separate `boundaries-unsteady.cli`, no `STAGE-DISCHARGE CURVES` keyword (that is the alternative route). The build serializes the FRONT2 liquid-boundary numbering to `liquid-boundaries.json` (via `boundary.dump_liquid_boundaries` in `pipeline.run`), so `unsteady.py` recovers the boundary order **without re-meshing**. `build_unsteady_case` writes `unsteady2d.cas` with quasi-steady numerics (`NUMBER OF CORRECTIONS OF DISTRIBUTIVE SCHEMES : 2`), a distinct `RESULTS FILE` (`r2d-unsteady.slf`, so it does not clobber its own hotstart input), and optional `CONTROL SECTIONS` (`write_control_sections` parses the `.cli`, grouping consecutive same-tag rows **by rank** into one section per open-boundary segment, endpoints = that run's first/last global node - so the run reports the flux across each boundary). `unsteady_run.py` has **in-script toggles**: `MODE_3D` (`build_unsteady_3d_case` drives the same hydrograph on the non-hydrostatic 3D mesh via `threed.build_3d_cas(unsteady=True, liquid_boundaries_file=..., duration=...)`, spanning the hydrograph by step count since 3D has no `DURATION`), and `GAIA_ENABLED` / `GAIA_BEDLOAD` / `GAIA_SUSPENDED` (fold into `morphodynamics`, adding `COUPLING WITH : 'GAIA'` + `GAIA STEERING FILE` + `COUPLING PERIOD FOR GAIA` to whichever run is built here - so **GAIA is coupled to both `unsteady2d.cas` and `unsteady3d.cas`** (and the steady case), sharing one generated GAIA `.cas`). Suspended sediment is carried as TELEMAC tracers by GAIA, needing no manual `NUMBER OF TRACERS`. `steering.write_gaia_cas` emits a **damocles-valid** GAIA steering file (verified against `gaia.dico`): it references the **same `GEOMETRY FILE` + `BOUNDARY CONDITIONS FILE`** as the coupled run (GAIA needs both even when coupled) and its results keyword is `RESULTS FILE` (**not** `GAIA RESULTS FILE`, which is not a GAIA keyword - fixed), plus `BED LOAD FOR ALL SANDS` / `SUSPENSION FOR ALL SANDS` and the bed-process capacities driven by the `morphodynamics` config block: `MORPHOLOGICAL FACTOR` (`morphological_factor`, bed-evolution acceleration over a hydrograph), `SLOPE EFFECT` + `FORMULA FOR SLOPE EFFECT` + `FRICTION ANGLE OF THE SEDIMENT` (`slope_effect`/`slope_formula`/`friction_angle`), `SECONDARY CURRENTS` + `SECONDARY CURRENTS ALPHA COEFFICIENT` (`secondary_currents`, spiral-flow bedload deviation in bends), `NUMBER OF LAYERS FOR INITIAL STRATIFICATION` + `ACTIVE LAYER THICKNESS` (`bed_layers`/`active_layer_thickness`), `PRESCRIBED SOLID DISCHARGES` (`prescribed_solid_discharges`, sediment supply per liquid boundary in FRONT2 order), `CLASSES TYPE OF SEDIMENT` (`sediment_type`), `MASS-BALANCE` and the GAIA `VARIABLES FOR GRAPHIC PRINTOUTS`. Pass `--run` to also launch the solver. The steering writers (`steering.write_cas`, `write_gaia_cas`, `threed.build_3d_cas`) are unit-tested without the solver (`tests/test_unsteady.py`).

**Optional OpenFOAM free-surface extension (`openfoam_preprocessing.py` / `openfoam_run.py`, `axqua/openfoam/`).** A **3D two-phase (VOF) `interFoam` case** built from the same config, the same geodata and the same converged `r2d.slf` as the TELEMAC case, into `<sim_dir>/openfoam/`. Entirely **additive**: a config with no `openfoam:` block gets the default `OpenFoam` dataclass and nothing in the TELEMAC path consults it. It exists because `simpleFoam` cannot represent a water surface with a gradient (so the air-water interface must be modelled) while the air phase itself is of no interest and is what usually wrecks these runs.

**The TELEMAC pre-run seeds it, automatically (`axqua/prerun.py`).** OpenFOAM is the expensive model in the chain and TELEMAC is cheap, so the surface is *approximately known* before `interFoam` starts. `prerun.ensure_seed(cfg)` returns the result to seed from, in order of preference: the case's own converged `r2d.slf` (`reuse`, the default - hours of fine-grid compute beat anything generated here); else a **dedicated coarse pre-run**, a deepcopy of the case at `pre_run.size_scale` x the cell size, pre-wetted and marched at `pre_run.courant` 0.6, built and run by `pipeline.run(dry_run=True)` into `<model_dir>/pre-run/` with its other products sent to a discarded scratch dir - the same shape as `convergence._level_simulator`, because that pattern is already proven; else nothing, when `pre_run.enabled` is false (`--no-pre-run`, or `PRE_RUN = False` in the case script), and the case builds cold under a flat lid. Measured on isar-2025: a x4 pre-run **builds and runs in 54 s** and yields a 3D mesh within 3% of the one the full production `r2d.slf` seeds (14,192 vs 14,632 cells, 81.9% vs 79.3% water at t=0). It **lives at the top level, not in the OpenFOAM backend**, because `tests/test_capabilities.py::test_openfoam_does_not_import_the_telemac_backend` reads the backend's source and fails on any reference to `axqua.solvers.telemac` - orchestration driving both belongs above both, next to `workflow.py`. A failed pre-run **warns and returns a cold seed** rather than losing the build; an unconverged one warns (`require: warn`) or raises (`error`), judged by reading the pre-run's own `.sortie` through `sortie.read_sortie` + `flux_convergence.relative_imbalance` against `hydrodynamics.flux_tolerance`. `pre_run.dimension: 3d` follows it with the hydrostatic `telemac3d` case and seeds a **vertical velocity profile** - but **only when the mesh can carry one, and it often cannot**. Verified end to end against the real solver, which changed four things. (a) The extension applies to a **reused** 2D result too; hanging it off the coarse-pre-run branch alone made `dimension: 3d` silently do nothing on every case that already had an `r2d.slf`, i.e. the normal case under `reuse: true`. (b) It runs in the folder **holding the seed** (`FILE FOR 2D CONTINUATION` names the result, so a pre-run subfolder is not the main model dir). (c) A **level gate** (`MIN_USEFUL_LEVELS` 3) refuses before launching the solver: TELEMAC-3D has only sigma planes and `infer_vertical_layers` refuses cells more than 4x taller than wide, so a **shallow reach meshed fine in plan has no room for an interior level** - isar-2025 is 0.26 m deep with 0.62 m cells and gets exactly **2 planes on the production mesh**, one layer, a depth-averaged answer at 3D cost. The gate returns in seconds with that reason instead of burning the run. (d) The seed run is made **robust rather than faithful** (`_make_3d_robust`): it cold-starts from `INITIAL CONDITIONS : 'CONSTANT DEPTH'` instead of the 2D continuation, because the continuation lifts a surface carrying many dry/near-dry columns onto the sigma mesh and TELEMAC-3D then diverges **on the very first solve** (`GRACJG ... RELATIVE PRECISION NaN` immediately after `DEPTH IS READ IN THE BINARY FILE`) - measured on the coarse pre-run mesh *and* on the fine production mesh with a converged 2D result and no user-fortran, so it is neither the coarsening nor the seed quality; and it **replaces a Spalart-Allmaras pick with k-epsilon**, since S-A maps to 3D model 5 which diverges in the velocity-diffusion solve on a wetting/drying bed unless a source-term patch is linked (NaN on two meshes with S-A, zero NaN with k-epsilon). Both are the right trade for a *seed*, which needs a plausible profile rather than agreement with the 2D surface - and the cold start is the same choice the vertical-convergence study already makes. A produced result is additionally checked **finite** before adoption (`_is_finite`): a diverged run can march to the end and write a file of NaN, and seeding `U` from that gives an OpenFOAM run that dies with no visible cause. **The NPLAN trap, found only by reading a real result:** TELEMAC-3D writes the plane count in **`IPARAM(7)`** (index 6) and leaves the dims record's fourth slot at **1** - so `read_slf` reading `dims[3]`, the intuitive place, reported every real 3D result as 2D (verified on `inn-kb08/r3dsteady_Q46.slf`: `iparam[6] = 5`, `dims[3] = 1`, NPOIN 1,103,870 = 5 x 220,774). The synthetic test fixture had set *both* fields, which hid it; it now writes the file the way TELEMAC does. Verified end to end on that result: 5 planes, `has_profile` true, and a genuine boundary layer at the deepest node (u 0.039 m/s at the bed to 0.124 m/s at the surface), which `initial_velocity` turns into a seed spanning 0.074-0.390 m/s where a 2D seed gives a uniform 0.251 m/s. **Verified end to end on 12 cores** (isar-2025, `pre_run.n_levels: 6` pinned past the gate deliberately, since the reach itself only supports 2): aXqua built the 3D case, launched `telemac3d`, the result passed the finite check and was adopted with its profile - and the OpenFOAM case built from it seeds `U` with a **mean 0.415 m/s bed-to-surface spread per column, against exactly 0.000 from the 2D seed**, which is the entire point of the mode. The mechanics: `core/selafin.read_slf` now returns `nplan` and, for a 3D file, cuts `x`/`y` back to the `npoin2` plan nodes and reshapes every variable to `(nplan, npoin2)` (a 2D file is untouched); `State2D._from_3d` keeps `u3d`/`v3d`/`z3d`, derives the depth-averaged `u`/`v` by **trapezoidal integration over the actual level elevations** (not the mean over levels - sigma layers are equal only where the depth is, so the plain mean over-weights the thin near-bed layers where the velocity is smallest, a one-sided error), and `sample_profile(xy, z)` interpolates linearly in z, **holding** the end levels rather than extrapolating a jet above the surface. `fields.initial_velocity` uses it when present.

**The seed is an approximation, and the build says where it might be wrong.** Under `openfoam.headroom_mode: auto` (default) the `freeboard` and `wet_margin` are **sized from the seed's own flow** instead of being constants: `State2D.headroom` = velocity head `p95(V)^2/2g` (what the water could convert at a stagnation point or the outside of a bend) + 0.25 x depth (for what a depth-averaged model cannot see at all - secondary currents, local deformation, standing waves), and `lateral_margin` = that rise / `bank_slope` (0.1), with the configured values as **floors, never caps** - so no existing case ever gets *less* room than it had. On isar (p95 0.90 m/s, 0.22 m deep) that derives 0.10 m and both stay at their 0.5 m / 5 m floors; a 3 m/s reach 1 m deep would get 0.71 m. Then, after the run, `report.surface_freedom` answers whether it mattered: two `surfaceFieldValue` monitors (`lidContact`, `wallContact`, `areaIntegrate` of `alpha.water` on the top and `banks` patches, read back by the same `read_monitors` machinery as the discharge) say whether the water ever reached the lid or the lateral wall - i.e. whether the answer was set by a **meshing decision** rather than by the hydraulics, which nothing else in the output reveals: the run converges, the discharge balances, the picture looks like a river. Judged as a **fraction of the patch's own area** (from the `# Area :` header), because a bare area means nothing across reach sizes and because the domain has to end somewhere - at the inflow and outflow the channel necessarily runs into that edge, so `WALL_CONTACT_TOLERANCE` is 2% and the lid's is 0.1%. Verified on a deliberately 8x-coarse isar run: lid 0.001% (dismissed as noise), wall 5.6% (flagged - at dx 2.4 m a 5 m margin is two cells). Under `mode: rigid-lid` it reports "prescribed by the 2D seed, not solved" instead, since there the surface never had freedom to lose.

**Meshing - extrude, don't snap (`openfoam/polymesh.py` + `openfoam/mesh.py`).** aXqua writes `constant/polyMesh` itself (as `selafin.py` writes SERAFIN), because a river bed is a **single-valued height field** z_b(x,y) and can therefore be *followed* rather than snapped to. snappyHexMesh's castellate-and-snap buys nothing on such a surface and costs the sliver/negative-volume repairs that make it painful. The mesh is a **structured (i,j,k) lattice warped onto the bed**: in plan a uniform Cartesian grid of spacing `cell_size`, optionally **rotated onto the reach's principal axis** (`align_to_flow`, PCA of `geodata.channel_centerline`; isar +32.9 deg), with columns outside the footprint absent, hole-filled and reduced to the largest 4-connected block; in the vertical `n_layers` sigma layers per column. Result: **all-hexahedral, conformal by construction** (levels are computed at the *plan vertices*, so neighbouring columns of different height share their corner points exactly - no merging, no hanging nodes) and **bed-fitted** (the bottom face of the lowest cell *is* the DEM, not a staircase). `polymesh.assemble` enforces the format contract - internal faces first in **upper-triangular** order, `owner < neighbour`, every face oriented owner→neighbour using the known cell centres - and `polymesh.validate` additionally checks **cell closure** (face area vectors summing to zero) before anything is written. Files are ASCII (written once, read once); the run's own output is `writeFormat binary`. Verified: `checkMesh` reports **Mesh OK, 1,579,074 hexahedra, one region, upper triangular ordering OK** on the isar case at 0.5 m / 14 layers.

**The lid is the fix for the air phase.** The lid is clamped `freeboard` (0.5 m) above the **2D free surface** instead of being a flat plane over the terrain, so most air cells simply never exist (isar: only 9.7% of cells start as water, and a flat lid would be far worse), the `atmosphere` patch stays close to the interface where `inletOutlet`/`totalPressure` behave, and the surface still has room to move. It is grey-**dilated** (`lid_dilation`, default **2** - 1 left a single 70.16 deg severely non-orthogonal face where the lid dipped over a shallow cell) then smoothed (`lid_smoothing`), so it is never *below* the surface it came from and has no dents that pinch the air into slivers. `domain: wetted` further trims the plan footprint to the 2D wetted extent buffered by `wet_margin` (isar: 28,198 m2 of the 66,000 m2 ROI).

**The other two air levers** are in `openfoam/dicts.py`: **`MULESCorr yes`** (semi-implicit MULES) removes the alpha equation's own Courant limit, so `maxCo`/`maxAlphaCo` run at ~0.9 instead of the tutorials' 0.2; and **`system/fvConstraints`** carries a **`limitVelocity`** constraint at `air_velocity_cap` (default 5x the reach's p95 water speed, isar 4.5 m/s). Water never reaches the cap; a runaway air jet does, and that is what collapses the time step. Also `momentumPredictor no` (buoyancy dominates) and `nNonOrthogonalCorrectors 2` (a bed-following mesh *is* non-orthogonal where the bed is steep).

**Cutting the air phase out entirely: `openfoam.mode: rigid-lid`.** The levers above *tame* the air; this removes it. The lid is placed **on** the 2D free surface as a `slip` wall, so the domain is water only and `alpha` is identically 1 - `interFoam` degenerates to a single-phase run while `p_rgh` and gravity stay intact (which is what keeps it a river rather than a duct). Consequences, all measured on isar-2025: no interface, so **no spin-up stage** (`stages()` returns one) and no interface Courant limit (`maxAlphaCo` 10, and the run reports `Interface Courant max: 0`); **`MULESCorr no`**, because an implicit correction to a field that is uniformly 1 is pure overhead - it cost **four fifths of the run time** (60 s of river in 88 s with it, 21 s without, same dt, same alpha to 8 significant figures); and the ~90% of cells that were air are simply absent. `openfoam.cell_size_factor` coarsens relative to the 2D channel size (one number, so a test run cannot drift away from the mesh being tested). Together, for 300 s of river on one core: `vof` at 0.5 m is 1,579,074 cells at dt 3.1e-3 s (~97,600 steps); `rigid-lid` at factor 5 is **14,632 cells at dt 3.7e-1 s - 832 steps, 91 s wall-clock** (factor 3: 36,164 cells, 60 s of river in 96 s). **What it gives up is the free surface**: it cannot move, so the mode cannot show a hydraulic jump, a standing wave or superelevation in a bend - it is the way to a trustworthy `vof` run, not a substitute. Two knobs are rigid-lid-only. `min_water_depth` (0.20 m) drops shallower columns, and **cannot be raised freely** - at 0.25 m the trim ate isar's inlet patches, whose inflow sections are themselves shallower than that. The layer count is then **fitted to it** (`build_mesh`): under a rigid lid `n_layers` spans the water alone (0.2-1.0 m), not water plus freeboard (0.7-1.8 m), so the count carried over from a two-phase case gives cells 3-4x thinner - past the bed roughness they are meaningless, and thin enough that the bed's variation within one plan cell folds them, which `checkMesh` rejects as incorrectly-oriented face pyramids. 14 layers over 0.20 m is reduced to 4 and the build says so. `auto_bed_layer` defaults **off** here for the same reason (48 bad face pyramids and 83.6 deg non-orthogonality with it on, 0 and 74.7 deg with it off). The cost estimate has its own rigid-lid model: carrying the two-phase one across (thinnest layer at the full water speed) predicted 0.019 s against a measured 0.369 s, because only the *vertical* component crosses a thin layer - so `estimate_time_step` sums `u/dx` and `u.S/dz` with `S` the mesh's own median bed slope (`case.terrain_slope`, isar ~8%), which lands within 25%.

**Two-stage run.** `system/stage1-spinup/` and `system/stage2-run/`; `dicts.activate` copies one into `system/`. The first moments after a hotstart are the least like the converged flow - the 2D state is depth-averaged, so at t=0 there is no vertical structure at all - so **stage 1** runs briefly (`spinup_time`) at `spinup_courant` 0.3 with **half** the interface compression (`Gauss interfaceCompression vanLeer 0.5`; in OF9 cAlpha lives in the *scheme*, so dropping compression entirely instead demands a legacy `cAlpha` fvSolution key and smears the surface through the whole spin-up) and upwinded momentum; **stage 2** restarts (`startFrom latestTime`) at `max_courant` 0.9 with full compression and `limitedLinearV 1`. `fvSchemes` also needs `wallDist { method meshWave; }` for kOmegaSST.

**Boundary conditions (OF9-verified against that install's source + the `waterChannel`/`weirOverflow` tutorials).** Inlet/outlet patches come from the **same `boundaries.liquid_boundaries` layer that drives the `.cli`** (`boundary.liquid_line_details`), one patch per line, so 2D and 3D take flow in and out at identical places and each line's `Target flow` gives its own Q (isar: `inlet-1` 1.6, `inlet-2` 0.8 m3/s). Inlet: `variableHeightFlowRateInletVelocity` + `variableHeightFlowRate` alpha - the inlet **stage is an outcome, not an input** (prescribing Q *and* a depth over-determines it). Outlet: the case's own `outflow_condition` becomes `prghPressure` with a hydrostatic `p` profile below the target level plus an `inletOutlet` alpha profile 1 below / 0 above - the direct analogue of TELEMAC's `PRESCRIBED ELEVATIONS` (isar: 815.347 m from the section rating at Q=2.4); `free` still selects the weirOverflow-style outfall. Bed/banks: `noSlip` + **`nutkRoughWallFunction` with per-face `Ks`** from the same `geodata.roughness_zones` that drives `FRIC_ID`/`.tbl`.

**Initial fields (`openfoam/fields.py`, `openfoam/hotstart.py`).** `alpha.water` is the **submerged fraction of each cell** below the 2D free surface (a one-cell-sharp interface, far better than `setFields` boxes); `U` is the 2D depth-averaged velocity in water, scaled by alpha, zero in air, deliberately **uniform over the depth** (the vertical structure is what the 3D run is *for*); `p_rgh` uniform 0; k/omega uniform from the reach's own depth and velocity. `State2D` samples the 2D result **nearest-node on a KD-tree, not P1 on the element table**: a SELAFIN merged from a parallel run is not a clean triangulation (isar: 4,393 coincident nodes and 66,759 zero-area triangles of 460,314, which makes matplotlib's `TrapezoidMapTriFinder` reject the mesh outright), and nearest-node costs nothing in accuracy because the 2D mesh is *finer* than the 3D lattice it seeds - `resolution_check` warns if that ever reverses.

**The honest limitation (`openfoam/quality.py`).** `nutkRoughWallFunction` needs the first cell **centre** above the roughness crests (`y1 > ks`, i.e. a bed layer ~`2 ks`), so `auto_bed_layer` pins the bed layer to **2x the wetted-median ks** (isar 0.10 m; the *wetted* median, because the dry floodplain's vegetation ks 0.5 m has no bearing on a wall function under water). Even so, on isar **41% of wetted bed faces** still have `y1 < ks` - the reach's roughness (ks 0.085-0.5 m) is a large fraction of its depth (median 0.22 m). OpenFOAM does **not** fail there: it clamps y+ to `e/E` and carries on, so the run completes and the near-bed velocity is simply not physical. Refining towards the bed makes it worse, not better. The report states the share per build; read such a result as bulk flow, not as a resolved bed boundary layer. `quality.py` also reproduces `checkMesh`'s **own** definitions exactly - `face_geometry` (triangle-fan centroids: a terrain-following quad is non-planar, so its centre is not the corner average), `cell_geometry` (pyramid decomposition), skewness normalised by the **face half-width** floored at `0.2|d|` (not by `|d|`, which understates it ~7x), aspect ratio as `max(component ratio, hydraulic ratio)` (the component form dominates on flat cells: 16.7 where the hydraulic form alone reads 3.1), and the mean non-orthogonality as `acos(mean(cos))`. Verified against `checkMesh` on the isar mesh to 3 significant figures (60.11 deg / 7.84 deg, skew 4.025, aspect 16.66, identical volumes). `MeshReport.usable` (structurally sound: no zero/negative volumes) is deliberately **weaker than `.ok`** (passes every checkMesh check): a mesh cut from a real DEM routinely carries a few marginal faces at survey steps and seams - isar has exactly one skew face in 4.9 million, which no lid smoothing moves because it comes from the bathymetry - and refusing to run on that would be refusing to model the terrain. `runtime.check_mesh` blocks only on its `_FATAL_CHECKS`.

**Running and reporting.** `OpenFoamRuntime` extends the new shared `env.ShellRuntime` (extracted from `TelemacRuntime`, behaviour unchanged) and sources `openfoam.bashrc` per command: `checkMesh`, `decomposePar` (**scotch**, since the wetted corridor is sinuous and a geometric split would hand some ranks empty space), `mpirun -np N interFoam -parallel`, `reconstructPar`. Output is **streamed** with an `OpenFoamProgress` bar sharing the new `progress.ProgressBar` with the TELEMAC renderer; it shows **`Co` and `dt`**, which are the diagnostic - a healthy run holds `dt` near the Courant target, a misbehaving air phase shows `dt` falling by orders of magnitude while the clock barely advances. `openfoam/report.py` reads the `surfaceFieldValue` monitors written into `controlDict` (`sum(phi)` **weighted by `alpha.water`**, so it is the water discharge, not water+air) into `discharge-convergence.csv`/`.png` and judges the relative inlet/outlet imbalance against the **same `hydrodynamics.flux_tolerance`** the 2D run is judged by, so 2D and 3D are held to one standard. CLI: `axqua openfoam <config> [--check] [--cell-size <m>] [--layers <n>]` (`--check` reports the cell count without building). Tests: `tests/test_openfoam.py` (no OpenFOAM, no solver).

The mesh-convergence study (`axqua/convergence.py`, step 2; `cases/example-Inn/mesh_convergence_study.py`, which creates and works in its own `axqua-case/mesh-convergence/` folder) runs the same steady sim on a **four-mesh r=1.3 ladder** (`ratio_levels`: one coarser x1.3, the configured baseline, two finer /1.3 and /1.3² - Celik et al. 2008 recommend a grid refinement factor **r >= 1.3**; closer-spaced grids like the old ±20% `percent_levels`, kept only for backward compat, drown the grid-to-grid differences in solver noise and degenerate the GCI denominator r^p−1) at constant discharge with TELEMAC's variable time step (per-mesh CFL dt), samples water depth + scalar velocity at the ground-truth probe points (`default_probes`), and judges convergence on the **GCI of the finest grid triplet** (observed p clamped to `THEORETICAL_ORDER` 2 for the GCI; an **asymptotic-range check** `GCI(med)/(r^p·GCI(fine)) ∈ 0.8..1.25` decides whether the GCI is trustworthy, else the finest successive relative change is the fallback - `ConvergenceReport.verdict_basis`) vs a tolerance (default **5%**, `DEFAULT_TOLERANCE`; Celik: 5-10% is engineering accuracy). Each level is built with **`mesh.size_scale`** (= level channel size / config `channel_size`), a global multiplier applied to *every* target edge length **including the per-zone `Max Edge Length (m)` gpkg values** - scaling only `channel_size`/`floodplain_size` does nothing when the gpkg carries that field (the bug that invalidated the first ering study: five "levels", one mesh). The study is **resumable** (each level folder gets a `level.json`; on re-run a prompt offers reusing completed levels, QoI re-extracted from their `r2d.slf`; size-mismatched levels re-run) and **extensible**: when not converged it offers up to `MAX_EXTRA_LEVELS` further /1.3 refinements one at a time, each prompt showing a **runtime estimate** (log-log fit of measured runtimes, theoretical t~dx⁻³ fallback) and the **mesh-validity check** of the candidate size; non-interactive sessions auto-resume and auto-stop (no hang). A refinement that **fails to mesh/run** (e.g. BAMG gives up even after its retries, or the solver diverges) is caught as the practical refinement limit: the extension stops and the report is written from the levels already completed, instead of crashing the study. **Auto-refinement mode** (`run_mesh_convergence(auto_extend=True)`, exposed by the per-case `mesh_convergence_study.py` as `python .../mesh_convergence_study.py mode='auto-refinement'`) auto-approves the resume prompt and every extension (no prompts, interactive or batch) so the study marches finer one grid at a time until it converges, exhausts `AUTO_MAX_EXTRA_LEVELS` (default 8, vs. the interactive `MAX_EXTRA_LEVELS` 3), or a level fails. Every level's report row carries the `axqua/mesh_validity.py` checks: shear velocity from the fully-rough log law, wall **y+** (O(10⁴) in rivers, always passes - reported as standard), roughness Reynolds **ks+** (>=70 fully rough for the Nikuradse law), **dx vs ks** (dx < channel ks = roughness double-counting risk; fires first under refinement), and **turbulence-model consistency** (`steering.turbulence_pick_for_dx` vs the pinned baseline model). Every per-level build is **pre-wetted** (`INITIAL_DEPTH`, default 0.5 m -> `initialization.prewet_depth`): the channel mesh-zone nodes are hotstarted with that water depth so the solver need not advance the wetting front from a dry bed (see "Pre-wetting" below). `ConvergenceReport.to_xlsx()` writes a **styled .xlsx** (openpyxl) to `mesh-convergence/` (incl. the validity rows) and `recommendation()` picks the **coarsest grid-independent cell size** (convergence vs. compute-time tradeoff, with the runtime speed-up vs. the finest; under a GCI verdict with no rel-change-adequate level it recommends the medium grid of the converged triplet). The TELEMAC run is injectable (`simulate=`) so the report maths/xlsx are unit-tested without the solver (`tests/test_convergence.py`, `tests/test_mesh_validity.py`). Results SELAFINs are read with the minimal `selafin.read_slf` (the writer's counterpart; single/double precision, multi-frame, returns the last frame); `_geom_stats` drops the zero-length edges that merged parallel results carry at subdomain interfaces (else min-edge/dt report as 0/NaN).

A build needs a **ROI boundary polygon** (`geodata.boundary`, a closed polygon/polyline in EPSG:25832; the Inn example uses `cases/example-Inn/user-sources/geodata/roi-kb15.gpkg`) and `boundaries.liquid_boundaries` (both set in the Inn config). The steady **inflow Q comes from this case's `boundaries.prescribed_flowrate`** (m³/s) - the shared `axqua.prepare_steady_inputs` helper (used by `preprocessing.py` and the mesh-convergence script) reads it from the config rather than a value hard-coded in any script, so each case uses its own discharge. A constant-Q `boundaries.inflow` series is then **auto-synthesised** at that discharge when missing (`boundaries.inflow` itself is optional - only a *varying* series triggers the unsteady case), and the outflow rating `boundaries.stage_discharge` is synthesised from a normal-flow curve when the `stage_discharge` outflow condition is active and none is given (the default `outflow_condition: elevation` needs no rating, just `boundaries.prescribed_elevation`), so the only machine-specific thing to set for a build is `telemac.pysource`.

### OpenFOAM Bayesian calibration (`axqua/solvers/openfoam/calibration.py` + `axqua/hbc.py`)

The OpenFOAM half of the HydroBayesCal integration; `axqua/bayescal.py` is now the **TELEMAC adapter** and `axqua/hbc.py` the solver-agnostic plumbing both share (`require_hbc`, `stage_driver`, `launch_driver`, `solver_running`, `solver_environment`). They are **not** one parameterised emitter: the two HBC schemas differ in block names (`simulation` vs `hydrodynamic_simulation`), block membership (`n_cpus` moves into `sampling`), an extra `interfoam` block, and what `case_template_dir` *means* (referenced in place vs **copied per run**).

What it calibrates: **`ks` + the k-epsilon coefficients** against **`U_x, U_y, U_z` (+ `TKE`)** at the survey verticals - the vertical structure an ADV actually measures and that a depth-averaged 2D model cannot be calibrated against at all. `calibration._resolve_quantity` gained the OpenFOAM names (`SCALAR VELOCITY` and `U_MAG` now share `_scalar_velocity_with_error`, so the error propagation cannot drift).

**The campaign runs coarse and under a rigid lid** (`campaign_config` deep-copies the config so the production case is untouched): ~90% of a VOF case's cells are air and a surrogate needs tens of runs, and rigid-lid has exactly **one** stage, so the copied template is correct straight out of `build_case`. The trade is real and is why `openfoam_verify_posterior.py` is part of the workflow, not an extra: under a rigid lid the surface is *prescribed*, so a roughness error that would have shown as a surface-slope error is absorbed into the velocity field. `apply_posterior` refuses a value sitting within 5% of its prior bound.

**`ks` is ONE GLOBAL VALUE** (the binding has no per-zone roughness), so the OpenFOAM posterior is **not** comparable with the zoned `zone<N>` posterior of the 2D calibration.

**Both calibrations share one `calibration.parameters` list and each filters to its own** - `calibration.telemac_parameters` drops `ks`/`Cmu`, `openfoam_parameters` drops the zones and `.cas` keywords, each warning. Without that, an OpenFOAM `ks` emitted into `config_Telemac.py` has HBC rewriting a nonexistent `.cas` keyword for a whole campaign.

**Guards that fire before the campaign starts** (`_assert_template`), each replacing a failure that otherwise surfaces hours later: the bed `Ks` must be **uniform** (aXqua writes a per-face list from `roughness_zones`, and HBC rewrites one `^\s*Ks\s+` line without skipping a multi-line list -> orphaned tokens, unparseable `0/nut`; hence `build_case(uniform_bed_ks=True)`); `constant/momentumTransport` must carry a `kEpsilonCoeffs` line per calibrated coefficient (OpenFOAM silently falls back to built-ins for an absent one, so the perturbation would be an unreported no-op - hence `dicts.momentum_transport` now emits the block, and `OpenFoam.kepsilon_*` exist as config fields); plus write-count, `startFrom`, `decomposeParDict` and stray-time-directory checks. **Always run `--smoke` first** (3 runs x 30 s).

### Ground-truth & calibration data (`cases/example-Inn/user-sources/ground-truth/`)

Field measurements that become **calibration targets** for HydroBayesCal, ingested by `ground_truth.py`. The canonical input is the tidy multi-tab table (below); it is authored by the user (`ground_truth.measurements`), **compiled by aXqua** from raw sources declared in `ground_truth.sources` (a list of `{category, kind, values, positions, join_key}`), or - the recommended, consistent route - compiled from the **calibration-target template** (`axqua targets <config>` → `user-sources/ground-truth/calibration-target-data.xlsx`, referenced under `ground_truth.targets` with per-tab position layers `hydraulics_positions`/`sediment_positions`; `src/axqua/targets.py`, tests in `tests/test_targets.py`). The template's rows are keyed by **unique IDs** joining the point gpkg/shp layers (any CRS, reprojected on ingest; explicit x/y win); its `hydraulics` tab carries u_x/u_y/u_z + fluctuations u_x'/u_y'/u_z' with auto-derived U_h/U_h'/TKE (live Excel formulas, recomputed on ingest → tidy `u_mag`/`u_mag_std`/`tke`), water depth and bottom elevation - and is populated from SonTek FlowTracker2 exports by `src/axqua/flowtracker.py` (`read_flowtracker`/`fill_template_hydraulics`, tests in `tests/test_flowtracker.py`), auto-detecting the three real layouts (`.ft.sum`, TKE-stats, multi-sheet `FT_TKE_Summary`) keyed by each point's own ID; **the fluctuations u' are the sample standard deviation (`u std`/`Std Dev v'(x)`/σ), NOT the `VxErr` columns** (`VxErr` is the standard error of the mean ≈ std/√Npts) - where only a plain `.ft.sum` (VxErr + Npts, no std-dev) is given, u' is reconstructed as `VxErr·√Npts`; `write_target_template` drops a co-located runnable `extract_flowtracker.py` next to the xlsx that calls `fill_template_hydraulics`; its `morphodynamics` tab carries d16..d90 [mm → m] + fine fraction < 1 mm and auto-samples the **DoD raster into a per-point `dz` column** on ingest (the DoD→targets adapter); its `parameters` tab is a drop-down over `targets.PARAMETER_CATALOG` (verified TELEMAC-2D/3D/GAIA keywords: friction zones prefilled with current ks, CLASSES SHIELDS PARAMETERS, MINIMUM VALUE OF DEPTH, VELOCITY DIFFUSIVITY, secondary-currents coefficients, GAIA transport knobs, ...) with min/max test ranges + tips, ingested by `targets.read_target_parameters` and merged over `calibration.parameters` in `emit_hbc_config` (template wins; `calibration.merged_parameters`). The **hydraulics/FlowTracker path is also implemented** (`kind: flowtracker` joins `.ft.sum` values to a DGPS position layer; `kind: points` reads a layer that already carries quantities). **Still to build:** the sediment/GSD adapter into GAIA `sediment_classes` (the GSD values now land in the tidy `morphodynamics` tab but are not yet folded into the GAIA `.cas`).

- Measurement **positions** are point shapefiles under `cases/example-Inn/user-sources/geodata/` - and are in **different CRSs than the project's 25832, so they must be reprojected on ingest**:
  - `geodata/flowtracker2/dgps-flowtracker-day{1,2}_utm33.shp` - EPSG:**25833** (UTM 33N). Columns `ID, E_25833, N_25833, WaterDepth, z` (z = bed elevation). 15 points (day1) / 30 (day2).
  - `geodata/sediment/MultiPAC-Mar2020-KB15.shp` - EPSG:**32632** (WGS84/UTM 32N). `name` = Surface/Subsurface. NB its `x`/`y` *attribute* columns are swapped vs the geometry - trust the geometry.
- Measured **values** live under `cases/example-Inn/user-sources/ground-truth/`:
  - **Hydraulics - `hydraulics/FlowTracker2-KB15-day{1,2}.xlsx`**: SonTek FlowTracker2 `.ft.sum` exports for KB15. One sheet; row 0 = metadata (total `DISCHARGE` [CMS], reference gauge), row 1 = headers, row 2 = units, rows 3+ = one vertical each (joins 1:1 by `ID` to the DGPS shp). Key columns: `MeasD`/`FinalD` depth [m]; `VelX/VelY/VelZ` [m/s] (+ `VxErr/VyErr/VzErr`) → velocity components / scalar velocity.
  - **Sediment - `sediment/GSDs-Uni-Stuttgart.xlsx`**: surface & subsurface grain-size distributions (cumulative + fractional) with d65/d84; feeds GAIA `sediment_classes`.

**Target tidy model (generic, source-agnostic):** a multi-tab table - one tab per category (`hydraulics`, `sediment`, …), first 3 columns `x, y, z` (in the project CRS 25832), then quantity columns (FlowTracker hydraulics → `u, v, w, u', v', w', h`). FlowTracker is only one possible source; many ground-truth sources are conceivable, so the reader stays generic and per-source adapters feed it.

**Topographic change**: the DEM-of-Difference (`dem.dem_of_difference`, dem-2020 vs DEM-2025-20cm) is the bed-change ground truth for the GAIA / topographic-change calibration. It is produced in pre-processing when `dem_of_difference.enabled` (the `inn-2020-25` case enables it, 2020→2025), clipped to the ROI and thresholded by a **minimum level of detection** (propagated survey uncertainty `t·√(u_i²+u_t²)` or an explicit `min_lod`; sub-LoD change masked/zeroed) - see stage 1 above and the `dem_of_difference` config block. The DoD raster is **not yet** turned into per-point HydroBayesCal targets (the remaining adapter).

**xlsx gotcha:** these *FlowTracker/GSD* files break `openpyxl`'s style parser (`PatternFill ... unexpected keyword 'extLst'`), so `pandas.read_excel` fails on them on every available env. Read them by unzipping the workbook and parsing `xl/worksheets/sheet1.xml` + `xl/sharedStrings.xml` directly (the `.ft.sum` layout is stable), or with a defensive openpyxl wrapper - don't assume `read_excel` works on these inputs. (`openpyxl` itself **is** in `axqua-env` - `convergence.ConvergenceReport.to_xlsx` uses it to *write* the styled convergence report fine; the issue is only *reading* those specific styled inputs.)
