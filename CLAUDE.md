# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A TELEMAC hydro-morphodynamic model of a reach of the **Inn river in Bavaria, Germany**. The goal is a 2D depth-averaged hydraulic + sediment-transport simulation (TELEMAC-2D coupled with GAIA), set up automatically and calibrated with quantified uncertainty via [HydroBayesCal](https://github.com/Ecohydraulics/hydrobayescal).

**Overarching aim:** largely automate *both* sides of the workflow around HydroBayesCal - **pre-processing** (geodata → ready TELEMAC case) and **post-processing** (field **ground-truth** → calibration targets + result extraction). Pre-processing (stages 1–5) is built for the 2D hydraulic path; the **post-processing / ground-truth ingestion is the active frontier** (turning FlowTracker velocity/depth, grain-size distributions, and DEM-of-Difference topographic change into the calibration-points CSV and GAIA inputs HydroBayesCal consumes). See "Ground-truth & calibration data" below.

The tracked repository is the **`axqua` package** (`src/axqua/`) plus a data-free **`cases/case-template/`** scaffold (config + the workflow scripts `preprocessing.py` / `initial_run.py` / `mesh_convergence_study.py` / `run_Bayes_cal.py` and the multi-discharge variant `run_Bayes_cal_multiflow.py`, the optional 3D extension `add3d.py` / `vertical_convergence_3d.py`, and the optional unsteady extension `unsteady_run.py` + `USAGE.info` + `user-sources/README.md`, the starting point for a new case) and the worked example case under `cases/example-Inn/` (its `case-config.yml`, `preprocessing.py`, `initial_run.py`, `mesh_convergence_study.py`, `add3d.py`, `vertical_convergence_3d.py`, `run_Bayes_cal.py`). Each case lives in `cases/<name>/` and keeps only those tracked files; the real Inn **input data** (DEMs, orthos, zone GeoPackages, gauge data, ground truth) is large (~5 GB) and lives in `cases/example-Inn/user-sources/` for co-development only, while produced artifacts land in `cases/example-Inn/axqua-case/`, split by workflow phase: `preprocessing/` (DEM clips, meshes, ground-truth table), `simulation/` (the TELEMAC case build + results, incl. the 3D `<case>3d.cas`), `postprocessing/` (general post-processing, plus `mesh-convergence/` grid-independence and `vertical-convergence/` 3D layer studies), `calibration-validation/` (HydroBayesCal artifacts). Each phase's script writes its outputs and its `axqua.log` into its own subfolder. Both `user-sources/` and `axqua-case/` are **gitignored** (`.gitignore` ignores `cases/*/user-sources/` and `cases/*/axqua-case/`, plus a safety net of binary/geo extensions `*.tif/*.gpkg/*.shp/*.xlsx/*.slf/*.log/...`); a CI workflow (`.github/workflows/file-size-limit.yml`) additionally fails any push/PR with a tracked file over 20 MB. Don't assume the data files are present in a fresh checkout. See `README.md` for the workflow and `cases/example-Inn/case-config.yml` for the case config (a commented template; all paths resolve relative to the config file's directory).

## The `axqua` workflow

`axqua cases/example-Inn/case-config.yml` runs a 5-stage pipeline (`src/axqua/pipeline.py`):

1. `dem.py` - reproject + clip the initial (and optional target) DEM to the ROI boundary. When `dem_of_difference.enabled` (or `morphodynamics.enabled`), also computes the **DEM-of-Difference** (`dem.dem_of_difference`, `dem_target - dem_initial` on the ROI-clipped initial grid) thresholded by a **minimum level of detection** (`dem.resolve_lod`): an explicit `dem_of_difference.min_lod`, else the propagated survey uncertainty `t·√(uncertainty_initial² + uncertainty_target²)` (`dem.propagated_lod`, `t` from `confidence_level`); sub-LoD cells are masked to nodata (`mask_below_lod`) or zeroed, and the net/erosion/deposition volumes are logged. A precomputed `geodata.dem_of_difference` short-circuits the computation.
2. `mesh.py` + `selafin.py` - gmsh triangular mesh; DEM interpolated onto nodes; geometry written as SELAFIN with a `FRIC_ID` per-node variable (so no separate ZONES FILE is needed). The geometry is written in **double precision** (SERAFIND); single precision collapses sub-metre cells on UTM coordinates (see `selafin.py` design point). `build_mesh` prunes gmsh's geometry/1D-only nodes to triangle-referenced nodes (no orphans/duplicates), enforces consistent CCW winding, then runs `mesh_quality.assess_quality` (logged via `log_report`, stored on `Mesh.quality`). The mesh boundary is walked to build IPOBO, which **must** stay consistent with the `.cli` row order. **Two meshing strategies** (auto-selected): *anisotropic* (when `geodata.mesh_zones` + `geodata.channel_centerline` are set) types each mesh-zone polygon `channel`/`floodplain`/`refinement` (by `Zone Name` substring) and sizes it by its own `Max Edge Length (m)` field - channel cells elongated along the centerline, floodplain/refinement near-equilateral - via a metric-tensor background view + gmsh **BAMG** (`Mesh.Algorithm=7`); *isotropic fallback* uses `default_size`/`breakline_size`/`region_sizes` distance fields. See "Meshing" below.
3. `boundary.py` - classify contour nodes against the liquid-boundary lines and write the `.cli`. The lines come from `boundaries.liquid_boundaries` (a line layer whose `Type (inflow/outflow)` field - note the Inn file's typo `Type (inflow/outlfow)`, still detected - tags each line `inflow`/`outflow`; several of each allowed) and must coincide with the mesh-zone outer bounds. Codes: solid wall `2 2 2` (every non-liquid outer node), inflow `4 5 5` (prescribed Q, depth free - `LIHBOR` must be 4 not 5, else the inflow depth is forced to the inflow's PRESCRIBED ELEVATIONS slot of 0 and TELEMAC's DEBIMP aborts on a dry inflow), outflow `5 4 4` prescribed-elevation (the default `boundaries.outflow_condition: elevation`, a fixed WSE from `boundaries.prescribed_elevation`; or `stage_discharge` for a WSE from the rating curve at the simulated Q) or `4 4 4` free/Neumann (`outflow_condition: free`, needs no WSE). Matching tolerance is tied to the local edge length (anisotropic: ~2×`floodplain_size`). If total inflow- vs outflow-node counts differ by >10%, a stability-risk warning is logged.
4. `steering.py` - friction `.tbl` (one row per friction zone: `<id> <LAW> <coef> NULL`, ends with `END`; comments only on `*` lines - rows come from `friction.zones`/MATID or, failing that, the roughness table as `<Zone ID> NIKU <ks> NULL`) and the Telemac2d `.cas`; GAIA `.cas` when enabled. The **default solver is the classic finite-element kernel** (`hydrodynamics.finite_volumes: false`); set it true for the HLLC finite-volume kernel (robust on transcritical wetting/drying but constant-viscosity only). The **turbulence model is auto-selected** (`hydrodynamics.turbulence_model: auto`) by `steering.select_turbulence_model(cfg, mesh)` from the channel cell size relative to the turbulence length scale (the flow depth) and the velocity guess `initial_velocity_guess` (U≈1 m/s): **Smagorinski LES (4)** when the mesh resolves ≥80% of the TKE (`dx/L ≤ 0.2^1.5`, ~11+ cells/L - the LES validity gate), **k-epsilon (3)** at moderate resolution (≥~4 cells/L), **Spalart-Allmaras (6)** on coarse meshes; an explicit int/name overrides, and finite volumes force model 1. The **initial run is always steady** (`steady2d.cas`). The FE numerics are written **compute-stable by default** to keep the wetting/drying steady march from exploding: `time_step` is only a conservative CFL **start** step (0.25 s) while `desired_courant` (0.30) drives the adaptive marching step, `IMPLICITATION FOR DEPTH/VELOCITY` 0.80 (config `implicitation`), `FREE SURFACE GRADIENT COMPATIBILITY` 0.9, `DISCRETIZATIONS IN SPACE : 11;11` (linear FE, required by the distributive advection scheme 14), `NUMBER OF SUB-ITERATIONS FOR NON-LINEARITIES`/`MAXIMUM NUMBER OF ITERATIONS FOR ADVECTION SCHEMES`, `H CLIPPING : NO`, and a raised k-epsilon solve budget (`MAXIMUM NUMBER OF ITERATIONS FOR K AND EPSILON`, config `max_keps_iterations`). The graphic printout is `'U,V,S,B,H,M,Q,F'` plus `K,E` (TKE + dissipation) **for the k-epsilon model (3)**. **Time bound:** with the default `variable_timestep` the run is capped by `DURATION` (the explicit `hydrodynamics.duration` in seconds, else the `n_time_steps × time_step` fallback - so a small CFL start step no longer shrinks the simulated time), **not** `NUMBER OF TIME STEPS` - the latter does **not** terminate a variable-dt run (the CFL-driven dt is unknown a priori), so it would otherwise be unbounded. Convergence is judged by the **boundary-flux balance** (`initial_run.py` → `axqua.flux_convergence`), not by the solver. **The steady-state auto-stop is OFF by default** (`hydrodynamics.stop_if_steady: false`) and is hard-suppressed whenever `variable_timestep` is on: TELEMAC's `steady.f` stops when the change between **two consecutive time steps** falls below `STOP CRITERIA`, but that is an **absolute per-step** change (order **H ; (U,V) ; tracers** in `steady.f`; the dico's English help listing (U,V) first is wrong), and with the tiny CFL dt it false-fires during a slow transient (e.g. a low-Q reach still filling from a dry start) **long before the fluxes balance** - the run halts far from steady state (the symptom: it stops with inflow ≠ outflow). It is emitted only for a steady **fixed-step** run (`variable_timestep: false`, where a per-step change is meaningful), never for the unsteady run, and **TELEMAC-3D has no equivalent keyword**. When `boundaries.inflow` carries a *varying* hydrograph, `pipeline.run` additionally writes `unsteady2d.cas` (DURATION from the series) plus a TELEMAC liquid-boundaries file (`inflow-hydrograph.liq`, `Q(t)` per inflow / `SL(t)` per prescribed-elevation outflow via `steering.write_liquid_boundaries`). The steady inflow Q comes from `boundaries.prescribed_flowrate` (the optional `boundaries.inflow` series, read by `hydraulics.py`, is only for a varying hydrograph / unsteady case). The outflow water-surface elevation is needed for the prescribed-elevation conditions: the default `boundaries.outflow_condition: elevation` uses `boundaries.prescribed_elevation`, while `stage_discharge` interpolates `boundaries.stage_discharge` (a Q-h CSV; one pair suffices for steady) at the simulated Q; `free` prescribes nothing. When no measured rating curve exists, `axqua.rating.generate_stage_discharge` (CLI: `axqua rating`) synthesizes one from a Manning `n`/Strickler `Kst` and a trapezoidal channel geometry by inverting Manning's normal-flow equation; `rating.synthesize_outflow_rating(cfg, Q)` derives the geometry from the case data (width = outflow liquid-boundary line length, bed = DEM thalweg along it, slope = reach slope from the DEM along the centerline, roughness = `friction.boundary_*`) and `cases/example-Inn/preprocessing.py` (and the convergence-study script) call it to auto-generate `boundaries.stage_discharge` when missing. The lateral-boundary friction keywords (`LAW OF FRICTION ON LATERAL BOUNDARIES` / `ROUGHNESS COEFFICIENT OF BOUNDARIES`) come from `friction.boundary_law` / `boundary_coefficient` (Inn: Strickler 38).
5. `ground_truth.py` + `calibration.py` - compile the configured `ground_truth.sources` into the **tidy multi-tab table** (`ground_truth.compile_ground_truth`, written to `preprocessing_dir/ground-truth.xlsx` unless `ground_truth.measurements` overrides), then turn it into `measurements-calibration.csv` and the HydroBayesCal `config_Telemac.py` (both in `calibration_dir` = `calibration-validation/`).

`pipeline.run()` returns an `Artifacts` dataclass listing every produced path; `cli.py` logs these. The package's public API (`axqua/__init__.py`) exports `Config`, `load_config`, `clip_to_roi`, `clip_dem_to_roi`, the DoD helpers `dem_of_difference` / `propagated_lod` / `resolve_lod`, `compile_ground_truth`, `read_tidy`, the mesh helpers `build_mesh` / `channel_node_mask` / `interpolate_elevations` / `interpolate_roughness` / `write_mesh` / `assess_quality`, the rating-curve helpers `generate_stage_discharge` / `normal_depth` / `stage_for_discharge` / `synthesize_outflow_rating`, the wetted-extent diagnostics `wetting_report` / `outlet_profile` (`axqua/wetting.py`), the water-table helpers `fit_phreatic_plane` / `water_table_depth` / `patch_node_mask` / `PhreaticPlane` (`axqua/watertable.py`), the turbulence helpers `select_turbulence_model` / `eddy_viscosity_estimate`, the TELEMAC-3D helpers `build_3d_cas` / `infer_vertical_layers` / `select_3d_turbulence` / `run_vertical_convergence` / `layer_levels`, the mesh-convergence helpers `run_mesh_convergence` / `percent_levels`, the shared per-case workflow helpers `prepare_steady_inputs` / `resolve_discharge` / `synthesize_constant_inflow` / `synthesize_rating_if_missing` / `format_flux_convergence` / `report_wetting` / `report_sections` / `mesh_from_geometry` / `water_table_mask` / `run_solver_streaming` / `expected_duration` (`axqua/workflow.py` - the logic the per-case `preprocessing.py` / `initial_run.py` / `mesh_convergence_study.py` scripts share, so they stay thin), the live solver-progress renderer `SolverProgress` (`axqua/progress.py`), and the logging helpers `setup_logging` / `log_step` / `logging_to`. `mesh.build_mesh(cfg)` (no DEM) yields a bare mesh; `interpolate_elevations(mesh, dem, decimals=4)` fills the bottom from a raster (rounded); `write_mesh(mesh, path)` writes a geometry SELAFIN. These low-level helpers let you build a mesh programmatically; the worked example's `preprocessing.py` instead drives the full `pipeline.run` build (writing `geometry.slf` etc. into `simulation/`; see the workflow below).

### Meshing (stage 2)

The mesher is **gmsh**, chosen over the SALOME/Q4TS route (which the working Inn model historically used) because gmsh is pip-installable, fully headless/scriptable, and supports the anisotropic meshing needed here - whereas Q4TS runs inside SALOME's GUI/SMESH stack and is heavyweight/version-sensitive to automate. SALOME lives at `/home/modelling/telemac-v911/salome/` if ever needed.

- **Anisotropic, flow-aligned channel** (the requirement): channel triangles are *elongated along the channel centerline*, floodplain triangles near-equilateral, with a smooth transition. Implemented exactly like gmsh tutorial **t17**: build a coarse background triangulation (a Delaunay grid over the ROI bbox, node-budget-capped ~40k so any domain fits in memory), assign each background node a **3×3 metric tensor** (eigenvalue = 1/h²; anisotropic `1/(channel_size·anisotropy)²` along the local centerline tangent and `1/channel_size²` across, inside `channel` zones; isotropic `1/floodplain_size²` elsewhere), push it as a `TT` list **PostView** + `setAsBackgroundMesh`, then mesh with **`Mesh.Algorithm=7` (BAMG)**, `Mesh.SmoothRatio=growth_ratio`, `Mesh.AnisoMax`. The coarse background also produces the smooth channel→floodplain blend (gmsh interpolates the metric within each background triangle).
- Zone selection is by **substring** of the `Zone Name` attribute (case-insensitive): `*channel*` vs `*floodplain*` in `geodata.mesh_zones`. The centerline (`geodata.channel_centerline`) is sampled and `np.gradient` gives per-vertex tangents (nearest via `cKDTree`).
- BAMG **approximates** the metric: realized cross-channel size and anisotropy come out a bit gentler than the configured targets, and `growth_ratio` (default 1.2) intentionally relaxes them near banks. Knobs: `mesh.channel_size` 0.5, `floodplain_size` 1.5, `growth_ratio` 1.2, `channel_anisotropy` 4.0, `max_aspect_ratio` 4.0. Defaults are **high-res**: the Inn KB15 ROI (~0.32 km², ~130 m-wide channel) yields ~720k elements / ~360k nodes (~90 s, ~0.7 GB; the aspect cap below tightens `AnisoMax` which refines the mesh) - raise the sizes while iterating.
- **Aspect-ratio cap** (`mesh.max_aspect_ratio`, default 4.0 = longest:shortest edge): BAMG overshoots the metric anisotropy in the tail (~1.6x) and leaves a few channel slivers, so `Mesh.AnisoMax` is set to `max_aspect_ratio/1.6` and a post-mesh **edge-flip** pass (`_flip_sharp_edges`) flips the shared (long) edge of over-sharp cell pairs - a topological repair that touches only the offending cells (boundary untouched, IPOBO/winding preserved, no inversions), bringing the realized channel max from ~6.5:1 down to ≤~4:1 while keeping the bulk elongation (channel aspect median ~2.0 vs floodplain ~1.4).
- **The anisotropic mesh is NOT reproducible run to run** - a measured property, not a suspicion. Building the isar-2025 mesh twice from identical inputs **inside one process** gives 230,286 vs 231,223 nodes (458,769 vs 460,654 elements, 1801 vs 1790 boundary nodes; ~0.4% spread, min edge 0.191 vs 0.194 m). The cause is the retry below: **BAMG fails intermittently on the first attempt** with the same inputs, and the retry ladder then meshes with a coarser background metric grid, giving a different but equally valid mesh. gmsh is already single-threaded (`General.NumThreads` = 1), so this is not thread scheduling. Consequences worth knowing: `geometry.slf` / `boundaries.cli` / `initial-conditions.slf` **cannot be byte-compared** between runs (regression-test them on mesh *statistics* within ~1% instead); a **resumed mesh-convergence study may compare levels built at different retry rungs**, so a level re-run is not guaranteed to reproduce its own earlier mesh; and a published result should quote the `geometry.slf` actually used rather than assume it can be regenerated bit-for-bit. The OpenFOAM mesh has no such problem - it is aXqua's own structured lattice and *is* bit-reproducible.
- **BAMG failure retry** (`build_mesh`, `_BAMG_RETRY_LADDER`): at fine, high-contrast anisotropic metrics (e.g. a small `refinement` zone next to a coarser floodplain, hit as the mesh-convergence study refines) BAMG's Delaunay insertion can abort with `Fatal error in the meshgenerator 1001 / BAMG failed`. Empirically a **coarser** background metric grid rescues it (larger background triangles smooth the interpolated size gradient BAMG must honor; a *denser* grid makes it worse), as does a looser `Mesh.AnisoMax`. `build_mesh` therefore retries `gmsh.model.mesh.generate(2)` on a BAMG failure with a ladder of `(background node budget, AnisoMax relaxation)` each gentler than the last (`(40000,1.0) -> (20000,1.0) -> (10000,1.5) -> (6000,2.5)`) before re-raising; the normal path meshes on the first (default) attempt with no retry. Isotropic meshing has a single attempt.
- The **isotropic fallback** (no mesh_zones/centerline) is the original distance-field path (`default_size`/`breakline_size`/`region_sizes`); the integration test exercises it.
- **Quality assessment** (`mesh_quality.py`, vectorized, scales to the ~525k-element mesh): logs per-region (channel vs floodplain, via a centroid-in-`_channel_union` mask) internal angles, aspect ratio, skewness; the **shortest edge** (flagged as CRITICAL for the CFL-limited adaptive time step); and the fraction of adjacent-cell area jumps over `mesh.max_area_jump` (20%). The channel is `relaxed=True` so its *intended* anisotropy (aspect ≫ 1) is reported but never warned on - shape warnings (angle < `min_angle_deg`/> `max_angle_deg`, high aspect) apply to the floodplain only. Fatal defects (zero-area, inverted/mixed-orientation, duplicate nodes, non-manifold edges) **raise**; orphan nodes, extra boundary loops (hanging gaps) and IPOBO mismatch (wrong boundary tags) warn. Thresholds are `mesh.min_angle_deg`/`max_angle_deg`/`max_area_jump`.
- Meshing (mesh-zones) and friction (roughness-zones) are **separate concerns**: `geodata.mesh_zones` only sizes the mesh. Friction zonation comes from `geodata.roughness_zones` (an integer `Zone ID` per polygon): `mesh.interpolate_roughness(cfg, mesh)` tags every node/element with the `Zone ID` it falls in (nearest polygon otherwise), writes it as the per-node `FRIC_ID` (overriding the MATID-derived ids), and stores the `roughness_table` value for that id as the `BOTTOM FRICTION` variable. `mesh.run` (hence `pipeline.run`) calls it whenever `roughness_zones` + `roughness_table` are set, so the built `geometry.slf` carries the zone `FRIC_ID` + `BOTTOM FRICTION`, and `steering.write_friction_tbl` derives the matching `.tbl` rows (`<Zone ID> NIKU <ks> NULL`, law `friction.roughness_law`, default 5) from the same table. HydroBayesCal perturbs each `ks` via `zone1`/`zone2`.

Key design points:
- The build runs in its **own** `axqua-env` conda env (gmsh/geopandas/rasterio); it does not import TELEMAC's Python. `env.py` *sources* `telemac.pysource` (the `pysource.*.sh`) in a subshell for any solver/SELAFIN call. The config's `telemac.pysource` must point at the real script (e.g. `/home/modelling/telemac-v911/telemac-mascaret/configs/pysource.debian12.sh`).
- Friction zonation has two routes: (a) the **roughness-zones** route - `geodata.roughness_zones` (`Zone ID`) + `geodata.roughness_table` (id→ks) drive the per-node `FRIC_ID` and `BOTTOM FRICTION` via `interpolate_roughness` (preferred for the Inn case; see the Meshing section); (b) the older **MATID** scheme (1 riverbed_fine … 5 floodplain; see table below) carried by `geodata.region_points` + `geodata.region_table` and/or `friction.zones` in the config → friction `.tbl` rows and `zone<MATID>` calibration parameters. Either way HydroBayesCal perturbs the coefficient column of the `.tbl`. `steering.write_friction_tbl` builds the `.tbl` in priority order: explicit `friction.zones` (MATID) > the roughness table (one `<Zone ID> NIKU <ks> NULL` row each) > a single default zone - so the `.tbl` rows always match the geometry's per-node `FRIC_ID`.
- `src/axqua/selafin.py` is a self-contained big-endian SELAFIN writer (plus a `read_slf` reader for results); its output is validated against TELEMAC's own `data_manip.formats.selafin.Selafin` reader in the tests.
- **Logging** (`src/axqua/logsetup.py`): each script/phase writes a compound, timestamped `axqua.log` into its **own output folder** (`setup_logging(path)` routes the `axqua` logger and captured Python warnings to it; file at DEBUG, console at the chosen level, append mode). the build (`pipeline.run`, called by `preprocessing.py`; and `initial_run.py`'s test run) -> `model_dir` (`simulation/`), the mesh-convergence study -> `mesh-convergence/` (scoped via the `logging_to(path)` context manager so it doesn't capture the per-level builds elsewhere). `log_step(name)` logs `START`/`DONE … in N.NNs` (or `FAILED … after N.NNs`) - wrapped around every pipeline stage and the heavy mesh/convergence sub-steps for per-step timing. `pipeline.run(..., log_to_file=False)` skips its own logfile (the convergence study's per-level builds use this so they log only to `mesh-convergence/axqua.log`). Tests reset handlers via an autouse fixture (`tests/conftest.py`).
- **Initial condition - DRY START (default) vs pre-wetting**: the initial run is a **dry start** by default. A *fully* dry bed (`ZERO DEPTH`) can't be used because TELEMAC's `DEBIMP` aborts at a prescribed-Q inflow when the inflow cross-section is dry (it scales the velocity profile by Q/Q1 with Q1 ∝ ∫H along the inflow; H=0 ⇒ Q1=0 ⇒ abort, even with the correct `4 5 5` code - see the inflow-cli memory). So `steering.write_dry_start_conditions` seeds a thin water **plug only on the nodes within `initialization.dry_start_extent` of the inflow line(s)** (default ~5 cells) to `dry_start_depth` (default 0.5 m, kept ≥ normal depth so the inflow stays subcritical) and leaves the rest of the domain **dry**; the `.cas` continues from this SELAFIN (`PREVIOUS COMPUTATION FILE` + `INITIAL TIME SET TO ZERO : YES`) and the flow wets the reach from the inflow. The inflow geometry comes from `boundary._load_liquid_lines`; with no inflow line it falls back to the analytical dry `INITIAL CONDITIONS`. **Pre-wetting** (`initialization.prewet_depth`, m) is the *alternative*: when set, stage 4 instead hotstarts the **`*channel*` mesh-zone** (`write_initial_conditions` + `mesh.channel_node_mask`) so the wetting front need not advance from the inflow - a large time saving, used by the **mesh-convergence study** (`INITIAL_DEPTH`, default 0.5 m) but **not** the initial run (which the user wanted dry). **How the seeded surface is built** is `initialization.prewet_mode`: the default **`normal-depth`** (`_normal_depth_prewet_depth`) cuts a real perpendicular cross-section every `prewet_bin_spacing` (20 m) along the centerline, samples it at 0.5 m, clips it to the channel zones, and seeds the **stage that conveys the case discharge** through it via `rating.stage_for_discharge` (the Keulegan conveyance inversion factored out of `section_rating`, so the seed and the outflow rating share one implementation), with the local bed slope from the gradient of the transect thalwegs rather than one reach slope. The seeded surface is `thalweg + prewet_fill x (normal stage - thalweg)`; **`prewet_fill` is 0.70, below 1 on purpose** - under-seeding is recoverable (the flow refills a pool in seconds), over-seeding is not, because a 2D model has neither infiltration nor evaporation and water perched above the converged surface becomes permanent stagnant film. `prewet_mode: constant` is the older `_longitudinal_prewet_depth` (a low bed percentile per bin + `prewet_depth`), also the automatic fallback without a centerline or a discharge; on the braided isar-2025 reach it seeded a median **0.28 m above** the converged surface and left 4694 m2 (35% of the wetted area) as film that had stopped draining. `prewet_min_depth` (0.05 m) additionally leaves a node dry rather than laying down a feathered margin (a seed film is exactly what stalls), and `drainable_prewet` still runs on top. **After every filter the inflow plug is re-imposed** (`_inflow_plug_mask`, same `dry_start_extent`/`dry_start_depth` as the dry start): none of the filters has any reason to keep the inflow cross-section wet, and the normal-depth seed is shallowest exactly at the upstream end, so without the guard `DEBIMP` aborts the run at t=0 on a dry inflow - which is precisely what the old over-seeding had been hiding. Sizes are validated in `tests/test_prewet.py`; the calibration is recorded in `cases/isar-2025/test-approaches.md` (R2). `pipeline.run` records whichever file in `Artifacts.initial_conditions`. A side effect of the dry start: while the domain is mostly dry the **k-epsilon / Spalart-Allmaras turbulence linear solve** is ill-conditioned, so TELEMAC's needlessly tight default accuracy (`ACCURACY OF K`/`EPSILON`/`SPALART-ALLMARAS` = 1e-9) is unreachable within its 50-iteration cap - the transient `GRACJG: EXCEEDING MAXIMUM ITERATIONS 50` warning, which is **benign** (it reaches ~1e-6, the run stays mass-conservative and self-heals once the reach wets). `steering` therefore writes `hydrodynamics.turbulence_solver_accuracy` (default **1e-6**, plenty for turbulence) for the k-epsilon (3) / Spalart-Allmaras (6) models, which converges the turbulence solve in fewer iterations.
- Calibration CSV schema (read by HydroBayesCal): `id, x, y, z, <QTY>_DATA, <QTY>_ERROR`, where `<QTY>` is a SELAFIN name (e.g. `WATER DEPTH`, `SCALAR VELOCITY`).

v1 covers the **2D hydraulic** path end to end; the **DEM-of-Difference** (with a level of detection) is implemented in pre-processing (`dem_of_difference` config block, `dem.dem_of_difference` / `dem.resolve_lod`), and **GAIA morphodynamics** is wired for simulation - `steering.write_gaia_cas` writes a damocles-valid GAIA steering file (transport modes + bed-process capacities: morphological factor, slope effect, secondary currents, active-layer stratigraphy, prescribed solid discharges) coupled to the steady, `unsteady2d.cas` and `unsteady3d.cas` runs (`morphodynamics` config block). What **remains an extension point** is the *calibration* side: turning the DoD into per-point topographic-change calibration targets and folding the GSD `sediment_classes` into GAIA from the ground-truth template.

### The per-case workflow

`cases/example-Inn/` holds the worked example for the Inn case, run against its `case-config.yml` as flat scripts (`mamba run -n axqua-env python cases/example-Inn/<script>.py`). The **workflow is three ordered steps**: (1) `preprocessing.py` builds the complete TELEMAC case into `axqua-case/simulation/` (via `pipeline.run`, at the steady discharge from **this case's** `case-config.yml` `boundaries.prescribed_flowrate` - the shared `axqua.prepare_steady_inputs` helper reads the inflow Q and outflow-stage prescription from the config rather than a value hard-coded in the script, synthesizing a constant inflow series + outflow rating only if missing) - the final mesh `geometry.slf`, `boundaries.cli`, `friction.tbl`, `steady2d.cas`, plus the HBC artifacts in `calibration-validation/`; (1b) `initial_run.py` test-runs *exactly that* `steady2d.cas` once (`axqua.run_solver_streaming` → `TelemacRuntime.run_solver` with `-s --nozip`, no rebuild) to confirm it does not crash - the solver's listing is **streamed live** to the terminal (via `TelemacRuntime.run`'s `on_line` callback, so the run isn't silent) with a **progress bar** of simulated time vs `DURATION` (`axqua.progress.SolverProgress`; the CFL-adaptive dt makes the *number* of steps unknown a priori, so progress is measured against the simulated-time cap `expected_duration(cfg)` = `hydrodynamics.duration` else `n_time_steps × time_step`, with the live iteration count shown). A module-level **`NCSIZE`** at the top of `initial_run.py` overrides `telemac.n_processors` for this one test run (leave it `None` to use the configured core count). The run then gets a **boundary-flux convergence analysis** (`axqua.flux_convergence`) that reads the `.sortie` (needs `PRINTING CUMULATED FLOWRATES : YES`, already emitted) and writes four files into `simulation/` - `extracted-fluxes.csv` + `flux-convergence.png` (per-boundary fluxes) and `convergence-rate.csv` + `convergence-rate.png` (the relative imbalance `|Q_in|-|Q_out|`/`|Q_in|` and its convergence rate). The listing is parsed by **`axqua.sortie`** (`read_sortie` / `latest_sortie`): each `BALANCE OF WATER VOLUME` block is read as a unit and its time taken from the `RELATIVE ERROR IN VOLUME AT T =` line *inside* it, so times, volumes and fluxes cannot drift out of alignment and no sample is fabricated. This replaced a dependency on the external **pythomac** package, which cannot be vendored (it is GPL-3 and its parser derives from TELEMAC's GPL-3 `postel`, while aXqua is BSD-3) and whose package boundary forced several adapters: the printout spacing had to be back-calculated (a CFL-adaptive run has no fixed `period*time_step`), `convergence-rate.csv` had to be written separately (only the `.png` was produced), and the rate plot had to be swapped out whenever the rate was undefined. Now `flux_convergence` owns the maths (`relative_imbalance`, `convergence_rate`, `convergence_index`) and both plots; the converged time and iteration count are read straight off the listing rather than estimated, and the convergence figure always shows the relative imbalance (with the tolerance marked) plus the rate where it is defined - during the filling phase the rate is undefined everywhere, which is exactly when one needs to see the imbalance. **Tolerance grades** (`hydrodynamics.flux_tolerance`, default **1e-3**): the imbalance is *relative*, so the discharge/depth/velocity read off a steady run inherit it directly - 0.1% is far inside field-measurement uncertainty and inside the 5% the mesh-convergence study accepts, so 1e-3 is the right grade for a hydraulic result. The stricter **1e-4** (`HOTSTART_TOLERANCE`) is for a **hotstart seed**, where the residual transient is inherited by every perturbed calibration run rather than averaged out; 1e-6 is a rarely-worth-it validation grade. The *absolute* steady criterion is derived as `flux_tolerance x prescribed_flowrate` (so the hotstart gate means the same on a 2 m3/s side channel as on a 200 m3/s river) rather than a fixed 1e-3 m3/s. The analysis also **deletes the per-processor `*_p0000N.sortie` copies** of a parallel run (only the merged main listing matters) and detects the **absolute steady window**: when `||Q_in|-|Q_out||` stays below 1e-3 m³/s over 10 consecutive listing printouts (`flux_convergence.find_steady_window`; on a noisy steady state, whose instantaneous imbalance oscillates above that floor, the 10-printout *mean* is the fallback, flagged as such), a **`hotstart2d.cas`** is generated next to the steady case via `steering.write_hotstart_cas` - it continues from `r2d.slf` (`PREVIOUS COMPUTATION FILE`, clock reset), renames the results to `r2d-hotstart.slf` (no self-clobber), caps `DURATION` at that steady time, and keeps the constant Q/H prescriptions unchanged. A balanced flux budget says nothing about **where** the water is, so `initial_run.py` additionally writes `wetting-report.csv` and `outlet-profile.csv` via **`axqua.wetting`**: `wetting_report` splits the wetted area into *active* flow (H > 0.05 m, |U| > 0.15 m/s, in the largest connected body), *stagnant film* (wet but under 0.05 m/s) and *isolated puddles*, attributes each to the pre-wet seed when the initial-conditions SELAFIN is passed, and samples earlier frames to say whether the film is still draining or has **plateaued** - the failure mode a longer run cannot fix, since a 2D model has neither infiltration nor evaporation (isar-2025: 4694 m2 of film, 75% seeded, shrinking 1.8% over 3100 s). `outlet_profile` bands the actively flowing nodes by distance from the outflow line, reports the discharge-weighted free surface / depth / Froude per band, and compares the near-boundary surface slope with the reach's own to return `backwater` (the prescribed stage is holding the level up over ground that should be dry) / `drawdown` / `neutral`. The report's wetted threshold is `hydrodynamics.wet_depth` (0.01 m) - a **reporting** convention, since on a bed with ks 0.05-0.5 m water 5 mm deep stands *inside* the grain roughness rather than flowing over it (on isar-2025 that band was 13% of the wetted area but 0.16% of the volume); use the same filter in ParaView so the picture and the report agree. Water an external source holds in place is passed in via `supported=` and reported as its own category, excluded from *film* and *isolated puddles* - otherwise a legitimately wet water-table pool reads as a defect. This ends preprocessing; (2) `mesh_convergence_study.py` runs the grid-independence study; (3) `run_Bayes_cal.py` calibrates the built case with HydroBayesCal. An **optional 3D extension** runs after step 1b (and after step 2 fixes the horizontal mesh): `add3d.py` writes the three 3D steering files (hydrostatic flux-convergence check, non-hydrostatic steady, unsteady), then `vertical_convergence_3d.py` runs the vertical-layer (`dz`) grid-independence study - both are documented in the `hbc-calibration` skill. Step 3 compiles the FlowTracker velocity ground truth into the calibration-points CSV (the point velocity, measured at **0.6·h**, approximates the depth-averaged velocity, so it is compared to TELEMAC `SCALAR VELOCITY` = sqrt(U²+V²) built from the **horizontal** components only), ensures the `.cas` outputs `SCALAR VELOCITY` (graphic-printout `M`), emits `config_Telemac.py`, and stages and launches HydroBayesCal's `bal_telemac.py`. **HydroBayesCal is a pip dependency** (`pip install 'axqua[calibration]'`, requiring `>=1.4.4`: 1.4.2 ships the drivers *with* the package, 1.4.4 makes the multi-flow driver honor the config's `extraction` block): the driver is copied out of the installed package by `hydroBayesCal.copy_driver` and run in aXqua's own environment, so there is no checkout directory to point at and no second conda env to name. It is an *optional extra* because its surrogate stack (bayesvalidrox, gpytorch, scikit-learn) is irrelevant to building or running a TELEMAC case, so `bayescal.require_hbc` imports it lazily and explains the install if missing. The driver is still a subprocess - it is a script with an `argparse` main() that must run with TELEMAC sourced, and sourcing mutates the environment - but under `sys.executable`. Pass `checkout=` to develop against an unreleased driver; `--prepare-only` writes the CSV+config without launching - everything into `calibration-validation/`. HydroBayesCal reads the CSV's first four columns by position (id, x, y, z) and `<QTY>_DATA`/`<QTY>_ERROR` by name; `_ERROR` is a site-specific error in physical units added in quadrature to its built-in 10% measurement + 10% surrogate error.

### The OpenFOAM free-surface extension

Documented in `src/axqua/solvers/openfoam/CLAUDE.md`, loaded when working on the OpenFOAM backend.

### Fine sediment over a bed that stays in place (`fine_sediment`, `solvers/openfoam/sediment.py`)

**Morphodynamics with OpenFOAM is not a moving bed.** It is Olsen's `sediDriftFoam2` with the bed and the water surface kept where they are: the concentration of one grain size, its settling onto the bed and its pick-up, and from them the mass of fine sediment the bed takes up per area, and for a bed layer of given thickness the change of its share of fines. The reason is the user's direction of 2026-10-12 for the Isar: "there was no elevation change for sure (any elevation change is a DGPS artifact -- only fine sediment fraction change is real)". **Never use a DEM of difference, a bed elevation change or a scour depth of the Isar as ground truth, as a calibration target or as a result worth showing.** A bed that moves stays TELEMAC and GAIA (`morphodynamics`). The case block is `fine_sediment` (grain size, concentration at the inflow in kg/m3, `pick_up: suspended | bedload | off`, and optionally a period with the bed layer the result is booked into); the job kinds are `openfoam-sediment-build` and `openfoam-sediment`; a case that asks for it uses the OpenFOAM backend also without an `openfoam` block. What the solver requires of a mesh and what running it on the Isar found (a wall distance that turns negative on a sloping bed, one roughness for the bed, the budget) is in `src/axqua/solvers/openfoam/CLAUDE.md`. Three things are open and are the user's to decide: the supply of fines (the solver's pick-up assumes a bed that consists of them, so the Isar is run with `off`), the grain size and the concentration at the inflow (no measurement of either is in the case), and whether the published example gets the block.

### Mesh-convergence study and build prerequisites

The mesh-convergence study (`axqua/convergence.py`, step 2; `cases/example-Inn/mesh_convergence_study.py`, which creates and works in its own `axqua-case/mesh-convergence/` folder) runs the same steady sim on a **four-mesh r=1.3 ladder** (`ratio_levels`: one coarser x1.3, the configured baseline, two finer /1.3 and /1.3² - Celik et al. 2008 recommend a grid refinement factor **r >= 1.3**; closer-spaced grids like the old ±20% `percent_levels`, kept only for backward compat, drown the grid-to-grid differences in solver noise and degenerate the GCI denominator r^p−1) at constant discharge with TELEMAC's variable time step (per-mesh CFL dt), samples water depth + scalar velocity at the ground-truth probe points (`default_probes`), and judges convergence on the **GCI of the finest grid triplet** (observed p clamped to `THEORETICAL_ORDER` 2 for the GCI; an **asymptotic-range check** `GCI(med)/(r^p·GCI(fine)) ∈ 0.8..1.25` decides whether the GCI is trustworthy, else the finest successive relative change is the fallback - `ConvergenceReport.verdict_basis`) vs a tolerance (default **5%**, `DEFAULT_TOLERANCE`; Celik: 5-10% is engineering accuracy). Each level is built with **`mesh.size_scale`** (= level channel size / config `channel_size`), a global multiplier applied to *every* target edge length **including the per-zone `Max Edge Length (m)` gpkg values** - scaling only `channel_size`/`floodplain_size` does nothing when the gpkg carries that field (the bug that invalidated the first ering study: five "levels", one mesh). The study is **resumable** (each level folder gets a `level.json`; on re-run a prompt offers reusing completed levels, QoI re-extracted from their `r2d.slf`; size-mismatched levels re-run) and **extensible**: when not converged it offers up to `MAX_EXTRA_LEVELS` further /1.3 refinements one at a time, each prompt showing a **runtime estimate** (log-log fit of measured runtimes, theoretical t~dx⁻³ fallback) and the **mesh-validity check** of the candidate size; non-interactive sessions auto-resume and auto-stop (no hang). A refinement that **fails to mesh/run** (e.g. BAMG gives up even after its retries, or the solver diverges) is caught as the practical refinement limit: the extension stops and the report is written from the levels already completed, instead of crashing the study. **Auto-refinement mode** (`run_mesh_convergence(auto_extend=True)`, exposed by the per-case `mesh_convergence_study.py` as `python .../mesh_convergence_study.py mode='auto-refinement'`) auto-approves the resume prompt and every extension (no prompts, interactive or batch) so the study marches finer one grid at a time until it converges, exhausts `AUTO_MAX_EXTRA_LEVELS` (default 8, vs. the interactive `MAX_EXTRA_LEVELS` 3), or a level fails. Every level's report row carries the `axqua/mesh_validity.py` checks: shear velocity from the fully-rough log law, wall **y+** (O(10⁴) in rivers, always passes - reported as standard), roughness Reynolds **ks+** (>=70 fully rough for the Nikuradse law), **dx vs ks** (dx < channel ks = roughness double-counting risk; fires first under refinement), and **turbulence-model consistency** (`steering.turbulence_pick_for_dx` vs the pinned baseline model). Every per-level build is **pre-wetted** (`INITIAL_DEPTH`, default 0.5 m -> `initialization.prewet_depth`): the channel mesh-zone nodes are hotstarted with that water depth so the solver need not advance the wetting front from a dry bed (see "Pre-wetting" below). `ConvergenceReport.to_xlsx()` writes a **styled .xlsx** (openpyxl) to `mesh-convergence/` (incl. the validity rows) and `recommendation()` picks the **coarsest grid-independent cell size** (convergence vs. compute-time tradeoff, with the runtime speed-up vs. the finest; under a GCI verdict with no rel-change-adequate level it recommends the medium grid of the converged triplet). The TELEMAC run is injectable (`simulate=`) so the report maths/xlsx are unit-tested without the solver (`tests/test_convergence.py`, `tests/test_mesh_validity.py`). Results SELAFINs are read with the minimal `selafin.read_slf` (the writer's counterpart; single/double precision, multi-frame, returns the last frame); `_geom_stats` drops the zero-length edges that merged parallel results carry at subdomain interfaces (else min-edge/dt report as 0/NaN).

A build needs a **ROI boundary polygon** (`geodata.boundary`, a closed polygon/polyline in EPSG:25832; the Inn example uses `cases/example-Inn/user-sources/geodata/roi-kb15.gpkg`) and `boundaries.liquid_boundaries` (both set in the Inn config). The steady **inflow Q comes from this case's `boundaries.prescribed_flowrate`** (m³/s) - the shared `axqua.prepare_steady_inputs` helper (used by `preprocessing.py` and the mesh-convergence script) reads it from the config rather than a value hard-coded in any script, so each case uses its own discharge. A constant-Q `boundaries.inflow` series is then **auto-synthesised** at that discharge when missing (`boundaries.inflow` itself is optional - only a *varying* series triggers the unsteady case), and the outflow rating `boundaries.stage_discharge` is synthesized from a normal-flow curve when the `stage_discharge` outflow condition is active and none is given (the default `outflow_condition: elevation` needs no rating, just `boundaries.prescribed_elevation`), so the only machine-specific thing to set for a build is `telemac.pysource`.

## Structures: dams, weirs, walls and buildings (`axqua/core/structures.py`)

**No STL anywhere, and that is not a limitation.** STL is a `snappyHexMesh` requirement: that mesher snaps a background block onto a triangulated surface, so every solid must arrive as triangles. aXqua writes `constant/polyMesh` directly (and `geometry.slf` for TELEMAC), so a structure only has to declare **where its footprint is** and **how high it stands** - both ordinary vector attributes. A structure layer is therefore a plain GeoPackage QGIS authors natively, with no CAD step and no format QGIS cannot round-trip.

**Geometry**: a **polygon** is the footprint directly; a **line** is buffered by its `Width (m)` (flat caps, mitred joins - a lozenge with rounded caps would over-block the channel at each end), which is how one actually draws a wall or a dam crest. **Height**: `Crest (m)` gives a *level* crest (dam, weir, floodwall); `Height (m)` gives a crest that *follows the terrain* (embankment, levee of constant build height). Neither is a sane default for the other, so the field the user fills in is what decides.

**Two modes, and the choice is hydraulic.** `overflow` (dam, weir, embankment, levee, block ramp) **raises the bed to the crest**: the structure is terrain the DEM did not carry, the plan mesh is unchanged, and water passes over it - identical in both solvers. `solid` (wall, floodwall, building, pier) **removes the footprint from the domain** so its sides become no-slip walls from bed to lid; use it for anything never overtopped, since it is both cheaper (no cells inside the obstacle) and more correct (a real vertical face rather than a very steep bed with a sliver of cells on top). The mode comes from the `Type` text by substring - the same convention as `classify_zone` - or from an explicit per-feature `Mode` column. Unrecognized text is `overflow`, deliberately: raising the bed keeps the domain connected and lets water pass, whereas wrongly blanking a footprint would silently wall off part of the reach. Note `block` is **not** a solid keyword - a *block ramp* is overtopped by design while a *concrete block* is not, so the word carries no usable signal.

**Where the two solvers necessarily differ**, and it is reported rather than left implicit: a 2D depth-averaged mesh has no vertical wall to remove, so `solid` structures are burnt into the TELEMAC bed as crest + `structures.solid_freeboard_2d` (default 2 m) - the standard way a floodwall is represented in TELEMAC - while OpenFOAM gets the genuine vertical face. In the OpenFOAM mesher the blanking is applied **after** `binary_fill_holes` in `build_plan_grid`: a building punched out of the domain *is* the interior void that hole-filling exists to close, so blanking first would simply be undone. If blanking disconnects the domain the build **warns** ("a solid structure has cut the domain in two") instead of silently deleting the far side. Verified end to end on isar-2025 with a dam polygon plus a floodwall line: 225 mesh vertices raised to the crest, the wall's columns removed, and `checkMesh` reporting **Mesh OK, 61,002 hexahedra, Number of regions: 1** with the wall's faces folded into the `banks` patch.

Config: `geodata.structures` (the layer) plus a `structures:` block for the attribute names (`type_field`, `mode_field`, `crest_field`, `height_field`, `width_field`, `name_field`, `default_width`, `solid_freeboard_2d`). Applied by `core.structures.apply_to_bed` / `solid_footprint`, called from `mesh.build_mesh` (TELEMAC, via `_burn_structures`) and `openfoam.mesh.build_mesh`. Tests: `tests/test_structures.py`.

## The config schema: round-tripping, classification, and typed errors

**`dump_config(cfg, path)` (`config.py`) is the counterpart of `load_config`**, and exists because anything that *edits* a case - a form in the planned QGIS plugin, a migration, a scripted sweep - has to put the result back. It goes through the dataclass rather than rewriting the YAML text, which **loses comments but cannot produce a config that will not load**; a comment that survives an edit it no longer describes is worse than no comment, and the annotated prose lives in `cases/case-template/case-config.yml`. Paths are written **relative to where the file will live** (`base=`), so `axqua migrate -o elsewhere/case.yml` does not silently break every relative data path, while a path outside the case tree (a solver install) stays absolute. Guarded by a parametrized round-trip test over **all ten** case configs in the repo: `load(dump(cfg))` is field-by-field identical.

**`axqua migrate <config> [-o out | --in-place]`** writes a config back in the current schema - loading already applies every compatibility mapping, so this just makes the file say what aXqua actually read and stops the deprecation warnings. `--in-place` keeps a `.bak`. `--to-case` derives the name of the new file and does not write over a file of that name that exists (it may have been edited since; naming it with `-o` replaces it). For a config that is a case file already the derived name is the file itself, so it is rewritten as `--in-place` does, and neither writes machine settings into a case file.

**`core/schema.py` states which settings are shared intent and which name a solver keyword** - as *data*, because a form-based editor cannot guess. The rule: a fact about the reach or the modeling goal is `SHARED` (geodata, boundaries, friction, ground truth, structures, `mesh.channel_size`, `hydrodynamics.duration`); a knob of one code belongs to that code (`mesh.growth_ratio` is BAMG's, `hydrodynamics.implicitation` is Telemac2d's, `openfoam.max_courant` is interFoam's). Only the genuinely mixed blocks (`mesh`, `hydrodynamics`) are spelled out field by field, and only their SHARED entries - so "is this shared?" has to be answered deliberately. An unknown key classifies as SHARED, which fails safe for a form (showing a setting on the reach page is a smaller mistake than hiding it behind a solver the user has not enabled). Two tests keep the table from drifting away from the dataclasses it describes. **The fields have deliberately NOT been moved.** The plan folded `openfoam.cell_size` into `mesh.channel_size`, but `openfoam.cell_size_factor` now expresses the OpenFOAM lattice *relative to* the 2D channel size - the same shared-intent link, without pretending the two numbers are the same quantity (a per-zone anisotropic target edge length vs a uniform Cartesian spacing). The rest would be pure renaming: no behavior change, every case config touched, the artifact regression baseline invalidated. `LEGACY_KEYS` is the mechanism for doing it later without breaking a config - it maps dotted old key to new, is applied at load, and emits **one aggregated** warning rather than a per-key wall of text. Note `project.results_dir` maps to `calibration_dir`, **not** `model_dir`: the old single "results" folder is where the HydroBayesCal artifacts land.

**`core/errors.py`** gives failures a **stable machine-readable `code`**, an optional `subject` (the config key or layer the failure is about) and an optional `remedy`. Not decoration: a job record has to store a failure that survives serialization, a plugin has to put a message next to the field that caused it, and a batch has to decide what is worth retrying. Deliberately **five categories, one level deep** - `ConfigError` (fix the YAML), `GeodataError` (fix the data), `EnvironmentError` (fix the install), `SolverError` (read the listing), `MeshError` (change resolution) - because mirroring the module layout would produce thirty classes that callers catch by their base anyway. `ErrorRecord.from_exception` turns *any* exception into a JSON-safe record, labeling an unanticipated one `axqua.unexpected` rather than mislabeling it. Additive: existing `ValueError`s keep working.

## The profile and the case file: the computer and the reach are two files

**A case file (`*.axq-case`, `core/casefile.py`) describes a reach and names nothing that belongs to one computer; the profile (`*.axq-profile`, `core/profile.py`) describes a computer and nothing else.** Before this split, where TELEMAC lives was spread over `solvers.yml` (`core/machine.py`), `profiles.yml` (`jobs/profiles.py`), the plugin's QSettings and, in every one of the nineteen tracked case configs, a `telemac.pysource` naming one of three people's home directories. The profile is the one documented place now; **none of the older mechanisms was removed**, which is the rule that let this land without touching a single existing installation: a computer without a profile behaves exactly as before (pinned by `tests/test_profile.py`).

**Resolution order** (`core/machine.resolve`): environment variable -> case-local `solvers.local.yml` -> **active profile** -> `solvers.yml` -> the case file's own value -> discovery. The active profile is `--profile` -> `$AXQUA_PROFILE` -> `default.axq-profile` beside `solvers.yml` (so `AXQUA_HOME` relocates it, which is how the test suite stays off the developer's real profile; `conftest.py` also clears `AXQUA_PROFILE`). `resolve(use_profile=False)` exists for one caller: `profile.detect()`, which must see the settings a profile is about to replace rather than the profile itself - otherwise a wrong entry could never be re-detected.

**`load_active()` is deliberately not strict.** It runs inside every case load, so a profile with a typing error is reported once and skipped, and the older settings serve the build. The commands that are *about* the profile (`axqua profile show|check`) pass `strict=True`. It caches by path and modification time, because a study loads the case once per mesh.

**Machine settings as data: `core/schema.MACHINE_FIELDS`** (`telemac.pysource|environment|version|solver_python`, `openfoam.bashrc|environment`, `postproc.visit|environment`). `dump_config(portable=True)` leaves them out and is what `axqua migrate --to-case` writes; the **default keeps them**, because the other caller of `config_to_dict` is the job record, and a job has to be reproducible from its own folder including the installation it ran with. `n_processors` stays in the case file as a fallback: the profile's `mpi_processes` wins where set (`jobs.profiles.from_plugin_profile`), a binding without a number has no opinion.

**The job system takes its binding from the active profile** through `jobs.profiles.implicit(cfg, solver)`, which replaced the two `from_config` call sites in `jobs/submit.py`. `--profile` accepts an `.axq-profile` file as well as a name out of `profiles.yml`; a file binds several codes, so `jobcli.run_submit` passes the solver of the job kind. One real bug fell out: `spec.launcher["requested"]` is always at least `"auto"`, which is truthy, so `requested or profile.launcher` never reached a profile's launcher. `"auto"` now means "no opinion". **`implicit` follows the resolution order too**: where the environment variable of a code or a `solvers.local.yml` outranks the profile, the job takes that script, keeps what the profile says about the computer (environment kind, processes, job root, launcher) and drops `config_name` and `overrides`, which belong to the installation of the profile. Until the review of 2026-10-10 a case was loaded with one installation and its job computed with another. A name given to `--profile` is looked up in `profiles.yml` first; only a name ending in `.axq-profile`, or one that is no profile name and is a file, is read as a profile file.

**Checks return findings, they do not raise** (`core/diagnostics.Finding`: severity, dotted code, subject, message, remedy; `anchor` is the label of the code in the docs). `profile.check()` has three tiers - files, factual, functional - and the functional one (`SolverEnvironment.validate`, unchanged) is what tells a working installation from a path that merely exists; it costs ~5 s here and `probe=False` skips it. `axqua profile check` exits 0 whatever it finds: findings are the *result* of the command, and an editor has to be able to show them all and still save. `axqua profile write` (JSON on stdin, what the plugin will call) parses before it writes, so a document that is not a profile cannot replace one that is. **`profile.file_path()` is the one place that says which file a profile name means**: a file that exists is used as it is named, a name without a file gets the suffix. `save` used to append the suffix always, so `profile init office` asked about `office` and wrote over `office.axq-profile`, and a profile kept in a file without the suffix (`AXQUA_PROFILE=~/this-computer.yml`) was read from that file and saved to another one beside it.

**The profile also names the folder each program is installed in** (`installations: {telemac, openfoam, paraview, visit}`; the user's decision of 2026-10-11, "the profile should also store local installation directories"). What aXqua runs is still the environment script of a code and the launcher of a postprocessor; where the profile names the folder only, `AxquaProfile.script()` looks the file up in it (`profile.locate`, by the table `LAYOUT`: `configs/pysource.*.sh` without the template, `shell-rc.sh` before `etc/bashrc`, `bin/paraview`, `bin/visit`, and the same one level below for the folder a wizard was given), so **a profile of four folders is a complete one** (checked on lww-134 against the real installations: `profile check` enters TELEMAC and OpenFOAM from it, and a build, a steady run and a calibration ran with it). An entry under `solvers` / `postprocessors` outranks the folder. Several environment scripts in one folder are a decision aXqua does not take (`locate` answers `None`, the check names them). `installation_of()` goes the other way and is what `detect()` and the installation runner (`bind`) use to enter the folder; a launcher in `/usr/bin` has none ("installed in /usr" says nothing), and a launcher that is a link is followed, the folders above it are not. `machine.resolve` and the job binding (`jobs.profiles.from_plugin_profile`) both go through `script()`. For the plugin: `axqua profile locate <program> <folder>`, and `programs` in the answer of `profile show` (what is run for each program; not part of the file, the editor strips it).

**A profile outlives the version that wrote it** (the user, same day: "when one updates the aXqua plugin in the future, profiles should be retained for local users"). It is kept in the configuration folder of the user, outside of the package and of the plugin (pinned by `test_the_profile_is_kept_outside_of_axqua_and_of_the_plugin`), and the plugin stores nothing but the path of the `axqua` program, in the QGIS settings. Three rules, stated in the docstring of `core/profile.py`: the layout only grows (the text `WRITTEN_BY_0_4_2` in `tests/test_profile.py` is a profile of that version and is never edited); **an entry this version does not know is kept and written back** (`extra`, a warning `axqua.config.unknown_entry` with the nearest known name, where a misspelled key used to make the whole profile unreadable) because the plugin and the library are updated separately and each may meet a file the other wrote; and `save()` never writes over a file it could not read without moving it to `<name>.<date>-<time>.bak` first (`profile.backup`, reported by `profile write` and shown by the editor). The last one closed a real loss: the plugin offers *Create profile...* when the profile cannot be read, and saving the detected one replaced the file. Text where a number belongs (`mpi_processes: many`) was an uncaught `ValueError` in every case load; it is a `ConfigError` now.

**`find_case_file(folder)`** is what the template scripts call instead of naming their case file. One `*.axq-case` is the answer; several raise and name them (a silent pick would run a different model than the user thinks); none falls back to `case-config.yml`. The example cases name their file explicitly, because isar-2025 has five variants. **`cases/munich-vsf/` and `cases/slot-flume/` are NOT converted** - lww-133 runs from them (issue #5); they keep `case-config*.yml` until it confirms.

**What an editor of a case needs is three verbs and one table** (`casecli.py`): `axqua schema` (the field table of `core/schema_meta.py`), `axqua case read|write|new`, and `axqua check` (`core/casecheck.py`). `Config.validate()` is now `for _, step in self.checks(): step()` - the same steps in the same order, as a list of `(what about, step)` - so that the check can run every one of them and report one finding per block instead of only the first failure; steps marked `machine` (`telemac.validate_installation`, the three `environment.validate`) are skipped there, because where TELEMAC is installed is the profile's finding, not the case's. `TelemacEnv.validate` was split into `validate_installation` + `validate_choice` for that reason. The check never raises, whatever the file holds, and `case write` saves first and checks afterwards. Every code either check can emit has an anchor in `docs/troubleshooting/` (`test_every_code_..._is_explained_in_the_documentation`).

## Validation: the calibrated model in another flow situation (`axqua/validation.py`)

**The user's rule, 2026-10-08: every dataset given to HydroBayesCal is calibration data, and validation needs a second dataset from another situation. No splits** - no leave-one-out, k-fold or random share, in the library, the plugin or the docs, because the points of one survey in one flow field are not independent. `calibration.validation` is a list of `ValidationSituation` (name, `sources` like `ground_truth.sources`, `prescribed_flowrate` or per-boundary `inflows`, `prescribed_elevation`, `duration`); a single mapping loads as a list of one.

**The validation run is the built steady case with other boundary values and nothing else** (`validation.build`): the as-built `steady2d.cas` is copied and patched in `TITLE`, `RESULTS FILE`, `PRESCRIBED FLOWRATES` / `ELEVATIONS` and the file names of what the calibrated values live in - a test asserts those lines and no others, so a difference to the measurements cannot come from a model that was built differently. The boundary arrays come from the same `steering._prescribed_arrays` and `liquid-boundaries.json` as the build (a total discharge keeps the split of the case; `inflows` gives each boundary its own), and the outflow level from `resolve_outflow_wse`, with the rating synthesized for the validation discharge by the case's own `rating_method` when the case has no measured curve. Under `outflow_condition: elevation` a situation without a level is refused: the calibration's level belongs to its discharge.

**The calibrated values are HydroBayesCal's joint posterior maximum** (`BAL_dictionary.pkl` -> `joint_optimum[-1]`, posterior mean for an older HBC), applied by HBC's own rules: `zone<N>` rewrites a row of a *copy* of the friction table, `f.<NAME>` a constant in a copy of the user Fortran folder, any other name a steering keyword. `gaia*` parameters are refused rather than ignored.

**The comparison reads the model on `geometry.slf` with the mesh's own triangles** (`compare`; see the single-precision note under post-processing), counts points outside the mesh and points that are dry in the model, and reports n, bias, relative bias, MAE, RMSE, correlation and the share within one and two measurement errors (the point's own error combined with `calibration.measurement_error` x value, as the calibration weighs it). The run's final flux imbalance is read from its listing and a run that had not reached the case's `flux_tolerance` says so. Outputs: `calibration-validation/validation/validation-<name>.{csv,json,png}`. It is the `validation` job kind (capability calibration, `study` verb, told from a calibration by `ValidationOptions.validate`); `axqua validation <case>` is what the plugin's form reads.

A run without `--docstrings` keeps the docstring entries the catalogs already have, and a machine entry whose new translation fails keeps its earlier text with its old hash, so the next run tries again (review of 2026-10-18: both used to be dropped, the first silently deleting reviewed API translations on every deploy). `recapitalize` changes only text outside literals, roles, links and single-asterisk labels, which it sets aside before cutting the text into sentences (they may hold `. ` themselves); where the markup does not pair up (a stray backtick or asterisk would reach over whole sentences) it protects per sentence instead. A kept-after-failure entry is listed in `failed-<lang>.txt` too, in a section of its own. The API reference (autodoc docstrings) stays English (`--docstrings` / `DOCSTRINGS=1` includes it), and so do list-of-references entries (paper titles). The full translation of both languages is about 4 minutes with 4 workers of 2 threads each (Argos takes every core per process otherwise); a normal deploy translates only what changed.

**What the first full runs found about Argos, each with its repair in `translate.py`** (pinned by `tests/test_docs_i18n.py`, which needs no engine): (1) Placeholders `@@N@@` come back spaced out or shortened (`@ @ 2 @ @`, `@1@@`); `SENTINEL_RE` takes those but must not eat the start of a neighboring placeholder or read `@@0@@ 3.5.0` as a placeholder 3; a placeholder that lost its number fails the message, which is retried with bold parts translated alone, then with glossary terms masked, then sentence by sentence; what still fails stays English (`docs/_build/i18n/failed-<lang>.txt`, 0 German and 1 French of ~1200). (2) **Glossary terms are injected into the English sentence before translation**, which gives correct German declension ("The Wassertiefe at the Zuflussrand" -> "Die Wassertiefe am Zuflussrand"); in French rare injected words are translated again ("courbe de tarage" -> "courbe de goudron", "Maillage" -> "Mèche"/"courrier"), so French terms go in **title case** (copied like names, articles and participles agree) and are lowercased afterwards; every injected term must come back (`_terms_came_back`) or the message is retried with the term masked. A message that is only terms and connecting words (`*Mesh*` headings, ``a`` or ``b``) is put together without the engine. (3) Single-asterisk text is the plugin's GUI labels and is never translated; masked parts at the start or end of a paragraph are peeled off (Argos turned a leading label into "Autres"). (4) A German sentence sometimes comes back all lower case; `recapitalize` uses the nouns of the other translations. (5) Articles before glossary terms of known gender are repaired (French `un tâche`, German feminine `des Steuerdatei`), French gets a non-breaking space before `: ; ! ?`, and an aspirated h does not elide (`la hauteur`). Glossaries: `glossary.<lang>.tsv` (`english[|plural] TAB target[|plural] [TAB m|f]`, a target equal to the English keeps it English, per form), `termfix.<lang>.tsv` (source-conditioned regex on the final text, never inside a literal), `keep.txt`.

## The fast end-to-end example (`cases/example-isar/`) and what running it found

`cases/example-isar/example-isar.axq-case` is the isar-2025 research case with `mesh.size_scale: 3.0` (26,500 nodes instead of 230,000) and own output folders; it reads its inputs from its own `user-sources/` folder, a reduced copy of the research inputs that is tracked in the repository (see "The example case is a folder that works on its own" below). Since 2026-10-15 it carries the corrected measurements again (`user-sources/ground-truth/flowtracker-2025-{11,09}.gpkg`, copied by `scripts/build_example_data.py` from the research case). Build 1 min, steady run 1.5 min (flux balance below 1e-3 after ~2240 s of 3000 s), a 12-run HydroBayesCal calibration of `zone4`/`zone5` against the 33 November verticals inside the model in 16 min, validation against the 83 September verticals 1.5 min, all on 8 cores. Its `README.md` is the step-by-step guide for the plugin. **Use it whenever a change has to be tried through the whole chain** - the research case costs a day for the same answer. It keeps the `gain_lose` block of the research case. **An exchange now needs the case to ask for it** (`boundary.exchange_regions`): the `int-*` lines are a property of the liquid-boundary layer, a layer is shared between cases, and they used to be applied whenever the layer held them - so a case that said nothing got an exchange anyway, as thin fixed-rate SOURCE REGIONS, which blow up at the first time step on this reach (rung T2 of `cases/isar-2025/test-approaches.md`, reproduced on the coarse mesh in 2 s). Without a `gain_lose` block the lines are now named in the build log and left out; `boundaries.internal_sources: true` is the explicit way back to the fixed-rate regions. The stale `isar-2025-DEB` and `-Mint` variants, which predated the lines, were removed on 2026-10-15.

**The case has two FlowTracker campaigns, and they are two flow situations.** `flowtracker/Nov25/` (24-25 Nov 2025, `Isar_Nov25.gpkg`) was measured at 2.6 m3/s in the main channel with 1.63 + 0.94 gauged upstream - the discharge of the model (2.4 m3/s, inflows 1.6 + 0.8 from the `Target flow` column, which `prescribed_flowrate` does not rescale). `flowtracker/Sep25/` (30 Sep 2025) was measured at about 5.3 m3/s (5.30 at the outlet transect, 5.32 and 5.09 upstream; 0.18 in the side channel). The example therefore **calibrates against November and validates against September** (`calibration.validation` with `inflows: {1: 0.2, 3: 5.1}`); it used to calibrate against September at 2.4 m3/s, which could not fit (-42 % after calibration). Of November's 56 verticals, 23 lie upstream of the model where the inflows were gauged; `bayescal._inside_the_model` now leaves points outside `geodata.boundary` out of the calibration CSV, because HydroBayesCal reads the nearest node with no distance limit.

**Neither campaign is reproduced, and the validation shows why that matters.** Measured on the example mesh with the corrected data (2026-10-15, depth-averaged verticals): in all 12 calibration runs the November velocity is 33-40 % low at 76-79 % of the verticals while the depth is 0.29-0.33 m against 0.28 m; HydroBayesCal ends with a degenerate posterior (1-3 of 5000 prior samples survive, `joint_optimum` NaN, so `validation.calibrated_parameters` takes the mean of the surviving sample, zone4 0.30 at its upper bound, zone5 0.30), RMSE 0.34 -> 0.33 m/s. Validated against September at 5.3 m3/s: velocity -21 %, depth +22 %, RMSE 0.42 m/s and 0.24 m. The October numbers with the uncorrected layers were the same within a few percent (-33 % / -20 % / +18 %), which fits the correction not having moved the Isar positions. So there is a cause that is not roughness and not the positions: candidates are the DEM against the channels of November and the split among the braids. The research model at full resolution gave the same mean velocity at the September verticals as the coarse example, so the mesh is not it.

Running that chain through the same CLI the plugin calls found defects no unit test had, each now pinned by one:

- **TELEMAC-2D ends a blown-up run as a success.** `CONTROL OF LIMITS` is a "neat (programmed) stop" in `telemac2d.F`: `LIMIT VALUES TRESPASSED, TELEMAC-2D IS STOPPED`, then `CORRECT END OF RUN` and exit code 0. The job was COMPLETED with U = -1002 m/s at t = 0. `workflow.run_solver_streaming` watches the listing for the marker and `_fail_on_limit_stop` gives the process return code 2 (TELEMAC's own code for a controlled error stop) plus `proc.stop_reason`, read from the listing by `sortie.find_limit_stops` - **from the per-processor `_p0000N` listings too**, because in a parallel run only the subdomain that owns the node names it. The backend raises a `SolverError` carrying quantity, value, coordinates and simulated time (`tests/test_limit_stop.py`).
- **A point layer as ground truth** (`kind: points`): column names with a unit in brackets (`v(x) [m/s]`, `Total Depth [m]`) are canonicalised, several readings on one vertical are reduced by the same `profile` rules as a FlowTracker workbook (`select_point_profiles`, grouped by position to 1 cm or by `group_key`), and a `z` column of zeros is a placeholder for "no elevations", not a survey 816 m below the bed (`tests/test_ground_truth_points.py`).
- **`dump_config` must not write a block the case never declared.** Every optional block has a dataclass with defaults, a written block is a declared block on the next load, and so every TELEMAC case came back from a dump asking for OpenFOAM as well - in a job's frozen copy and after `axqua migrate`. `_never_asked_for` skips an undeclared block that still equals its defaults (machine fields aside, since the loader fills those from the profile).
- **A single-flow calibration rewrites the built case in place.** HydroBayesCal's TELEMAC control runs in `model_dir` and writes each tested parameter set into `friction.tbl` and the results name into `steady2d.cas` (and `user_fortran/user_rain.f` for `gainlose_kf`), so the case was left holding the *last* set tried and the next steady run used it. `bayescal.case_as_built` copies those files into `calibration-validation/case-as-built/` and restores them when the driver returns; `restore_as_built` is also called before every TELEMAC launch, because a cancelled calibration is killed and restores nothing. Jobs of one case are queued one behind the other for this reason (`jobs/workspace.py`, see `src/axqua/jobs/CLAUDE.md`).
- **A calibration reports its run number** (`hbc.RunCounter` follows the driver's `logfile.log`). Read `Running full complexity model <N>`, which counts through both phases; `... model # N` and `... after BAL # N` each restart at 1. The driver truncates and rewrites that log between its phases (it contains NUL bytes afterwards, so `grep` needs `-a`).
- **The convergence jobs wrote no report.** `mesh_convergence_study.py` and `vertical_convergence_3d.py` call `report.to_xlsx()` / `report.save()` after the study returns; the job kinds returned the report object and wrote nothing, so the verdict was in `runner.log` only - although `export_qgis_results` already listed the workbook among the results. `backend._write_study_report` now does what the scripts do. Also worth knowing: `default_probes` uses the ground-truth points only when `preprocessing/ground-truth.xlsx` exists, i.e. **after a build**; on a fresh case it silently falls back to 40 points along the centerline, which on this braided reach are mostly dry and gave "22 % not converged" where the 84 verticals give 7 %. Both studies report each run as it finishes (`on_level`, shown as `level 2/4`). **The script and the job keep the study in two different folders**: the job, the capability spec and `export_qgis_results` use `postprocessing_dir/mesh-convergence`, the per-case `mesh_convergence_study.py` uses `postprocessing_dir.parent/mesh-convergence` - so one cannot resume the other's levels. Left as found, because moving either orphans existing studies.
- **The Steady 3D tab ran a simulation nobody could find afterwards.** The `steady-3d` kind defaults to the `hydrostatic` variant, which writes `r3d-hydrostatic.slf` / `r3d-2d-hydrostatic.slf`, while the capability's `run` predicate and `export_qgis_results` looked for the non-hydrostatic `r3d.slf` only. Both now know the hydrostatic names; the depth-averaged companion is what QGIS loads (it carries U and V but no `SCALAR VELOCITY`, so it gets no velocity-styled entry). The 3D volume files (`r3d*.slf`) are listed as files, not layers: QGIS reads SELAFIN in 2D only and each *Load results* ended with "r3d.slf did not load". The plugin's option table gained a `choice` type for `variant` (the first entry carries no value and is not sent). On the example the 3D model gets **two** vertical levels; the hydrostatic run takes 19 min for 4800 s, the non-hydrostatic one 10 min for 2035 s.
- **HydroBayesCal was not on PyPI above 1.7.0 until October 2026**; since then 1.9.0 and 1.11.1 are (checked 2026-10-19), so `pip install "axqua[calibration]"` resolves from PyPI alone.

Two traps in the test suite itself: tests built on `git grep` (`test_no_tracked_source_or_test_hard_codes_a_home_directory`) see **tracked files only**, so a new file passes locally until it is committed - `git add` before the final run; and CI runs `pytest`, not `python -m pytest`, so the repository root is not on `sys.path` and `from tests.x import ...` fails there (import `from x import ...` like the other test modules do). The `tests` workflow had been red on `main` since at least 2026-10-03 for the second reason, which is how the first went unnoticed.

## Package structure: solver-agnostic core + pluggable backends

aXqua is structured so TELEMAC and OpenFOAM are **two backends behind one case
description**, rather than one tool with a second bolted on.

**Two rules, enforced by tests rather than intent** (`tests/test_capabilities.py`): nothing in `core` imports a solver, and the OpenFOAM backend never reaches into the TELEMAC backend. Both are checked by reading the source, so they hold even for imports that only happen inside a function. OpenFOAM *is* hotstarted from a TELEMAC result, but it reads it through the shared SERAFIN codec in the core - which is exactly why `selafin` sits there.

**Every historic import path still works.** `axqua/mesh.py`, `steering.py`, `pipeline.py` (14 of them) plus `selafin.py` and `openfoam.py` are **shims that alias through `sys.modules`**, not re-export modules: `axqua.mesh is axqua.solvers.telemac.mesh` is literally true. Re-exporting would have silently dropped every private name (tests import `mesh._parse_decimal`) and broken identity checks; aliasing means there is exactly one module object and no second surface to keep in step. Parametrized over all 16 in the tests.

**Both `solvers/*/__init__.py` resolve attributes lazily** (PEP 562), like the top-level package. Not decoration: each backend's `spec.py` is read by `axqua status` to build a capability table, and importing `axqua.solvers.telemac.spec` runs the package `__init__` first - so eager imports there would drag gmsh and numpy into a question that should cost nothing. Measured: `import axqua` 6 ms / 64 modules, a capability listing 30 ms with **zero** heavy modules.

**Capabilities and the `MODEL=` marker files (`axqua/core/capabilities.py`).** Every
case carries one marker per solver at its top level - `MODEL=TELEMAC_ENABLED`,
`MODEL=OPENFOAM_DISABLED` - whose **name** says whether *the case* declares that solver
(`cfg.declared_blocks`, so the filename means the same on any machine) and whose **body**
is a strictly parseable status table: `#` comments, `key = value` header, then fixed-width
rows after `[capabilities]`. Each capability is reported on **three axes**, kept apart
because they have three different fixes: `implemented` (does aXqua support it *for
this solver* - `yes` / `no` = not yet / `n/a` = category error, e.g. OpenFOAM has no
depth-averaged mode while its morphodynamics is merely unbuilt), `configured` (does this
case ask for it, from the config alone), and `built`/`run` (do the artifacts exist - pure
path checks, never a parse, so a status report is fast and cannot fail). Unanswerable
cells render `-`, never a confident `no`. The files are **generated and gitignored**
(`cases/*/MODEL=*`, with `cases/case-template/MODEL=*` committed as the documented
example): they report the *currently available* setup, which is local state like
`axqua-case/`. Refreshed by `pipeline.run`, by `openfoam.build_case` and by
`axqua status <config> [--check-env] [--full]`; `refresh_markers` never raises, since
a succeeded build must not report failure because a status file could not be written.

**The solver registry (`axqua/core/registry.py`).** A backend is described by a
`BackendSpec` - name, title, config key, the capability support matrix, and the
`built`/`run` path predicates - which is **metadata only**, deliberately separate from the
`SolverBackend` implementation that builds and runs. The spec modules
(`axqua/solvers/{telemac,openfoam}/spec.py`) are import-light by contract: they use
the standard library plus attribute access on a `Config`, and nothing else. That is what
lets `axqua status` - and, later, a QGIS plugin running inside the QGIS Python process
- answer "what can this case do?" without importing gmsh, rasterio, pandas or a solver.
Backends are discovered through the `axqua.solvers` entry-point group, with a
hard-coded built-in list as a fallback for source checkouts that predate the group, so
"add your own" and "use ours" are the same mechanism.

**`axqua/__init__.py` resolves attributes lazily (PEP 562).** `import axqua` went
from 505 ms / 652 modules to **21 ms / 64 modules**, and a capability listing imports
**zero** heavy modules - measured, and asserted in `tests/test_capabilities.py` from a
subprocess so the rest of the suite's imports cannot mask a regression. The public API is
unchanged (`from axqua import build_mesh` still works); `__all__` is written out
literally because linters and IDEs read it statically, and a test keeps it in step with
the `_EXPORTS` map.

## Hydrology mode: rainfall-runoff with Green-Ampt (`axqua/hydrology/`, TELEMAC only)

**The user's order of 2026-10-24**: a sub-tab *Simulations > Hydrology*, a *Hydrology mode* check box in mesh generation, a preprocessing checkup and a data wizard. User decisions: Green-Ampt default = the Sadeghi solution recommended by de Vos et al. (2024, TUC XXX, hdl 20.500.11970/114347; the original implementation is Broich et al. 2022, hdl 20.500.11970/110848), rain uniform in space, wind AND evaporation included, the wizard downloads data itself after the national-agency hint.

**The block `hydrology` with `enabled: true` is the mode** (`config.Hydrology`, layer TELEMAC). `Config.outflow_condition` returns `hydrology.outlet_condition` in the mode, so boundary/steering/hydraulics read one property. The mode needs no discharge and no inflow line (a case without any liquid line is a closed catchment; `classify_nodes` returns all walls, `read_sortie` accepts listings without boundary fluxes); `gain_lose` in fortran mode and `prewet_depth` are refused. STEADY2D and MESH_CONVERGENCE are not configured in the mode; `Capability.HYDROLOGY` / `JobKind.HYDROLOGY_RUN` (`hydrology`) run `hydrology2d.cas`, built by the ordinary build (`pipeline._write_hydrology`; the river stage 4 moved unchanged into `_write_river_steering`).

**TELEMAC v9.1.1 ships only Travert's Green-Ampt** (`RAINFALL-RUNOFF MODEL 3`, hard-coded constant rain, no infiltration of ponded water after rain); de Vos's revision is not upstream (GitLab main, checked 2026-10-24). So aXqua generates `user_fortran/runoff_greenampt.f` (`solvers/telemac/greenampt.py`) with TELEMAC's exact interface: kernels `sadeghi` (default), `exact` (Ks(1+a/F)), `travert`; forcing (rain + evaporation, mm/h) from `FORMATTED DATA FILE 1` (`forcing.txt`); Ks [mm/h], `GA SUCTION A` = psi (theta_s - theta_i) and `GA DELTA THETA` per node as named private variables of `geometry.slf` (matched on 16 chars, `fonstr.f`), `INFILTRATED` written back. **PROSOU runs once per sub-iteration of a step**, so the routine computes from the state at the start of the step and commits when LT changes. It prints `AXQUA HYDROLOGY t rain infiltrated evaporated` [m3] at listing printouts (`hydrology/report.py` reads it with TELEMAC's FINAL BALANCE). The Python reference `hydrology/greenampt.py` is the same algorithm; TELEMAC and it agree to four digits on a flat closed basin (FE, FV, 4 cores). Sadeghi as de Vos give it infiltrates 1.4-4 % less than exact Green-Ampt under constant rain; `exact` is exact.

**Two findings that changed the plan, both measured on a synthetic V-catchment** (scratch, not tracked; the test fixture `tests/test_hydrology._catchment` is its small copy): the free outflow (4 4 4) ponds (FV) or blows up (FE, "ILL-POSED PROBLEM, ENTERING FREE VELOCITY") unless the outlet is supercritical, so **the default outlet is `normal_depth`**: TELEMAC's `STAGE-DISCHARGE CURVES` Z(Q) per outflow line from the line's DEM section (`rating.line_section`, ks of the roughness zones, else `friction.default_*`, never the lateral-wall keyword) and the slope upstream (`hydrology.outlet_slope`). And **the hydrology kernel defaults to finite volumes + `OPTION OF THE HYDROSTATIC RECONSTRUCTION : 2`** (Chen and Noelle, TELEMAC's `rain_runoff` validation): the classical reconstruction fails where h < bed step between nodes; FE left 13 % of the rain as film 30 min after the storm vs 0.5 % with FV. Equilibrium Q = iA reached to 0.01 %.

**Wind and sun**: wind through TELEMAC (`WIND`, `OPTION FOR WIND 2`, `atmosphere.txt` with components from the from-direction; `THRESHOLD DEPTH FOR WIND` default 1 m); evaporation computed by aXqua (FAO-56 ET0 x open-water factor 1.05, or hourly Penman-Monteith eq. 53, checked against FAO-56 Example 19) and taken from surface water only in the routine. **Mesh**: in the mode `mesh._hydrology_size_field` (isotropic, zone `Max Edge Length` applies isotropically, growth-limited size grid, Frontal-Delaunay), never BAMG. **Checkup** `hydrology/checks.py` (codes `axqua.hydrology.*`, anchors in `docs/troubleshooting/`, the terrain part = priority-flood wall crossings + depressions in `hydrology/terrain.py`), run by `axqua hydrology check`, by `axqua check` (without terrain) and at the start of the build (errors stop it). **Data**: `axqua hydrology info|portals|textures|rainfall|design|fetch|check` (`hydrologycli.py`); `fetch` = Open-Meteo ERA5 (event + soil moisture), SoilGrids WCS (textures -> Rawls 1983, values checked against the scan of the paper; the TUFLOW wiki copy has loam and silt loam wrong), ESA WorldCover COG (class 50), each with a provenance `<file>.json`. Docs: `docs/usage/hydrology-simulations.rst`.

**What the four reviews of 2026-10-25 fixed, each pinned in `tests/test_hydrology.py`**: `Config.hydrology_mode` is the one test of the mode (code that also gets stand-ins reads `getattr(cfg, "hydrology_mode", False)`); a listing without boundary fluxes passes `read_sortie` only when it says itself that its run had no liquid boundary (`THERE IS n SOLID BOUNDARIES:` without a liquid line before it in a serial run, `NUMBER OF LIQUID BOUNDARIES: 0` in a parallel one; `Sortie.liquid_boundaries`), so the run decides and not the case as built now, and a river run still gets the error; the build refuses `morphodynamics`, any `gain_lose` and `internal_sources` in the mode, because `_write_hydrology` writes none of them; a dry run launches `hydrology2d.cas`; the rain reader takes integer dates (`MESS_DATUM`, MeteoSwiss `time`) as dates in any column, years 1900 to 2100, except ten digits whose every step is a whole number of minutes (Unix seconds, which parse as `YYYYMMDDHH` from 2030 on; `YYYYMMDDHH` read as a number never steps so), `R1`/`RWS_10`/`RS` as depths in mm whatever the units and stamp settings say (end, end, and for `RS` the DWD's precipitation day from 05:50 UTC of the date to 05:50 UTC of the next, as the parameter metadata in each station archive say; 07:30 legal time before April 2001, `rainfall.dwd_day_starts`), -999 as missing; both readers keep only data rows (`rainfall._data_rows`: before the first and after the last time a row is left out only when it cannot be one with a broken time, i.e. its time has no digit or it has no number, a units row or a sum; an empty row or a repeated header inside is left out; any other row without a readable time stops the import with its value), and the weather reader interpolates a missing reading in time (`weather.fill_gaps`, the direction as an angle; warning `weather_gaps`), where -999 used to reach the evaporation and the wind; a missing value stays a dry interval of its own (`RainSeries.missing`, written empty into the canonical file so the checkup still sees it, warning `rainfall_gaps`, and a `caution` in the wizard) instead of stretching the next row over it; a design storm or an undated record clears `hydrology.rainfall_start`, and undated rain under dated weather is the warning `weather_alignment`; the size grid is cached per process by its inputs (`mesh._SIZE_GRIDS`) and the element estimate belongs to the slow checkup (`terrain=True`); `rating.ks_from_friction` is the one conversion of a friction law to ks; `steering.read_cas_values` is the one reader of steering-file keywords (`KEY : value` or `KEY = value`, comments skipped; `threed` and `cas_duration` use it). The fourth round: a time column pandas holds as dates (Excel date cells) is read as dates, not as nanoseconds (`rainfall._parse_times`, parsed once and handed to `_seconds`); a row whose time is the name of the time column is a repeated header wherever it is; ten digits whose rows lie more than a day apart as dates are Unix seconds too (a jittering logger); a DWD value covers its own period (`AGENCY_COLUMNS` carries it; `dwd_day_windows` ends each day by its own rule, so the change of April 2001 leaves 20 minutes that belong to no day) and a row such a file does not have becomes a gap (`_with_holes`); in a serial run with the listing printout off TELEMAC prints neither the boundary statement nor the balance blocks (`bilan.f` prints under the same switch), so a closed domain is never misjudged; the docstrings of the hydrology mode are unwrapped, one line per paragraph, as the user's rule asks.

**The second example, `cases/example-agrohydrology/` (2026-10-25, the user's order: "use these cases to generate one or two example cases (you may want to merge these two models into one)").** The user placed two TELEMAC models of one arable field in `cases/agrohydrology/ks_0.61mmh/` and `ks_2mmh/` (untracked; never `git add` that folder: its PNGs and `.cas` are not ignored) and said their boundaries were wrong. What was found: the two differ in the soil only (Ks 0.61 / 2 mm/h in the geometry, theta_i 0.2 / 0.32, theta_s 0.4 / 0.56, suction 0.1 m, TELEMAC's Travert Green-Ampt, FV scheme 5, Strickler 30, 8 h, the same hyetograph of 42.13 mm in 7 h); the coordinates are EPSG:25832 (13.117 E, 48.498 N, Lower Bavaria; the QGIS project says WGS84, which is wrong), and the mesh bottom is the Bavarian open DGM1 (tiles `803_5379`, `804_5379`, `803_5380`, `804_5380` from `download1.bayernwolke.de/a/dgm/dgm1/`, CC BY 4.0, attribution "Bayerische Vermessungsverwaltung – www.geodaten.bayern.de") interpolated to the nodes: 5 cm std, except 50 outline nodes and one 20 m pit in `ks_2mmh`; and every one of the 1,203 outline nodes was an open `5 4 4` with depth 0, also the upper edges. So the example is **merged into one**: the field (mesh outline simplified by 0.5 m), the DGM1 itself, the original `hyetograph.txt` unchanged, two soil tables (`soil-ks-0.61.csv` in the case, `soil-ks-2.csv` for step 5 of the guide), Strickler 30, a 2 m mesh (16,600 nodes against 61,300), Sadeghi instead of Travert. The research inputs are in `cases/agrohydrology/user-sources/` (gitignored), written by a reconstruction script that is not tracked (it reads the untracked models); the commit message holds its rules. **The field is no catchment**: routed over the DGM1 from its outline (the checkup's priority flood at 1 m), 78 % drains over the north edge (toward a creek), 11 % over the west edge (a steep bank) and 9 % over the southeast edge (a furrow 5 m outside); those are the three outflow lines (bins of 10 m with more than 50 m2 of exits, the edge cells alone giving 10 to 17, runs joined over gaps up to 70 m, runs under 20 m dropped; a threshold of 40 joined the southeast and north edges over the east corner, a gap of 30 left a stretch of the southeast edge to the wall), and the checkup finds 0.3 % crossing walls, below its 2 %. About 2.3 ha upslope drain onto the field (mostly along the tillage lines of the field to the southwest); the example leaves that run-on out and says so.

**What the example needed in aXqua, each pinned in `tests/test_hydrology.py`.** (1) **`hydrology.outlet_condition: overfall`**, for an outline that is the lower edge of a field rather than a divide: the outflow lines get a level 1 m below the lowest node (`hydrology.overfall_level`), so TELEMAC's `bord.f` gives them a depth of zero and the FV kernel (`cdl_fv.f`) a dry ghost: water leaves as over a brink and none comes in. Measured on the example: `free` took in up to 2.7 m3/s through the north edge 16 min after runoff began (FV free = zero gradient, `HG=H1, UG=U1`, so an inward velocity is an inflow); `normal_depth` let 1.4 m3 in through the west line, whose lowest point is a corner the field drains away from (the outlet slope came out -0.037 and fell back to 1e-4, Z(0.44 m3/s) 0.65 m above the bed); `overfall` let nothing in and closed to 3e-7, the bulk results of the two equal (runoff coefficient 0.628, peak 0.123 m3/s). The FE kernel with `overfall` also took nothing in (1e-15), only drained slower. (2) **TELEMAC's own hyetograph file** (`#HYETOGRAPH FILE`, RAINDEF 3 of `RUNOFF_GREENAMPT`) is read as TELEMAC reads it (`rainfall.telemac_hyetograph`: two lines skipped, the depth of a line falls in the interval ending at its time, the first line's depth belongs to no interval); it used to stop with a pandas `ParserError`. (3) A hydrology case shows water from 1 mm (`config.HYDROLOGY_WET_DEPTH` as `hydrodynamics.wet_depth` unless the case sets one): with the river's 1 cm the depth map of sheet flow is nearly empty. (4) The hydrology report deletes the per-processor listings, as the steady analysis does, and `axqua <case>` names `axqua submit <case> --kind hydrology` as the next step instead of HydroBayesCal.

## Coordinate system - non-negotiable

**Everything is EPSG:25832 (ETRS89 / UTM Zone 32N), units in meters.** This was verified for the DEMs, all shapefiles, and the gauge metadata. Any new raster, mesh, or shapefile must use the same CRS, or downstream alignment (DEM interpolation onto the mesh, breakline snapping) will silently break.

Vertical datum varies across the gauge data (DHHN12 / DHHN2016 / "m NN" vs "m NHN") - check and reconcile datum before using gauge zero-point heights as model boundary elevations.

## Data layout and meaning

The Inn co-development dataset lives under `cases/example-Inn/user-sources/geodata/` (gitignored). The exact files evolve; what `cases/example-Inn/case-config.yml` currently points at:
- `dem-2020.tif` - baseline terrain (0.5 m DEM), `geodata.dem_initial`.
- `DEM-2025-20cm.tif` - 0.20 m high-res survey, `geodata.dem_target` (enables the morphodynamic/DoD path).
- `roi-kb15.gpkg` - the ROI / max-wetted-extent polygon (`geodata.boundary`), subreach KB15.
- `liquid-boundaries.gpkg` - inflow/outflow boundary segments (drives the `.cli`).
- `mesh-zones.gpkg` - polygons with a `Zone Name` (`channel`/`floodplain`) driving the anisotropic mesh (`geodata.mesh_zones`). `channel-centerline.gpkg` - the line channel cells are elongated along (`geodata.channel_centerline`).
- `roughness-zones.gpkg` - polygons with an integer **`Zone ID`** (1 = channel, 2 = floodplain) driving the friction zonation (`geodata.roughness_zones`); `roughness-table.csv` (`zone_id,ks`, e.g. `1,0.2` / `2,0.5`) maps each id to a Nikuradse ks (`geodata.roughness_table`). `interpolate_roughness` writes these as the per-node `FRIC_ID` + `BOTTOM FRICTION` and `steering` makes the matching `.tbl` (`<id> NIKU <ks> NULL`).
- `rating-curve.csv` - outflow `Q,WSE` stage-discharge curve (`boundaries.stage_discharge`); auto-synthesised from the geodata by `preprocessing.py` if absent.
- `iws-uas/`, `flowtracker2/`, `sediment/`, `muehldorf-gauge-XS/` - ortho/UAS imagery, FlowTracker velocity ground truth, GSDs, and gauge cross-section. `cases/example-Inn/user-sources/ground-truth/` holds the calibration ground-truth spreadsheets.

`-roi-clip.tif` files are generated clip outputs (from `preprocessing.py` / `axqua clip`), not raw inputs.

### Material / region classification (MATID scheme)

Region/zone polygons assign a max triangle area (mesh density) and a `MATID` (material zone) used later for roughness and sediment classes in GAIA. Base resolution is ~0.2 m.

| MATID | name           | max area (m²) | type        | meaning                              |
|-------|----------------|---------------|-------------|--------------------------------------|
| 1     | riverbed_fine  | 1.0           | riverbed    | fine bed (sand, silt)                |
| 2     | riverbed_coarse| 4.0           | riverbed    | coarse bed (gravel, cobbles)         |
| 3     | block_ramp     | 0.5           | block_ramp  | block ramp / high-roughness structure|
| 4     | gravel_bank    | 2.0           | gravel_bank | gravel bank / transition zone        |
| 5     | floodplain     | 25.0          | floodplain  | floodplain, vegetated overbank       |

### Boundary-condition gauge data (Bavarian LfU)

The upstream (discharge) and downstream (water level) boundaries are driven by gauge exports from the Bavarian LfU (gkd.bayern.de) - discharge [m³/s] at Kraiburg (Q ≈ 47 m³/s for the Nov-2020 reference period), stage [cm] at Wasserburg (upstream) and Mühldorf (downstream). When such CSVs are supplied via `boundaries.inflow` / `boundaries.stage_discharge`, mind the **German LfU CSV format**:
- UTF-8 **BOM** on the first line.
- **Semicolon** delimiter, **comma** decimal separator (e.g. `43,3`).
- 9 metadata lines (Quelle, station name/no., Gewässer, gauge coordinates as `Ostwert`/`Nordwert`, `Pegelnullpunktshöhe`), a blank line, then a header row (`Datum;"...[unit]";Prüfstatus`), then `"YYYY-MM-DD HH:MM";value;Geprueft` rows.
- Times are MEZ (CET). Stage is in **cm**; convert to m and add the gauge zero-point height for absolute water-surface elevation.

Read with `pandas`: `pd.read_csv(path, sep=';', decimal=',', skiprows=10, encoding='utf-8-sig')`.

### Ground-truth & calibration data (`cases/example-Inn/user-sources/ground-truth/`)

Field measurements that become **calibration targets** for HydroBayesCal, ingested by `ground_truth.py`. The canonical input is the tidy multi-tab table (below); it is authored by the user (`ground_truth.measurements`), **compiled by aXqua** from raw sources declared in `ground_truth.sources` (a list of `{category, kind, values, positions, join_key}`), or - the recommended, consistent route - compiled from the **calibration-target template** (`axqua targets <config>` → `user-sources/ground-truth/calibration-target-data.xlsx`, referenced under `ground_truth.targets` with per-tab position layers `hydraulics_positions`/`sediment_positions`; `src/axqua/targets.py`, tests in `tests/test_targets.py`). The template's rows are keyed by **unique IDs** joining the point gpkg/shp layers (any CRS, reprojected on ingest; explicit x/y win); its `hydraulics` tab carries u_x/u_y/u_z + fluctuations u_x'/u_y'/u_z' with auto-derived U_h/U_h'/TKE (live Excel formulas, recomputed on ingest → tidy `u_mag`/`u_mag_std`/`tke`), water depth and bottom elevation - and is populated from SonTek FlowTracker2 exports by `src/axqua/flowtracker.py` (`read_flowtracker`/`fill_template_hydraulics`, tests in `tests/test_flowtracker.py`), auto-detecting the three real layouts (`.ft.sum`, TKE-stats, multi-sheet `FT_TKE_Summary`) keyed by each point's own ID; **the fluctuations u' are the sample standard deviation (`u std`/`Std Dev v'(x)`/σ), NOT the `VxErr` columns** (`VxErr` is the standard error of the mean ≈ std/√Npts) - where only a plain `.ft.sum` (VxErr + Npts, no std-dev) is given, u' is reconstructed as `VxErr·√Npts`; `write_target_template` drops a co-located runnable `extract_flowtracker.py` next to the xlsx that calls `fill_template_hydraulics`; its `morphodynamics` tab carries d16..d90 [mm → m] + fine fraction < 1 mm and auto-samples the **DoD raster into a per-point `dz` column** on ingest (the DoD→targets adapter); its `parameters` tab is a drop-down over `targets.PARAMETER_CATALOG` (verified TELEMAC-2D/3D/GAIA keywords: friction zones prefilled with current ks, CLASSES SHIELDS PARAMETERS, MINIMUM VALUE OF DEPTH, VELOCITY DIFFUSIVITY, secondary-currents coefficients, GAIA transport knobs, ...) with min/max test ranges + tips, ingested by `targets.read_target_parameters` and merged over `calibration.parameters` in `emit_hbc_config` (template wins; `calibration.merged_parameters`). The **hydraulics/FlowTracker path is also implemented** (`kind: flowtracker` joins `.ft.sum` values to a DGPS position layer; `kind: points` reads a layer that already carries quantities). **Still to build:** the sediment/GSD adapter into GAIA `sediment_classes` (the GSD values now land in the tidy `morphodynamics` tab but are not yet folded into the GAIA `.cas`).

**Positions vs. values are split across two folders, joined by `ID`/row order:**
- Measurement **positions** are point shapefiles under `cases/example-Inn/user-sources/geodata/` - and are in **different CRSs than the project's 25832, so they must be reprojected on ingest**:
  - `geodata/flowtracker2/dgps-flowtracker-day{1,2}_utm33.shp` - EPSG:**25833** (UTM 33N). Columns `ID, E_25833, N_25833, WaterDepth, z` (z = bed elevation). 15 points (day1) / 30 (day2).
  - `geodata/sediment/MultiPAC-Mar2020-KB15.shp` - EPSG:**32632** (WGS84/UTM 32N). `name` = Surface/Subsurface. NB its `x`/`y` *attribute* columns are swapped vs the geometry - trust the geometry.
- Measured **values** live under `cases/example-Inn/user-sources/ground-truth/`:
  - **Hydraulics - `hydraulics/FlowTracker2-KB15-day{1,2}.xlsx`**: SonTek FlowTracker2 `.ft.sum` exports for KB15. One sheet; row 0 = metadata (total `DISCHARGE` [CMS], reference gauge), row 1 = headers, row 2 = units, rows 3+ = one vertical each (joins 1:1 by `ID` to the DGPS shp). Key columns: `MeasD`/`FinalD` depth [m]; `VelX/VelY/VelZ` [m/s] (+ `VxErr/VyErr/VzErr`) → velocity components / scalar velocity.
  - **Sediment - `sediment/GSDs-Uni-Stuttgart.xlsx`**: surface & subsurface grain-size distributions (cumulative + fractional) with d65/d84; feeds GAIA `sediment_classes`.

**Target tidy model (generic, source-agnostic):** a multi-tab table - one tab per category (`hydraulics`, `sediment`, …), first 3 columns `x, y, z` (in the project CRS 25832), then quantity columns (FlowTracker hydraulics → `u, v, w, u', v', w', h`). FlowTracker is only one possible source; many ground-truth sources are conceivable, so the reader stays generic and per-source adapters feed it.

**Topographic change**: the DEM-of-Difference (`dem.dem_of_difference`, dem-2020 vs DEM-2025-20cm) is the bed-change ground truth for the GAIA / topographic-change calibration. It is produced in pre-processing when `dem_of_difference.enabled` (the `inn-2020-25` case enables it, 2020→2025), clipped to the ROI and thresholded by a **minimum level of detection** (propagated survey uncertainty `t·√(u_i²+u_t²)` or an explicit `min_lod`; sub-LoD change masked/zeroed) - see stage 1 above and the `dem_of_difference` config block. The DoD raster is **not yet** turned into per-point HydroBayesCal targets (the remaining adapter).

**xlsx gotcha:** these *FlowTracker/GSD* files break `openpyxl`'s style parser (`PatternFill ... unexpected keyword 'extLst'`), so `pandas.read_excel` fails on them on every available env. Read them by unzipping the workbook and parsing `xl/worksheets/sheet1.xml` + `xl/sharedStrings.xml` directly (the `.ft.sum` layout is stable), or with a defensive openpyxl wrapper - don't assume `read_excel` works on these inputs. (`openpyxl` itself **is** in `axqua-env` - `convergence.ConvergenceReport.to_xlsx` uses it to *write* the styled convergence report fine; the issue is only *reading* those specific styled inputs.)

## Working conventions

- Large rasters (the DEMs/orthos run to hundreds of MB) - don't open them blindly; use `gdalinfo`/`rasterio` to read headers, and window/downsample for any processing.
- Keep raw input data immutable. Generated artifacts go under the configured phase dirs in `cases/example-Inn/axqua-case/` (preprocessing/ simulation/ postprocessing/ mesh-convergence/ calibration-validation/), not mixed into `user-sources/`.
- Per-case `user-sources/` (input data) and `axqua-case/` (produced artifacts) are large/local and gitignored; only the package, the case config + scripts, and docs are tracked.
