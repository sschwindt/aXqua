# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A TELEMAC hydro-morphodynamic model of a reach of the **Inn river in Bavaria, Germany**. The goal is a 2D depth-averaged hydraulic + sediment-transport simulation (TELEMAC-2D coupled with GAIA), set up automatically and calibrated with quantified uncertainty via [HydroBayesCal](https://github.com/Ecohydraulics/hydrobayescal).

**Overarching aim:** largely automate *both* sides of the workflow around HydroBayesCal - **pre-processing** (geodata → ready TELEMAC case) and **post-processing** (field **ground-truth** → calibration targets + result extraction). Pre-processing (stages 1–5) is built for the 2D hydraulic path; the **post-processing / ground-truth ingestion is the active frontier** (turning FlowTracker velocity/depth, grain-size distributions, and DEM-of-Difference topographic change into the calibration-points CSV and GAIA inputs HydroBayesCal consumes). See "Ground-truth & calibration data" below.

Each case lives in `cases/<name>/` and tracks only its case config and workflow scripts (`cases/case-template/` is the data-free starting point, `cases/example-Inn/` the worked example). Input data live in `user-sources/`, produced artifacts in `axqua-case/`, split by phase: `preprocessing/`, `simulation/`, `postprocessing/` (with `mesh-convergence/`, `vertical-convergence/`), `calibration-validation/`; each phase's script writes its outputs and its `axqua.log` into its own subfolder. Both folders are **gitignored** (plus a safety net of binary/geo extensions), and `.github/workflows/file-size-limit.yml` fails any push/PR with a tracked file over 20 MB. Don't assume the data files are present in a fresh checkout. All config paths resolve relative to the config file's directory.

## The `axqua` workflow

`axqua cases/example-Inn/case-config.yml` runs a 5-stage pipeline (`src/axqua/pipeline.py`):

1. `dem.py` - reproject + clip the initial (and optional target) DEM to the ROI boundary. When `dem_of_difference.enabled` (or `morphodynamics.enabled`), also computes the **DEM-of-Difference** (`dem.dem_of_difference`, `dem_target - dem_initial` on the ROI-clipped initial grid) thresholded by a **minimum level of detection** (`dem.resolve_lod`): an explicit `dem_of_difference.min_lod`, else the propagated survey uncertainty `t·√(uncertainty_initial² + uncertainty_target²)` (`dem.propagated_lod`, `t` from `confidence_level`); sub-LoD cells are masked to nodata (`mask_below_lod`) or zeroed, and the net/erosion/deposition volumes are logged. A precomputed `geodata.dem_of_difference` short-circuits the computation.
2. `mesh.py` + `selafin.py` - gmsh triangular mesh; DEM interpolated onto nodes; geometry written as SELAFIN with a `FRIC_ID` per-node variable (so no separate ZONES FILE is needed). The geometry is written in **double precision** (SERAFIND); single precision collapses sub-metre cells on UTM coordinates (see `selafin.py` design point). `build_mesh` prunes gmsh's geometry/1D-only nodes to triangle-referenced nodes (no orphans/duplicates), enforces consistent CCW winding, then runs `mesh_quality.assess_quality` (logged via `log_report`, stored on `Mesh.quality`). The mesh boundary is walked to build IPOBO, which **must** stay consistent with the `.cli` row order. **Two meshing strategies** (auto-selected): *anisotropic* (when `geodata.mesh_zones` + `geodata.channel_centerline` are set) types each mesh-zone polygon `channel`/`floodplain`/`refinement` (by `Zone Name` substring) and sizes it by its own `Max Edge Length (m)` field - channel cells elongated along the centerline, floodplain/refinement near-equilateral - via a metric-tensor background view + gmsh **BAMG** (`Mesh.Algorithm=7`); *isotropic fallback* uses `default_size`/`breakline_size`/`region_sizes` distance fields. See "Meshing" below.
3. `boundary.py` - classify contour nodes against the liquid-boundary lines and write the `.cli`. The lines come from `boundaries.liquid_boundaries` (a line layer whose `Type (inflow/outflow)` field - note the Inn file's typo `Type (inflow/outlfow)`, still detected - tags each line `inflow`/`outflow`; several of each allowed) and must coincide with the mesh-zone outer bounds. Codes: solid wall `2 2 2` (every non-liquid outer node), inflow `4 5 5` (prescribed Q, depth free - `LIHBOR` must be 4 not 5, else the inflow depth is forced to the inflow's PRESCRIBED ELEVATIONS slot of 0 and TELEMAC's DEBIMP aborts on a dry inflow), outflow `5 4 4` prescribed-elevation (the default `boundaries.outflow_condition: elevation`, a fixed WSE from `boundaries.prescribed_elevation`; or `stage_discharge` for a WSE from the rating curve at the simulated Q) or `4 4 4` free/Neumann (`outflow_condition: free`, needs no WSE). Matching tolerance is tied to the local edge length (anisotropic: ~2×`floodplain_size`). If total inflow- vs outflow-node counts differ by >10%, a stability-risk warning is logged.
4. `steering.py` - friction `.tbl` (one row per friction zone: `<id> <LAW> <coef> NULL`, ends with `END`; comments only on `*` lines - rows come from `friction.zones`/MATID or, failing that, the roughness table as `<Zone ID> NIKU <ks> NULL`) and the Telemac2d `.cas`; GAIA `.cas` when enabled. The **default solver is the classic finite-element kernel** (`hydrodynamics.finite_volumes: false`); set it true for the HLLC finite-volume kernel (robust on transcritical wetting/drying but constant-viscosity only). The **turbulence model is auto-selected** (`hydrodynamics.turbulence_model: auto`) by `steering.select_turbulence_model(cfg, mesh)` from the channel cell size relative to the turbulence length scale (the flow depth) and the velocity guess `initial_velocity_guess` (U≈1 m/s): **Smagorinski LES (4)** when the mesh resolves ≥80% of the TKE (`dx/L ≤ 0.2^1.5`, ~11+ cells/L - the LES validity gate), **k-epsilon (3)** at moderate resolution (≥~4 cells/L), **Spalart-Allmaras (6)** on coarse meshes; an explicit int/name overrides, and finite volumes force model 1. The **initial run is always steady** (`steady2d.cas`). The FE numerics are written **compute-stable by default** to keep the wetting/drying steady march from exploding: `time_step` is only a conservative CFL **start** step (0.25 s) while `desired_courant` (0.30) drives the adaptive marching step, `IMPLICITATION FOR DEPTH/VELOCITY` 0.80 (config `implicitation`), `FREE SURFACE GRADIENT COMPATIBILITY` 0.9, `DISCRETIZATIONS IN SPACE : 11;11` (linear FE, required by the distributive advection scheme 14), `NUMBER OF SUB-ITERATIONS FOR NON-LINEARITIES`/`MAXIMUM NUMBER OF ITERATIONS FOR ADVECTION SCHEMES`, `H CLIPPING : NO`, and a raised k-epsilon solve budget (`MAXIMUM NUMBER OF ITERATIONS FOR K AND EPSILON`, config `max_keps_iterations`). The graphic printout is `'U,V,S,B,H,M,Q,F'` plus `K,E` (TKE + dissipation) **for the k-epsilon model (3)**. **Time bound:** with the default `variable_timestep` the run is capped by `DURATION` (the explicit `hydrodynamics.duration` in seconds, else the `n_time_steps × time_step` fallback - so a small CFL start step no longer shrinks the simulated time), **not** `NUMBER OF TIME STEPS` - the latter does **not** terminate a variable-dt run (the CFL-driven dt is unknown a priori), so it would otherwise be unbounded. Convergence is judged by the **boundary-flux balance** (`initial_run.py` → `axqua.flux_convergence`), not by the solver. **The steady-state auto-stop is OFF by default** (`hydrodynamics.stop_if_steady: false`) and is hard-suppressed whenever `variable_timestep` is on: TELEMAC's `steady.f` stops when the change between **two consecutive time steps** falls below `STOP CRITERIA`, but that is an **absolute per-step** change (order **H ; (U,V) ; tracers** in `steady.f`; the dico's English help listing (U,V) first is wrong), and with the tiny CFL dt it false-fires during a slow transient (e.g. a low-Q reach still filling from a dry start) **long before the fluxes balance** - the run halts far from steady state (the symptom: it stops with inflow ≠ outflow). It is emitted only for a steady **fixed-step** run (`variable_timestep: false`, where a per-step change is meaningful), never for the unsteady run, and **TELEMAC-3D has no equivalent keyword**. When `boundaries.inflow` carries a *varying* hydrograph, `pipeline.run` additionally writes `unsteady2d.cas` (DURATION from the series) plus a TELEMAC liquid-boundaries file (`inflow-hydrograph.liq`, `Q(t)` per inflow / `SL(t)` per prescribed-elevation outflow via `steering.write_liquid_boundaries`). The steady inflow Q comes from `boundaries.prescribed_flowrate` (the optional `boundaries.inflow` series, read by `hydraulics.py`, is only for a varying hydrograph / unsteady case). The outflow water-surface elevation is needed for the prescribed-elevation conditions: the default `boundaries.outflow_condition: elevation` uses `boundaries.prescribed_elevation`, while `stage_discharge` interpolates `boundaries.stage_discharge` (a Q-h CSV; one pair suffices for steady) at the simulated Q; `free` prescribes nothing. When no measured rating curve exists, `axqua.rating.generate_stage_discharge` (CLI: `axqua rating`) synthesizes one from a Manning `n`/Strickler `Kst` and a trapezoidal channel geometry by inverting Manning's normal-flow equation; `rating.synthesize_outflow_rating(cfg, Q)` derives the geometry from the case data (width = outflow liquid-boundary line length, bed = DEM thalweg along it, slope = reach slope from the DEM along the centerline, roughness = `friction.boundary_*`) and `cases/example-Inn/preprocessing.py` (and the convergence-study script) call it to auto-generate `boundaries.stage_discharge` when missing. The lateral-boundary friction keywords (`LAW OF FRICTION ON LATERAL BOUNDARIES` / `ROUGHNESS COEFFICIENT OF BOUNDARIES`) come from `friction.boundary_law` / `boundary_coefficient` (Inn: Strickler 38).
5. `ground_truth.py` + `calibration.py` - compile the configured `ground_truth.sources` into the **tidy multi-tab table** (`ground_truth.compile_ground_truth`, written to `preprocessing_dir/ground-truth.xlsx` unless `ground_truth.measurements` overrides), then turn it into `measurements-calibration.csv` and the HydroBayesCal `config_Telemac.py` (both in `calibration_dir` = `calibration-validation/`).

`pipeline.run()` returns an `Artifacts` dataclass listing every produced path; `cli.py` logs these. The public API is `__all__` in `axqua/__init__.py` (resolved lazily; see Package structure). `mesh.build_mesh(cfg)` (no DEM) yields a bare mesh; `interpolate_elevations(mesh, dem, decimals=4)` fills the bottom from a raster (rounded); `write_mesh(mesh, path)` writes a geometry SELAFIN. These low-level helpers let you build a mesh programmatically; the worked example's `preprocessing.py` instead drives the full `pipeline.run` build (writing `geometry.slf` etc. into `simulation/`; see the workflow below).

### Meshing (stage 2)

Documented in `src/axqua/solvers/telemac/CLAUDE.md` (gmsh + BAMG anisotropic meshing, aspect-ratio cap, BAMG retry ladder, quality assessment, isotropic fallback, mesh-zones vs roughness-zones). **The anisotropic mesh is not reproducible run to run** (~0.4 % node-count spread from BAMG retries): never byte-compare `geometry.slf` / `boundaries.cli` / `initial-conditions.slf` between runs; regression-test on mesh statistics within ~1 %.

Key design points:
- The build runs in its **own** `axqua-env` conda env (gmsh/geopandas/rasterio); it does not import TELEMAC's Python. `env.py` *sources* `telemac.pysource` (the `pysource.*.sh`) in a subshell for any solver/SELAFIN call. The config's `telemac.pysource` must point at the real script (e.g. `/home/modelling/telemac-v911/telemac-mascaret/configs/pysource.debian12.sh`).
- Friction zonation has two routes: (a) the **roughness-zones** route - `geodata.roughness_zones` (`Zone ID`) + `geodata.roughness_table` (id→ks) drive the per-node `FRIC_ID` and `BOTTOM FRICTION` via `interpolate_roughness` (preferred for the Inn case; see the Meshing section); (b) the older **MATID** scheme (1 riverbed_fine … 5 floodplain; see table below) carried by `geodata.region_points` + `geodata.region_table` and/or `friction.zones` in the config → friction `.tbl` rows and `zone<MATID>` calibration parameters. Either way HydroBayesCal perturbs the coefficient column of the `.tbl`. `steering.write_friction_tbl` builds the `.tbl` in priority order: explicit `friction.zones` (MATID) > the roughness table (one `<Zone ID> NIKU <ks> NULL` row each) > a single default zone - so the `.tbl` rows always match the geometry's per-node `FRIC_ID`.
- `src/axqua/selafin.py` is a self-contained big-endian SELAFIN writer (plus a `read_slf` reader for results); its output is validated against TELEMAC's own `data_manip.formats.selafin.Selafin` reader in the tests.
- **Logging** (`src/axqua/logsetup.py`): each script/phase writes a compound, timestamped `axqua.log` into its **own output folder** (`setup_logging(path)` routes the `axqua` logger and captured Python warnings to it; file at DEBUG, console at the chosen level, append mode). the build (`pipeline.run`, called by `preprocessing.py`; and `initial_run.py`'s test run) -> `model_dir` (`simulation/`), the mesh-convergence study -> `mesh-convergence/` (scoped via the `logging_to(path)` context manager so it doesn't capture the per-level builds elsewhere). `log_step(name)` logs `START`/`DONE … in N.NNs` (or `FAILED … after N.NNs`) - wrapped around every pipeline stage and the heavy mesh/convergence sub-steps for per-step timing. `pipeline.run(..., log_to_file=False)` skips its own logfile (the convergence study's per-level builds use this so they log only to `mesh-convergence/axqua.log`). Tests reset handlers via an autouse fixture (`tests/conftest.py`).
- **Initial condition - DRY START (default) vs pre-wetting**: the initial run is a **dry start** by default. A *fully* dry bed (`ZERO DEPTH`) can't be used because TELEMAC's `DEBIMP` aborts at a prescribed-Q inflow when the inflow cross-section is dry (it scales the velocity profile by Q/Q1 with Q1 ∝ ∫H along the inflow; H=0 ⇒ Q1=0 ⇒ abort, even with the correct `4 5 5` code - see the inflow-cli memory). So `steering.write_dry_start_conditions` seeds a thin water **plug only on the nodes within `initialization.dry_start_extent` of the inflow line(s)** (default ~5 cells) to `dry_start_depth` (default 0.5 m, kept ≥ normal depth so the inflow stays subcritical) and leaves the rest of the domain **dry**; the `.cas` continues from this SELAFIN (`PREVIOUS COMPUTATION FILE` + `INITIAL TIME SET TO ZERO : YES`) and the flow wets the reach from the inflow. The inflow geometry comes from `boundary._load_liquid_lines`; with no inflow line it falls back to the analytical dry `INITIAL CONDITIONS`. **Pre-wetting** (`initialization.prewet_depth`, m) is the *alternative*: when set, stage 4 instead hotstarts the **`*channel*` mesh-zone** (`write_initial_conditions` + `mesh.channel_node_mask`) so the wetting front need not advance from the inflow - a large time saving, used by the **mesh-convergence study** (`INITIAL_DEPTH`, default 0.5 m) but **not** the initial run (which the user wanted dry). **How the seeded surface is built** is `initialization.prewet_mode`: the default **`normal-depth`** (`_normal_depth_prewet_depth`) cuts a real perpendicular cross-section every `prewet_bin_spacing` (20 m) along the centerline, samples it at 0.5 m, clips it to the channel zones, and seeds the **stage that conveys the case discharge** through it via `rating.stage_for_discharge` (the Keulegan conveyance inversion factored out of `section_rating`, so the seed and the outflow rating share one implementation), with the local bed slope from the gradient of the transect thalwegs rather than one reach slope. The seeded surface is `thalweg + prewet_fill x (normal stage - thalweg)`; **`prewet_fill` is 0.70, below 1 on purpose** - under-seeding is recoverable (the flow refills a pool in seconds), over-seeding is not, because a 2D model has neither infiltration nor evaporation and water perched above the converged surface becomes permanent stagnant film. `prewet_mode: constant` is the older `_longitudinal_prewet_depth` (a low bed percentile per bin + `prewet_depth`), also the automatic fallback without a centerline or a discharge; on the braided isar-2025 reach it seeded a median **0.28 m above** the converged surface and left 4694 m2 (35% of the wetted area) as film that had stopped draining. `prewet_min_depth` (0.05 m) additionally leaves a node dry rather than laying down a feathered margin (a seed film is exactly what stalls), and `drainable_prewet` still runs on top. **After every filter the inflow plug is re-imposed** (`_inflow_plug_mask`, same `dry_start_extent`/`dry_start_depth` as the dry start): none of the filters has any reason to keep the inflow cross-section wet, and the normal-depth seed is shallowest exactly at the upstream end, so without the guard `DEBIMP` aborts the run at t=0 on a dry inflow - which is precisely what the old over-seeding had been hiding. Sizes are validated in `tests/test_prewet.py`; the calibration is recorded in `cases/isar-2025/test-approaches.md` (R2). `pipeline.run` records whichever file in `Artifacts.initial_conditions`. A side effect of the dry start: while the domain is mostly dry the **k-epsilon / Spalart-Allmaras turbulence linear solve** is ill-conditioned, so TELEMAC's needlessly tight default accuracy (`ACCURACY OF K`/`EPSILON`/`SPALART-ALLMARAS` = 1e-9) is unreachable within its 50-iteration cap - the transient `GRACJG: EXCEEDING MAXIMUM ITERATIONS 50` warning, which is **benign** (it reaches ~1e-6, the run stays mass-conservative and self-heals once the reach wets). `steering` therefore writes `hydrodynamics.turbulence_solver_accuracy` (default **1e-6**, plenty for turbulence) for the k-epsilon (3) / Spalart-Allmaras (6) models, which converges the turbulence solve in fewer iterations.
- Calibration CSV schema (read by HydroBayesCal): `id, x, y, z, <QTY>_DATA, <QTY>_ERROR`, where `<QTY>` is a SELAFIN name (e.g. `WATER DEPTH`, `SCALAR VELOCITY`).

v1 covers the **2D hydraulic** path end to end; the **DEM-of-Difference** (with a level of detection) is implemented in pre-processing (`dem_of_difference` config block, `dem.dem_of_difference` / `dem.resolve_lod`), and **GAIA morphodynamics** is wired for simulation - `steering.write_gaia_cas` writes a damocles-valid GAIA steering file (transport modes + bed-process capacities: morphological factor, slope effect, secondary currents, active-layer stratigraphy, prescribed solid discharges) coupled to the steady, `unsteady2d.cas` and `unsteady3d.cas` runs (`morphodynamics` config block). What **remains an extension point** is the *calibration* side: turning the DoD into per-point topographic-change calibration targets and folding the GSD `sediment_classes` into GAIA from the ground-truth template.

### The per-case workflow

`cases/example-Inn/` holds the worked example for the Inn case, run against its `case-config.yml` as flat scripts (`mamba run -n axqua-env python cases/example-Inn/<script>.py`). The **workflow is three ordered steps**: (1) `preprocessing.py` builds the complete TELEMAC case into `axqua-case/simulation/` (via `pipeline.run`, at the steady discharge from **this case's** `case-config.yml` `boundaries.prescribed_flowrate` - the shared `axqua.prepare_steady_inputs` helper reads the inflow Q and outflow-stage prescription from the config rather than a value hard-coded in the script, synthesizing a constant inflow series + outflow rating only if missing) - the final mesh `geometry.slf`, `boundaries.cli`, `friction.tbl`, `steady2d.cas`, plus the HBC artifacts in `calibration-validation/`; (1b) `initial_run.py` test-runs *exactly that* `steady2d.cas` once (`axqua.run_solver_streaming` → `TelemacRuntime.run_solver` with `-s --nozip`, no rebuild) to confirm it does not crash - the solver's listing is **streamed live** to the terminal (via `TelemacRuntime.run`'s `on_line` callback, so the run isn't silent) with a **progress bar** of simulated time vs `DURATION` (`axqua.progress.SolverProgress`; the CFL-adaptive dt makes the *number* of steps unknown a priori, so progress is measured against the simulated-time cap `expected_duration(cfg)` = `hydrodynamics.duration` else `n_time_steps × time_step`, with the live iteration count shown). A module-level **`NCSIZE`** at the top of `initial_run.py` overrides `telemac.n_processors` for this one test run (leave it `None` to use the configured core count). The run then gets a **boundary-flux convergence analysis** (`axqua.flux_convergence`) that reads the `.sortie` (needs `PRINTING CUMULATED FLOWRATES : YES`, already emitted) and writes four files into `simulation/` - `extracted-fluxes.csv` + `flux-convergence.png` (per-boundary fluxes) and `convergence-rate.csv` + `convergence-rate.png` (the relative imbalance `|Q_in|-|Q_out|`/`|Q_in|` and its convergence rate). The listing is parsed by **`axqua.sortie`** (`read_sortie` / `latest_sortie`): each `BALANCE OF WATER VOLUME` block is read as a unit and its time taken from the `RELATIVE ERROR IN VOLUME AT T =` line *inside* it, so times, volumes and fluxes cannot drift out of alignment and no sample is fabricated. This replaced a dependency on the external **pythomac** package, which cannot be vendored (it is GPL-3 and its parser derives from TELEMAC's GPL-3 `postel`, while aXqua is BSD-3) and whose package boundary forced several adapters: the printout spacing had to be back-calculated (a CFL-adaptive run has no fixed `period*time_step`), `convergence-rate.csv` had to be written separately (only the `.png` was produced), and the rate plot had to be swapped out whenever the rate was undefined. Now `flux_convergence` owns the maths (`relative_imbalance`, `convergence_rate`, `convergence_index`) and both plots; the converged time and iteration count are read straight off the listing rather than estimated, and the convergence figure always shows the relative imbalance (with the tolerance marked) plus the rate where it is defined - during the filling phase the rate is undefined everywhere, which is exactly when one needs to see the imbalance. **Tolerance grades** (`hydrodynamics.flux_tolerance`, default **1e-3**): the imbalance is *relative*, so the discharge/depth/velocity read off a steady run inherit it directly - 0.1% is far inside field-measurement uncertainty and inside the 5% the mesh-convergence study accepts, so 1e-3 is the right grade for a hydraulic result. The stricter **1e-4** (`HOTSTART_TOLERANCE`) is for a **hotstart seed**, where the residual transient is inherited by every perturbed calibration run rather than averaged out; 1e-6 is a rarely-worth-it validation grade. The *absolute* steady criterion is derived as `flux_tolerance x prescribed_flowrate` (so the hotstart gate means the same on a 2 m3/s side channel as on a 200 m3/s river) rather than a fixed 1e-3 m3/s. The analysis also **deletes the per-processor `*_p0000N.sortie` copies** of a parallel run (only the merged main listing matters) and detects the **absolute steady window**: when `||Q_in|-|Q_out||` stays below 1e-3 m³/s over 10 consecutive listing printouts (`flux_convergence.find_steady_window`; on a noisy steady state, whose instantaneous imbalance oscillates above that floor, the 10-printout *mean* is the fallback, flagged as such), a **`hotstart2d.cas`** is generated next to the steady case via `steering.write_hotstart_cas` - it continues from `r2d.slf` (`PREVIOUS COMPUTATION FILE`, clock reset), renames the results to `r2d-hotstart.slf` (no self-clobber), caps `DURATION` at that steady time, and keeps the constant Q/H prescriptions unchanged. A balanced flux budget says nothing about **where** the water is, so `initial_run.py` additionally writes `wetting-report.csv` and `outlet-profile.csv` via **`axqua.wetting`**: `wetting_report` splits the wetted area into *active* flow (H > 0.05 m, |U| > 0.15 m/s, in the largest connected body), *stagnant film* (wet but under 0.05 m/s) and *isolated puddles*, attributes each to the pre-wet seed when the initial-conditions SELAFIN is passed, and samples earlier frames to say whether the film is still draining or has **plateaued** - the failure mode a longer run cannot fix, since a 2D model has neither infiltration nor evaporation (isar-2025: 4694 m2 of film, 75% seeded, shrinking 1.8% over 3100 s). `outlet_profile` bands the actively flowing nodes by distance from the outflow line, reports the discharge-weighted free surface / depth / Froude per band, and compares the near-boundary surface slope with the reach's own to return `backwater` (the prescribed stage is holding the level up over ground that should be dry) / `drawdown` / `neutral`. The report's wetted threshold is `hydrodynamics.wet_depth` (0.01 m) - a **reporting** convention, since on a bed with ks 0.05-0.5 m water 5 mm deep stands *inside* the grain roughness rather than flowing over it (on isar-2025 that band was 13% of the wetted area but 0.16% of the volume); use the same filter in ParaView so the picture and the report agree. Water an external source holds in place is passed in via `supported=` and reported as its own category, excluded from *film* and *isolated puddles* - otherwise a legitimately wet water-table pool reads as a defect. This ends preprocessing; (2) `mesh_convergence_study.py` runs the grid-independence study; (3) `run_Bayes_cal.py` calibrates the built case with HydroBayesCal. An **optional 3D extension** runs after step 1b (and after step 2 fixes the horizontal mesh): `add3d.py` writes the three 3D steering files (hydrostatic flux-convergence check, non-hydrostatic steady, unsteady), then `vertical_convergence_3d.py` runs the vertical-layer (`dz`) grid-independence study - both are documented in the `hbc-calibration` skill. Step 3 compiles the FlowTracker velocity ground truth into the calibration-points CSV (the point velocity, measured at **0.6·h**, approximates the depth-averaged velocity, so it is compared to TELEMAC `SCALAR VELOCITY` = sqrt(U²+V²) built from the **horizontal** components only), ensures the `.cas` outputs `SCALAR VELOCITY` (graphic-printout `M`), emits `config_Telemac.py`, and stages and launches HydroBayesCal's `bal_telemac.py`. **HydroBayesCal is a pip dependency** (`pip install 'axqua[calibration]'`, requiring `>=1.4.4`: 1.4.2 ships the drivers *with* the package, 1.4.4 makes the multi-flow driver honor the config's `extraction` block): the driver is copied out of the installed package by `hydroBayesCal.copy_driver` and run in aXqua's own environment, so there is no checkout directory to point at and no second conda env to name. It is an *optional extra* because its surrogate stack (bayesvalidrox, gpytorch, scikit-learn) is irrelevant to building or running a TELEMAC case, so `bayescal.require_hbc` imports it lazily and explains the install if missing. The driver is still a subprocess - it is a script with an `argparse` main() that must run with TELEMAC sourced, and sourcing mutates the environment - but under `sys.executable`. Pass `checkout=` to develop against an unreleased driver; `--prepare-only` writes the CSV+config without launching - everything into `calibration-validation/`. HydroBayesCal reads the CSV's first four columns by position (id, x, y, z) and `<QTY>_DATA`/`<QTY>_ERROR` by name; `_ERROR` is a site-specific error in physical units added in quadrature to its built-in 10% measurement + 10% surrogate error.

### The OpenFOAM free-surface extension

### Fine sediment over a bed that stays in place (`fine_sediment`, `solvers/openfoam/sediment.py`)

**Morphodynamics with OpenFOAM is not a moving bed.** It is Olsen's `sediDriftFoam2` with the bed and the water surface kept where they are: the concentration of one grain size, its settling onto the bed and its pick-up, and from them the mass of fine sediment the bed takes up per area, and for a bed layer of given thickness the change of its share of fines. The reason is the user's direction of 2026-10-12 for the Isar: "there was no elevation change for sure (any elevation change is a DGPS artifact -- only fine sediment fraction change is real)". **Never use a DEM of difference, a bed elevation change or a scour depth of the Isar as ground truth, as a calibration target or as a result worth showing.** A bed that moves stays TELEMAC and GAIA (`morphodynamics`). The case block is `fine_sediment` (grain size, concentration at the inflow in kg/m3, `pick_up: suspended | bedload | off`, and optionally a period with the bed layer the result is booked into); the job kinds are `openfoam-sediment-build` and `openfoam-sediment`; a case that asks for it uses the OpenFOAM backend also without an `openfoam` block. What the solver requires of a mesh and what running it on the Isar found (a wall distance that turns negative on a sloping bed, one roughness for the bed, the budget) is in `src/axqua/solvers/openfoam/CLAUDE.md`. Three things are open and are the user's to decide: the supply of fines (the solver's pick-up assumes a bed that consists of them, so the Isar is run with `off`), the grain size and the concentration at the inflow (no measurement of either is in the case), and whether the published example gets the block.

### Mesh-convergence study and build prerequisites

The mesh-convergence study (`axqua/convergence.py`, r = 1.3 four-mesh ladder, GCI verdict, resumable and auto-refining) is documented in `src/axqua/solvers/telemac/CLAUDE.md`; read it before changing the study.

A build needs a **ROI boundary polygon** (`geodata.boundary`, a closed polygon/polyline in EPSG:25832; the Inn example uses `cases/example-Inn/user-sources/geodata/roi-kb15.gpkg`) and `boundaries.liquid_boundaries` (both set in the Inn config). ## The config schema: round-tripping, classification, and typed errors

**`dump_config(cfg, path)` (`config.py`) is the counterpart of `load_config`**, and exists because anything that *edits* a case - a form in the planned QGIS plugin, a migration, a scripted sweep - has to put the result back. It goes through the dataclass rather than rewriting the YAML text, which **loses comments but cannot produce a config that will not load**; a comment that survives an edit it no longer describes is worse than no comment, and the annotated prose lives in `cases/case-template/case-config.yml`. Paths are written **relative to where the file will live** (`base=`), so `axqua migrate -o elsewhere/case.yml` does not silently break every relative data path, while a path outside the case tree (a solver install) stays absolute. Guarded by a parametrized round-trip test over **all ten** case configs in the repo: `load(dump(cfg))` is field-by-field identical.

**`axqua migrate <config> [-o out | --in-place]`** writes a config back in the current schema - loading already applies every compatibility mapping, so this just makes the file say what aXqua actually read and stops the deprecation warnings. `--in-place` keeps a `.bak`. `--to-case` derives the name of the new file and does not write over a file of that name that exists (it may have been edited since; naming it with `-o` replaces it). For a config that is a case file already the derived name is the file itself, so it is rewritten as `--in-place` does, and neither writes machine settings into a case file.

**`core/schema.py` states which settings are shared intent and which name a solver keyword** - as *data*, because a form-based editor cannot guess. The rule: a fact about the reach or the modeling goal is `SHARED` (geodata, boundaries, friction, ground truth, structures, `mesh.channel_size`, `hydrodynamics.duration`); a knob of one code belongs to that code (`mesh.growth_ratio` is BAMG's, `hydrodynamics.implicitation` is Telemac2d's, `openfoam.max_courant` is interFoam's). Only the genuinely mixed blocks (`mesh`, `hydrodynamics`) are spelled out field by field, and only their SHARED entries - so "is this shared?" has to be answered deliberately. An unknown key classifies as SHARED, which fails safe for a form (showing a setting on the reach page is a smaller mistake than hiding it behind a solver the user has not enabled). Two tests keep the table from drifting away from the dataclasses it describes. **The fields have deliberately NOT been moved.** The plan folded `openfoam.cell_size` into `mesh.channel_size`, but `openfoam.cell_size_factor` now expresses the OpenFOAM lattice *relative to* the 2D channel size - the same shared-intent link, without pretending the two numbers are the same quantity (a per-zone anisotropic target edge length vs a uniform Cartesian spacing). The rest would be pure renaming: no behavior change, every case config touched, the artifact regression baseline invalidated. `LEGACY_KEYS` is the mechanism for doing it later without breaking a config - it maps dotted old key to new, is applied at load, and emits **one aggregated** warning rather than a per-key wall of text. Note `project.results_dir` maps to `calibration_dir`, **not** `model_dir`: the old single "results" folder is where the HydroBayesCal artifacts land.

**`core/errors.py`** gives failures a **stable machine-readable `code`**, an optional `subject` (the config key or layer the failure is about) and an optional `remedy`. Not decoration: a job record has to store a failure that survives serialization, a plugin has to put a message next to the field that caused it, and a batch has to decide what is worth retrying. Deliberately **five categories, one level deep** - `ConfigError` (fix the YAML), `GeodataError` (fix the data), `EnvironmentError` (fix the install), `SolverError` (read the listing), `MeshError` (change resolution) - because mirroring the module layout would produce thirty classes that callers catch by their base anyway. `ErrorRecord.from_exception` turns *any* exception into a JSON-safe record, labeling an unanticipated one `axqua.unexpected` rather than mislabeling it. Additive: existing `ValueError`s keep working.

## Validation: the calibrated model in another flow situation (`axqua/validation.py`)

**The user's rule, 2026-10-08: every dataset given to HydroBayesCal is calibration data, and validation needs a second dataset from another situation. No splits** - no leave-one-out, k-fold or random share, in the library, the plugin or the docs, because the points of one survey in one flow field are not independent. `calibration.validation` is a list of `ValidationSituation` (name, `sources` like `ground_truth.sources`, `prescribed_flowrate` or per-boundary `inflows`, `prescribed_elevation`, `duration`); a single mapping loads as a list of one.

**The validation run is the built steady case with other boundary values and nothing else** (`validation.build`): the as-built `steady2d.cas` is copied and patched in `TITLE`, `RESULTS FILE`, `PRESCRIBED FLOWRATES` / `ELEVATIONS` and the file names of what the calibrated values live in - a test asserts those lines and no others, so a difference to the measurements cannot come from a model that was built differently. The boundary arrays come from the same `steering._prescribed_arrays` and `liquid-boundaries.json` as the build (a total discharge keeps the split of the case; `inflows` gives each boundary its own), and the outflow level from `resolve_outflow_wse`, with the rating synthesized for the validation discharge by the case's own `rating_method` when the case has no measured curve. Under `outflow_condition: elevation` a situation without a level is refused: the calibration's level belongs to its discharge.

**The calibrated values are HydroBayesCal's joint posterior maximum** (`BAL_dictionary.pkl` -> `joint_optimum[-1]`, posterior mean for an older HBC), applied by HBC's own rules: `zone<N>` rewrites a row of a *copy* of the friction table, `f.<NAME>` a constant in a copy of the user Fortran folder, any other name a steering keyword. `gaia*` parameters are refused rather than ignored.

**The comparison reads the model on `geometry.slf` with the mesh's own triangles** (`compare`; see the single-precision note under post-processing), counts points outside the mesh and points that are dry in the model, and reports n, bias, relative bias, MAE, RMSE, correlation and the share within one and two measurement errors (the point's own error combined with `calibration.measurement_error` x value, as the calibration weighs it). The run's final flux imbalance is read from its listing and a run that had not reached the case's `flux_tolerance` says so. Outputs: `calibration-validation/validation/validation-<name>.{csv,json,png}`. It is the `validation` job kind (capability calibration, `study` verb, told from a calibration by `ValidationOptions.validate`); `axqua validation <case>` is what the plugin's form reads.

## Package structure: solver-agnostic core + pluggable backends

aXqua is structured so TELEMAC and OpenFOAM are **two backends behind one case
description**, rather than one tool with a second bolted on.

**Two rules, enforced by tests rather than intent** (`tests/test_capabilities.py`): nothing in `core` imports a solver, and the OpenFOAM backend never reaches into the TELEMAC backend. Both are checked by reading the source, so they hold even for imports that only happen inside a function. OpenFOAM *is* hotstarted from a TELEMAC result, but it reads it through the shared SERAFIN codec in the core - which is exactly why `selafin` sits there.

**Every historic import path still works.** `axqua/mesh.py`, `steering.py`, `pipeline.py` (14 of them) plus `selafin.py` and `openfoam.py` are **shims that alias through `sys.modules`**, not re-export modules: `axqua.mesh is axqua.solvers.telemac.mesh` is literally true. Re-exporting would have silently dropped every private name (tests import `mesh._parse_decimal`) and broken identity checks; aliasing means there is exactly one module object and no second surface to keep in step. Parametrized over all 16 in the tests.

**Both `solvers/*/__init__.py` resolve attributes lazily** (PEP 562), like the top-level package. Not decoration: each backend's `spec.py` is read by `axqua status` to build a capability table, and importing `axqua.solvers.telemac.spec` runs the package `__init__` first - so eager imports there would drag gmsh and numpy into a question that should cost nothing. Measured: `import axqua` 6 ms / 64 modules, a capability listing 30 ms with **zero** heavy modules.

**Capabilities and the `MODEL=` marker files (`axqua/core/capabilities.py`).** Every
case carries one marker per solver at its top level - `MODEL=TELEMAC_ENABLED`,
`MODEL=OPENFOAM_DISABLED` - whose **name** says whether *the case* declares that solver
(`cfg.declared_blocks`, so the filename means the same on any machine) and whose **body**
is a strictly parseable status table: `#` comments, `key = value` header, then fixed-width
rows after `[capabilities]`. Each capability is reported on **three axes**, kept apart
because they have three different fixes: `implemented` (does aXqua support it *for
this solver* - `yes` / `no` = not yet / `n/a` = category error, e.g. OpenFOAM has no
depth-averaged mode while its morphodynamics is merely unbuilt), `configured` (does this
case ask for it, from the config alone), and `built`/`run` (do the artifacts exist - pure
path checks, never a parse, so a status report is fast and cannot fail). Unanswerable
cells render `-`, never a confident `no`. The files are **generated and gitignored**
(`cases/*/MODEL=*`, with `cases/case-template/MODEL=*` committed as the documented
example): they report the *currently available* setup, which is local state like
`axqua-case/`. Refreshed by `pipeline.run`, by `openfoam.build_case` and by
`axqua status <config> [--check-env] [--full]`; `refresh_markers` never raises, since
a succeeded build must not report failure because a status file could not be written.

**The solver registry (`axqua/core/registry.py`).** A backend is described by a
`BackendSpec` - name, title, config key, the capability support matrix, and the
`built`/`run` path predicates - which is **metadata only**, deliberately separate from the
`SolverBackend` implementation that builds and runs. The spec modules
(`axqua/solvers/{telemac,openfoam}/spec.py`) are import-light by contract: they use
the standard library plus attribute access on a `Config`, and nothing else. That is what
lets `axqua status` - and, later, a QGIS plugin running inside the QGIS Python process
- answer "what can this case do?" without importing gmsh, rasterio, pandas or a solver.
Backends are discovered through the `axqua.solvers` entry-point group, with a
hard-coded built-in list as a fallback for source checkouts that predate the group, so
"add your own" and "use ours" are the same mechanism.

**`axqua/__init__.py` resolves attributes lazily (PEP 562).** `import axqua` went
from 505 ms / 652 modules to **21 ms / 64 modules**, and a capability listing imports
**zero** heavy modules - measured, and asserted in `tests/test_capabilities.py` from a
subprocess so the rest of the suite's imports cannot mask a regression. The public API is
unchanged (`from axqua import build_mesh` still works); `__all__` is written out
literally because linters and IDEs read it statically, and a test keeps it in step with
the `_EXPORTS` map.

## Data layout and meaning

The Inn co-development dataset lives under `cases/example-Inn/user-sources/geodata/` (gitignored). The exact files evolve; what `cases/example-Inn/case-config.yml` currently points at:
- `dem-2020.tif` - baseline terrain (0.5 m DEM), `geodata.dem_initial`.
- `DEM-2025-20cm.tif` - 0.20 m high-res survey, `geodata.dem_target` (enables the morphodynamic/DoD path).
- `roi-kb15.gpkg` - the ROI / max-wetted-extent polygon (`geodata.boundary`), subreach KB15.
- `liquid-boundaries.gpkg` - inflow/outflow boundary segments (drives the `.cli`).
- `mesh-zones.gpkg` - polygons with a `Zone Name` (`channel`/`floodplain`) driving the anisotropic mesh (`geodata.mesh_zones`). `channel-centerline.gpkg` - the line channel cells are elongated along (`geodata.channel_centerline`).
- `roughness-zones.gpkg` - polygons with an integer **`Zone ID`** (1 = channel, 2 = floodplain) driving the friction zonation (`geodata.roughness_zones`); `roughness-table.csv` (`zone_id,ks`, e.g. `1,0.2` / `2,0.5`) maps each id to a Nikuradse ks (`geodata.roughness_table`). `interpolate_roughness` writes these as the per-node `FRIC_ID` + `BOTTOM FRICTION` and `steering` makes the matching `.tbl` (`<id> NIKU <ks> NULL`).
- `rating-curve.csv` - outflow `Q,WSE` stage-discharge curve (`boundaries.stage_discharge`); auto-synthesised from the geodata by `preprocessing.py` if absent.
- `iws-uas/`, `flowtracker2/`, `sediment/`, `muehldorf-gauge-XS/` - ortho/UAS imagery, FlowTracker velocity ground truth, GSDs, and gauge cross-section. `cases/example-Inn/user-sources/ground-truth/` holds the calibration ground-truth spreadsheets.

`-roi-clip.tif` files are generated clip outputs (from `preprocessing.py` / `axqua clip`), not raw inputs.

### Material / region classification (MATID scheme)

Region/zone polygons assign a max triangle area (mesh density) and a `MATID` (material zone) used later for roughness and sediment classes in GAIA. Base resolution is ~0.2 m.

| MATID | name           | max area (m²) | type        | meaning                              |
|-------|----------------|---------------|-------------|--------------------------------------|
| 1     | riverbed_fine  | 1.0           | riverbed    | fine bed (sand, silt)                |
| 2     | riverbed_coarse| 4.0           | riverbed    | coarse bed (gravel, cobbles)         |
| 3     | block_ramp     | 0.5           | block_ramp  | block ramp / high-roughness structure|
| 4     | gravel_bank    | 2.0           | gravel_bank | gravel bank / transition zone        |
| 5     | floodplain     | 25.0          | floodplain  | floodplain, vegetated overbank       |

### Boundary-condition gauge data (Bavarian LfU)

The upstream (discharge) and downstream (water level) boundaries are driven by gauge exports from the Bavarian LfU (gkd.bayern.de) - discharge [m³/s] at Kraiburg (Q ≈ 47 m³/s for the Nov-2020 reference period), stage [cm] at Wasserburg (upstream) and Mühldorf (downstream). When such CSVs are supplied via `boundaries.inflow` / `boundaries.stage_discharge`, mind the **German LfU CSV format**:
- UTF-8 **BOM** on the first line.
- **Semicolon** delimiter, **comma** decimal separator (e.g. `43,3`).
- 9 metadata lines (Quelle, station name/no., Gewässer, gauge coordinates as `Ostwert`/`Nordwert`, `Pegelnullpunktshöhe`), a blank line, then a header row (`Datum;"...[unit]";Prüfstatus`), then `"YYYY-MM-DD HH:MM";value;Geprueft` rows.
- Times are MEZ (CET). Stage is in **cm**; convert to m and add the gauge zero-point height for absolute water-surface elevation.

Read with `pandas`: `pd.read_csv(path, sep=';', decimal=',', skiprows=10, encoding='utf-8-sig')`.

## Working conventions

- Two traps in the test suite itself: tests built on `git grep` (`test_no_tracked_source_or_test_hard_codes_a_home_directory`) see **tracked files only**, so a new file passes locally until it is committed - `git add` before the final run; and CI runs `pytest`, not `python -m pytest`, so the repository root is not on `sys.path` and `from tests.x import ...` fails there (import `from x import ...` like the other test modules do). The `tests` workflow had been red on `main` since at least 2026-10-03 for the second reason, which is how the first went unnoticed.
- Large rasters (the DEMs/orthos run to hundreds of MB) - don't open them blindly; use `gdalinfo`/`rasterio` to read headers, and window/downsample for any processing.
- Keep raw input data immutable. Generated artifacts go under the configured phase dirs in `cases/example-Inn/axqua-case/` (preprocessing/ simulation/ postprocessing/ mesh-convergence/ calibration-validation/), not mixed into `user-sources/`.
- Per-case `user-sources/` (input data) and `axqua-case/` (produced artifacts) are large/local and gitignored; only the package, the case config + scripts, and docs are tracked.
