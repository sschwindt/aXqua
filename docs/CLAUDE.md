# The documentation

Moved from the root `CLAUDE.md`; loaded when working under `docs/`.

## The documentation in three languages, on two hosts (`deploy.sh`, `docs/i18n/`, `docs/locale/`)

**Two hosts, by the user's decision of 2026-10-18** ("readthedocs.org is not compatible with my spaceship registrations"): GitHub Pages serves the branch `gh-pages` at `https://axqua.eu` with English at `/`, German at `/de/` and French at `/fr/`; `axqua.de` and `axqua.ch` forward to `/de/`, `axqua.fr` to `/fr/` (the user's order of 2026-10-18; the registrar settings are the user's), and Read the Docs keeps building the English pages from `main` for `axqua.readthedocs.io`. **`bash deploy.sh [--push] [--retranslate]`** in the repository root (modeled on the user's `hyhome-v2/deploy.sh`) builds the three languages with `docs/i18n/build_i18n.sh`, rsyncs `docs/_build/site/` into the gh-pages worktree (`DEPLOY_DIR`, default `../aXqua-gh-pages`, created with `git worktree add` when missing; `CNAME` axqua.eu and `.nojekyll` kept), and with `--push` commits the updated catalogs on `main`, **pushes `main`** (the user asked for that; it is also how the catalogs reach Read the Docs) and then commits and pushes gh-pages. It refuses uncommitted changes outside `docs/locale`, a `main` behind origin, and a diverged gh-pages. The environment is `axqua-docs` from `docs/i18n/environment.yml` (Sphinx, theme, Argos Translate with CPU torch), deliberately apart from `axqua-env`; `build_i18n.sh` finds it under the usual conda roots or takes `DOCS_PYTHON` (`mamba run` is avoided: in a non-interactive shell here it looks in `~/.local/share/mamba`).

**The catalogs are the translation memory**: `docs/locale/<lang>/LC_MESSAGES/<page>.po` (one per page, `gettext_compact = False`), tracked; Sphinx compiles `.mo` beside them (ignored). `docs/i18n/translate.py` writes them itself (no babel, no polib: own reader and writer, no wrapped lines, no locations, fixed header) and marks a machine entry `# machine translation: <engine> <hash>`, where the hash covers what was sent to the engine, the injected terms, their genders and the term repairs that apply: an entry goes to the engine again only when it is new, its English changed, or a glossary/termfix change concerns it. **An entry without that comment is a human review** and survives `--retranslate` while its English is unchanged. A run without `--docstrings` keeps the docstring entries the catalogs already have, and a machine entry whose new translation fails keeps its earlier text with its old hash, so the next run tries again (review of 2026-10-18: both used to be dropped, the first silently deleting reviewed API translations on every deploy). `recapitalize` changes only text outside literals, roles, links and single-asterisk labels, which it sets aside before cutting the text into sentences (they may hold `. ` themselves); where the markup does not pair up (a stray backtick or asterisk would reach over whole sentences) it protects per sentence instead. A kept-after-failure entry is listed in `failed-<lang>.txt` too, in a section of its own. The API reference (autodoc docstrings) stays English (`--docstrings` / `DOCSTRINGS=1` includes it), and so do list-of-references entries (paper titles). The full translation of both languages is about 4 minutes with 4 workers of 2 threads each (Argos takes every core per process otherwise); a normal deploy translates only what changed.

**What the first full runs found about Argos, each with its repair in `translate.py`** (pinned by `tests/test_docs_i18n.py`, which needs no engine): (1) Placeholders `@@N@@` come back spaced out or shortened (`@ @ 2 @ @`, `@1@@`); `SENTINEL_RE` takes those but must not eat the start of a neighboring placeholder or read `@@0@@ 3.5.0` as a placeholder 3; a placeholder that lost its number fails the message, which is retried with bold parts translated alone, then with glossary terms masked, then sentence by sentence; what still fails stays English (`docs/_build/i18n/failed-<lang>.txt`, 0 German and 1 French of ~1200). (2) **Glossary terms are injected into the English sentence before translation**, which gives correct German declension ("The Wassertiefe at the Zuflussrand" -> "Die Wassertiefe am Zuflussrand"); in French rare injected words are translated again ("courbe de tarage" -> "courbe de goudron", "Maillage" -> "Mèche"/"courrier"), so French terms go in **title case** (copied like names, articles and participles agree) and are lowercased afterwards; every injected term must come back (`_terms_came_back`) or the message is retried with the term masked. A message that is only terms and connecting words (`*Mesh*` headings, ``a`` or ``b``) is put together without the engine. (3) Single-asterisk text is the plugin's GUI labels and is never translated; masked parts at the start or end of a paragraph are peeled off (Argos turned a leading label into "Autres"). (4) A German sentence sometimes comes back all lower case; `recapitalize` uses the nouns of the other translations. (5) Articles before glossary terms of known gender are repaired (French `un tâche`, German feminine `des Steuerdatei`), French gets a non-breaking space before `: ; ! ?`, and an aspirated h does not elide (`la hauteur`). Glossaries: `glossary.<lang>.tsv` (`english[|plural] TAB target[|plural] [TAB m|f]`, a target equal to the English keeps it English, per form), `termfix.<lang>.tsv` (source-conditioned regex on the final text, never inside a literal), `keep.txt`.

**Pages and language choice** (`inject_i18n.py`, `assets/lang.js`, only in the GitHub Pages build): hreflang links, a language button fixed in the top right corner of the window (the user, 2026-10-18: "preferably with a button in the top right corner"; a `<details>` menu right after `<body>`, so it needs no JavaScript), a machine-translation note (purple like the note boxes) on /de/ and /fr/, and a trilingual `404.html`. **The address always wins**: a /de/ or /fr/ page is never redirected (so a visitor through axqua.de stays German) and is remembered; only an entry from outside onto an English page goes to the remembered or browser language. Note and info boxes are dark aXqua purple on light purple (`docs/_static/axqua.css`; an info box is `.. admonition::` with `:class: info`). `locale_dirs` in `conf.py` also lets Read the Docs translation projects (`axqua-de`, `axqua-fr`, linked under Admin > Translations) build from the same catalogs, if the user ever adds them.

## Documentation: the outline is a contract (`docs/`, `tests/test_docs_outline.py`)

The outline of sections, subsections and subsubsections was prescribed by `docs/restructuring-instructions.md` (removed by the user on 2026-10-27) and is pinned by `tests/test_docs_outline.py` (plain text parsing, no Sphinx). One file per subsection, subsubsections as `---` headings inside it. The `help-...` labels are what the plugin tabs will open; the test lists them. `docs/conf.py` keeps the whole menu tree in every page and `_static/axqua.css` sets level 1 (Purpose, Installation & Configuration, ...) in bold capital letters (the user, 2026-10-11: "every toplevel item is bold capitalized in the outline"; a style of the menu, the titles in the sources are unchanged). **The menu shows the sections only: level 2 is folded by default** (the user, 2026-10-12: "in the docs menu tree, collapse also the level two items by default"; this replaced the line of `docs/restructuring-instructions.md` that asked for a menu unfolded down to the subsections). A section opens with its fold button or when one of its pages is shown, and a subsection opens its subsubsections in the same way. This is the folding of the theme itself: the rules that forced level 2 open and hid the fold button of a section were removed, the whole tree stays in every page because a section without its subsections in the page gets no fold button, and the one rule left for the folding makes the fold button of a closed section readable on the dark background. `test_the_subsections_are_folded_until_their_section_is_opened` fails when a rule sets the display of a menu level again. **The pictures of the plugin in the workflow pages are taken by `scripts/build_screenshots.py --case <case>`** (the user, same message: "add screenshot in the workflow to highlight how and where these items have to be set up in the plugin GUI"): it starts QGIS without a window through `scripts/qgis_dev.sh` with a QGIS profile in a temporary folder, shows each tab and editor for a built case with a steady result, frames and numbers the widgets a caption explains, and replaces the folders of the computer in every text by neutral ones (`/home/user/...`) before the picture is taken. `SCREENSHOTS` in `tests/test_docs_outline.py` pins which page shows which picture and that a caption counts its marks from (1). The pictures are made with a scratch copy of the Isar example under the name `isar-reach` that also has the blocks `openfoam` and `calibration` (so that those boxes are filled), **with made-up points on the channel centerline as measurement layers and a made-up validation situation** ("High flow", 0.5 and 4.0 m3/s): the first set, of 2026-10-11, was made with the layers of the campaigns and showed the name, a file name and the discharges of the September situation, which the review of the next day found, and nothing of the campaigns is published while their positions are being corrected. Since 2026-10-13 the copy also has a `fine_sediment` block with made-up values (30 um, 20 mg/l) and the two jobs of that simulation, for the pictures of its block in the case editor and of its sub-tab; how the copy is made is in the commit message of the pictures. The same review found that a mark whose widget was not on the screen was dropped and the rest renumbered: the script now fails for that figure, ends with an error, and records the marks of each figure in `docs/img/gui-screenshots.json`, which the test compares with the captions. **The build is warning-free and CI runs it with `-W`**: `conf.py` turns `|Q_in|` in docstrings into literals while autodoc reads them (the absolute-value notation otherwise parses as a substitution reference), skipping text that is already inside an inline literal. `napoleon_preprocess_types` keeps the word `optional` of a parameter type (`name : str, optional`) from being read as a type: it used to become a link to the one attribute called `optional` that the reference documents, and a second attribute of that name makes the reference ambiguous and the build fail. A numpydoc `Parameters` section swallows every paragraph after it, so prose goes *before* it. **The UML diagrams are generated from the source** (`scripts/build_uml.py`, standard library plus Graphviz for the figures): a package diagram whose arrows are the imports that exist (so it shows the two design rules, and also the cycles between the top-level modules and the backends, as they are), and four class diagrams read from the class definitions. The `.dot` texts are committed beside the `.svg` figures and compared by `test_the_uml_diagrams_show_the_code_as_it_is`, which needs no Graphviz: **a new top-level class in `config.py`, `jobs/model.py`, `core/registry.py`, `core/profile.py` and the other files named in `CLASS_DIAGRAMS`, or a new import between two packages, fails that test until the script is run again.** Writing rules for the pages are the user's: Bachelor-level hydraulic engineers, American English, no em dash, no hard-wrapped lines, and a function that does not exist yet gets one "not yet available" note rather than a description.

## Help in the plugin (`axqua docs`)

**Help opens a copy built on this computer first** (the user, 2026-10-18), the published `https://axqua.eu/` (+ `de/`/`fr/` by `QgsApplication.locale()`) otherwise; this replaced readthedocs, whose redirect to `axqua.ch` hit an apex domain without DNS records that day. `axqua docs --json` (`docscli.py`) names the copy (`$AXQUA_DOCS`, else `docs/_build/site` then `docs/_build/html` of the source checkout) and whether the default browser may read it: a snap or Flatpak browser (`xdg-settings get default-web-browser`; told by the desktop files of that name: one in the `snapd` or `flatpak` export folders, or the `Exec` of the one the desktop uses (group `[Desktop Entry]`) starting a snap or a Flatpak: named so (`/snap/bin/`, `snap run`, `flatpak run`), or its program, found on `PATH` past `env VAR=...`, resolving to the snap launcher or into a Flatpak folder, or being a launcher script that starts one (Ubuntu's `/usr/bin/firefox`; Debian's wrapper for firefox-esr, which this computer has, does not); so a copy a menu editor wrote in `~/.local/share/applications` still counts; the name `<snap>_<app>.desktop` or a reverse-DNS id decides only where no file is found: GNOME Web of the operating system is `org.gnome.Epiphany.desktop`, reviews of 2026-10-18) reads only non-hidden folders below the home folder, so a copy in `/srv` goes to the published docs there. A local `file://...#label` is opened through `_help/open.html` written beside the copy (meta refresh + `location.replace`), because `xdg-open` and Chromium drop the fragment of a file URL and `/tmp` is invisible to a snap; `deploy.sh` excludes `_help`.
